# Why does a program whose global functions call the next one in both branches take tens of seconds to load, and how does moving call-stack checks onto the call graph change the frame limit?

Because the verifier computes its call-stack rules by walking every chain of calls the program can take, and the number of chains grows exponentially while the number of calls does not. If each of N global functions calls the next one in both branches of an `if`, the program executes N calls and presents 2^N chains. The posting measures 24 such functions at 1.3 seconds to load and 28 at 24 seconds. None of the properties the walk enforces actually needs a chain: they depend on who calls whom. The proposed change builds a call graph after the main verification pass and computes the same properties there, which flattens that curve — 28 functions load in 0.7 milliseconds. Once no rule needs a chain, the frame limit no longer has to be small to keep the walk cheap, and the same posting raises it from 16 frames to 32, with a deliberate 16-frame limit left for the interpreter. Both changes move verdicts as well as cost, so a program can load where it used to be rejected, and a program that only breaks a rule in dead code or in an asynchronous callback can now be the one that gets rejected.

## The mechanism

1. **What the walk does today.** One function in the verifier walks the chains of calls of the program, starting from each entry point. It sums the bytes of stack and the bytes of the stack in arena along the chain, counts frames, marks which subprograms are reachable from a callback, marks which ones reach a tail call, and rejects recursion. It also decides whether a subprogram can have a private stack. Because it descends per chain, a subprogram reached from several places is walked once per path that reaches it. That is where the cost comes from: the diamond shape above visits every join again for every way of getting there. The posted numbers are 16 functions at 4 milliseconds, 20 at 70 milliseconds, 24 at 1.3 seconds, 28 at 24 seconds, and 30 at 105 seconds.

2. **What the graph is.** The first patch builds, after the main verification pass, one bitmap of callees per subprogram plus its transitive closure, so the verifier knows directly what each subprogram calls and what it gets to. The edges are exactly the ones the walk followed, dead code included: a direct call of a subprogram, the address of a subprogram — unless that subprogram is an asynchronous callback — and what the main pass recorded for a computed call and for helpers that run callbacks. Live subprograms are the main program, the asynchronous callbacks, and whatever those reach. Recursion becomes a set test: a live subprogram that gets to itself. Cycles through the address of an asynchronous callback are still rejected by the existing topological sort, which stays in place, so among live subprograms what remains is acyclic.

3. **Why the properties stop needing chains.** Each property is a fact about edges, not about paths. "Runs in a callback" is the set of callbacks plus everything they get to; the two instructions that a callback may not use are then looked for in that set instead of in every chain that passes through a callback. "Reaches a tail call" is the live subprograms that have a tail call or get to one: in a graph where the main program reaches a tail call through two different callers and one unrelated branch, all subprograms on both paths are marked and the unrelated branch is not, which is exactly the marking the walk produced by unwinding its caller chain. The need for a stack in arena flows backwards from callee to caller and stops at a callback, because the kernel calls a callback without setting up that register. Only three sums are left: bytes of stack, bytes of the stack in arena, and frames. Each is a longest-path value on an acyclic graph: a callee's depth is the largest, over its callers, of that caller's depth plus the caller's own frame, computed by relaxation from zero at the main program and at each asynchronous callback until nothing changes. Then each live subprogram's own sums are compared with the limits.

4. **What the frame limit is, and what raising it costs.** The current limit is 16 frames per chain, enforced in two places: the walk itself, and the main pass, which has a fixed-size array of frames per verifier state. Both report the same message with the frame count. The new limit is 32 for programs that are compiled, and 16 stays as what the interpreter has stack for, so a longer chain sets the flag that makes the program require the JIT — the same mechanism a computed call already uses. Where the JIT is always on, that check changes nothing. Raising the limit touches packed formats: the frame number in the jump-history entry grows from 4 bits to 5, the register index packed next to it shrinks from 11 bits to 10, the mask of frames in liveness widens to 32 bits, and one tracked-argument structure is explicitly packed so its array stays 10 bytes per instruction. Each verifier state also carries 16 more pointers. The measured memory cost is 4% on the selftests, 3% on a scheduler project, and 1% on a large production loader, by peak-memory comparison of the same objects. The verifier's own pre-pass that follows a chain which passes a pointer to the stack recurses once per frame, 264 bytes per frame on one compiler and architecture, so the longest accepted chain takes about 8.25K of a 16K kernel stack.

5. **Which verdicts move.** One real rule change: a tail call inside an asynchronous callback that calls nothing is now rejected. The walk started every entry point with "no tail call seen", so it never looked at that callback; such a tail call can only be dead code, because an asynchronous callback gets no context to tail call with, and the rule that forbids tail calls in callbacks applies to every other callback. The remaining differences are in what the log says. The recursion message names the last call of the cycle, which with several subprograms on the cycle can be a different call of the same cycle than before. When several subprograms exceed a limit, the message is about the first one in the program and carries the numbers of its longest chain, not of the chain the walk happened to reach first. A program that breaks two rules can get the other message and a different error code, because several of these checks now run before any walk. One case that previously failed with no text at all now reports itself: a chain deeper than the limit that passes a pointer to the stack used to return an error with no message from the pre-pass, and now prints which call is the problem plus the too-many-frames message and returns the same error code the main pass uses. Note that the two counters differ by one on purpose: the main pass counts the main program as a frame, the depth check does not, so the boundary test accepts 32 and rejects 33 and tolerates either number in the message.

## How to verify and debug

1. **Measure the shape, not just the size.** Build a program where each generated function calls the previous one from both branches of an `if`, and load it at increasing N. On a current kernel the load time doubles with every function, which is the giveaway: a program that is slow to verify for its instruction count is likely paying for chains. The posted test does exactly this, and the same program shapes go from 24 seconds at 28 functions to 0.7 milliseconds with the change. If your program has a few join points rather than a grid, the walk is not your problem: in the posted comparison the whole walk was under 0.1% of the verification time of two large production programs.

2. **Read which message you actually got.** Three limits report separately: the frame-count message with a number of frames, the combined-stack-size message with a number of calls and a number of bytes, and the tail-call message that complains about the bytes already on the stack. The first is the one this change moves. The other two count summed stack bytes and are unaffected, so a program rejected by them is not near the frame limit.

3. **Count frames the way the verifier does.** The limit is a static call-depth limit, per entry point. A global function starts a new count, so what matters is the chain of static calls inside one global function or inside the main program. Tail calls do not add frames; they unwind the frame that makes them, which is why a tail-call chain can be long while its frame count is not.

4. **Check the JIT before depending on a long chain.** On a kernel with the change, a chain longer than 16 frames requires the JIT, and such a program does not fall back to the interpreter if compilation fails — it fails to load. The selftests that exercise a longer chain are marked to run only with the JIT for exactly this reason, because with the JIT off they get the message about the JIT instead.

5. **Test the boundary deliberately.** The added selftests pin the edges: a chain of exactly 32 frames loads, a chain of 32 frames that passes a pointer to the stack returns its expected value, and the same shape at 33 frames is rejected. There is also a case that fails inside the deepest frame on the second path verified, which only works if the saved frame numbers in the jump history and in the liveness masks are wide enough — that is the test that would catch a broken packed field, and nothing else in the suite exercises a frame number above 15.

## The limitation

- This is a posting to the development tree, not a released kernel. Released kernels still have 16 frames and still walk the chains, so treat both the exponential load cost and the 16-frame boundary as live constraints until it lands.
- The 32-frame limit is for compiled programs; the interpreter stays at 16. On architectures where the JIT can be turned off, a long chain turns into a load failure rather than a slow run.
- One runtime question in this window is unresolved. The only rule that bounds compiled calls combined with tail calls is the check that the summed BPF stack of the callers of a tail-calling subprogram stays under 256 bytes, and that sum counts BPF stack only — not the kernel stack a compiled frame takes, which on one architecture is at least 32 bytes per tail-call-reachable frame even with an empty BPF stack. Since a tail call unwinds only its own frame and the counter is shared, a deep chain that tail calls can repeat that residue up to 33 times. The review reply in this window works the arithmetic at 32 frames and gets about twice the thread stack size, notes that the gap predates the change, and asks whether the tail-call-reachable chains should be capped at the interpreter's 16 frames or whether the per-frame cost should be added to the 256-byte check. No answer had been posted.
- Verification memory grows with the limit, so a loader that verifies many programs in parallel pays the difference even for programs that never use a long chain.
- If a tool matches on verifier log text, expect drift: a program that violates two rules can now produce a different message and a different error code, and the recursion message can name another call of the same cycle.
- The deep-nesting programs named as the motivation for the higher limit still do not all load; the posting says they need further verifier work beyond this series.

## Community discussion today

This run reviewed six allowlisted communities, thirteen allowlisted channels. The three channels reachable through the approved private read-only archive carried no message in the 24-hour window, so they are reported as quiet rather than skipped; in the seven-day window the archive-backed observability workspace carried five messages, summarized below. The ten channels in the two chat workspaces that have no archive were not covered: this environment has no authenticated session for them, and the visible browser lands on a login page, so they are recorded as inaccessible, not quiet. One kernel mailing list and one practitioner forum were read through their public pages. That is four sources with content or a confirmed empty window, and two not covered. The forum's older read-only interface now requires an account, so it was read through its ordinary public listing page, and its own post timestamps were used to date the newest threads.

The mailing list carried the question answered above, and the rest of the window splits into two themes: a map operation whose safety today depends on timing, and compiler drift that silently changes what the verifier can prove. The first is a small fix posted the day before and reviewed inside this window: inserting a new key or deleting from a runtime hash-table map while interrupts are disabled can deadlock, because the bucket lock is held with interrupts off, so a same-CPU re-entry spins forever. The patch adds an interrupt check that makes both operations return the busy error. The review reply argues that check is too broad, and its list of what it breaks is exactly the list of things practitioners attach: sampling programs, kprobes that trap through a breakpoint, the scheduler context-switch and wakeup tracepoints, and scheduler-extension callbacks run under the run-queue lock. The alternative posted instead is conditional — try the bucket lock when the caller already has interrupts off, spin otherwise — and its table is worth reading as a decision procedure: nothing locked, works today and keeps working; locked by another CPU, used to spin, now reports busy; locked by this CPU, used to hang, now reports busy. The same reply names one bug the alternative still leaves, because the resize path allocates with an interrupt-safe flag, which is not safe inside a non-maskable interrupt, and it changes lookups too, since a walk that starts from a chain the local CPU is midway through rehashing would otherwise retry forever. The practical reading for a practitioner is unchanged on either design: a busy error from a map insert or delete in a sampling or scheduler context is now a real possibility, and the difference between the two designs is only whether an unrelated interrupt-disabled caller pays for a rare deadlock.

The second theme is proof lost between the compiler and the verifier. One report shows a correct program failing to load because a sign extension of a value read from memory leaves the verifier with no link between the two registers: narrowing a comparison of the low half therefore cannot narrow the register that is returned, and the rejection text names the full 32-bit signed range where a much narrower value was expected. The fix makes equality tracking work on the low 32 bits rather than all-or-nothing on 64, and it also clears a restriction that a selftest has recorded since 2023, where a condition narrowed one register but not the one holding the same low half. A two-line selftest change shows the same drift from the other side: a compiler change stopped folding the result of a global function into zero, and since the verifier assumes nothing about what a global function returns, an entry program that must return zero now fails at exit with an unknown scalar and every subtest of that suite fails — on one flavor only, because the other flavors skip the program. The third item is about capability rather than proof: a second revision of the user-memory kernel functions adds sleeping functions that copy into the current task's address space and create or remove private anonymous mappings with optional execute permission. The motivation is concrete — rewriting a function in a live process, changing a process's environment — and the boundary is that the existing helper which writes to user memory disables page faults during the copy, so it cannot fault, while these new functions run in a sleeping program and can. The last item is tool behavior: a ninth revision of using batch lookups for map dumps, which falls back to individual lookups from the last printed key after a batch error, and whose latest changes are selftest-only — presizing a growing map so asynchronous growth does not perturb order-sensitive comparisons, and correcting which error number a hash-bucket lock failure actually returns today.

The archive-backed channels were empty in the 24-hour window, and five messages in the seven-day window of one of them form a third theme: who owns a piece of instrumentation, and when an attribute is stable enough to adopt. Three review requests were waiting on maintainer attention — an instrumentation for a local model server, an adoption of the per-operation cost attributes that the conventions repository has been developing for months without settling them, and a switch that turns off a vendor framework's own trace export so that the instrumentation path is the only one. The last drew the objection that the decision belongs to the vendor framework's configuration rather than to an environment variable read by the instrumentation, and the answer given was that the instrumentation already ships the equivalent control for manual instrumentation. That is the recurring shape: adoption of unsettled conventions stalls because a team that wants the attributes today cannot predict their names after a rename, and a control that removes a double export is contested on ownership rather than on mechanism. None of the three had been decided when this page was written; all were still open, and the cost-attribute request has been the longest-running of them.

On the practitioner forum no post arrived inside the 24 hours: the newest was posted about twenty-one hours before the window opened, and the one before it ten hours earlier. The newer is a security agent that learns a machine's normal behavior and then reacts in the kernel — cutting a process's network, and stopping a process rather than killing it. Stopping is the reversible choice, and it is reversible by mechanism: the stop signal keeps the process and its state in memory until it is continued, while a terminated process has to be started again, which is what lets the author promise that a false positive does not take anything down. The comments got past the demo and onto the two boundaries that matter for any learn-first design: an intruder already present during the learning window poisons the baseline, and a routine package upgrade produces exactly the signal the detector was built to find, a new binary spawning unfamiliar children. The answer was candid — in alert-only mode drift is simply absorbed, the exposure is enforcement during a deploy window, and a maintenance-mode relearn is what covers it — and it conceded a gap: the tool watches outbound connections and does not yet treat a newly opened listening socket as a signal, which is the drift a listener-binding intrusion produces. The other thread is a continuing one about evaluating detectors against a self-built rootkit, and its unanswered half is still the ramp-up estimate that nobody can give a stranger.

The forum's longest-running report is a socket-level port scanner, and it is worth closing the loop on, because two questions it left open have documented answers. Its numbers were corrected in public first: the author's original speedup came from a bug, since the benchmark scanned one host of two and reported a time below the floor its own rate limit implied, so the figure was withdrawn and the benchmark rebuilt to assert that every run finds its expected ports and to record CPU time and dropped frames. The rebuilt run puts this path level with the reference tool on wall-clock time at about a third of the CPU of a raw socket scan, and behind a raw scan that is allowed to fan out across cores. Two general causes sat behind that. A receive thread spinning on a pinned CPU is harmless on an idle laptop and actively harmful on a loaded machine, where it competes for the single virtual core. And one transmit call per probe dominated on a slow host; batching sixty-four frames into one call largely removed it. What remained open was asked twice. Parallel sending is capped because every ring is single-producer and single-consumer and each socket brings its own transmit and receive rings, so more senders means more sockets plus a driver that drives more queues — the zero-copy multi-queue hardware the author cannot test. And the optional wakeup flag exists only on the rings that user space produces to, where it means the kernel must be told explicitly by a poll or a send call; on a copy-mode ring it saves a call only when the kernel is already idle, which is precisely the case batching has already removed.
