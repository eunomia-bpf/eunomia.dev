# 为什么一个「每个全局函数在两个分支里都调用下一个」的程序要加载几十秒，而把调用栈检查搬到调用图上又如何改变了帧数上限？

因为校验器计算调用栈规则的方式，是把程序能走的每一条调用链都走一遍，而链的数量随函数数量指数增长，调用的数量却不是。如果 N 个全局函数每一个都在 `if` 的两个分支里调用下一个，程序一共执行 N 次调用，却呈现出 2^N 条链。送审材料里的实测是：24 个这样的函数加载要 1.3 秒，28 个要 24 秒。而这条链上的检查要判定的性质，没有一条真的需要一条链：它们只取决于谁调用谁。送审的改动在主验证趟之后建起一张调用图，在图上算出同样的性质，于是这条曲线被压平——28 个函数 0.7 毫秒。一旦没有任何规则还需要链，帧数上限就不必再为了「让这趟遍历便宜」而保持很小，同一份送审把上限从 16 帧提到 32 帧，并且有意给解释器留下 16 帧。这两处改动都会移动判决，而不只是移动成本：原本被拒绝的程序现在可能通过加载，而一个只在死代码里、或只在异步回调里违反规则的程序，现在可能正是被拒绝的那一个。

## 机制

1. **现在这趟遍历在做什么。** 校验器里有一个函数从每个入口出发，把程序的调用链一条一条走完。它沿链累加栈的字节数与 arena 里栈的字节数，数帧数，标记哪些子程序位于回调之内，标记哪些能到达尾部调用，并拒绝递归；它同时决定一个子程序能不能用私有栈。因为它是按链下探的，一个被多处到达的子程序，每来一条路径就会被重走一次。代价就出在这里：上面那种菱形结构里，每一个汇合点都会被它每一条到达路径重新访问。送审给出的数字是 16 个函数 4 毫秒、20 个 70 毫秒、24 个 1.3 秒、28 个 24 秒、30 个 105 秒。

2. **这张图是什么。** 第一个补丁在主验证趟之后，为每个子程序建一张被调方位图，再加上传递闭包，于是校验器能直接知道每个子程序调用谁、又能到达谁。图的边正是那趟遍历走过的边，死代码也算：对子程序的直接调用、子程序的地址（异步回调除外），以及主验证趟为计算式调用与会执行回调的辅助函数记录下的目标。所谓活跃子程序，就是主程序、异步回调，以及它们能到达的一切。递归于是变成一个集合判断：一个活跃子程序若能到达自己，就是递归。经过异步回调地址的环仍然由已有的拓扑排序拒绝，那个排序保留不动，所以活跃子程序之间剩下的是无环的。

3. **为什么这些性质不再需要链。** 每条性质说的都是边的事实，不是路径的事实。「运行在回调里」就是回调集合加上它们能到达的集合；于是回调不许使用的那两条指令，只需在这个集合里的子程序中查找，而不是在每一条穿过回调的链里查找。「能到达尾部调用」就是有尾部调用或能到达尾部调用的活跃子程序：在一幅主程序经由两个不同调用方到达尾部调用、另有一条无关分支的图里，两条路径上的所有子程序都被标记，那条无关分支不被标记——这正是原来那趟遍历靠回溯调用方链得到的标记结果。对 arena 里栈的需求则从被调方向调用方反向传播，到回调为止，因为内核调用回调时不会设好那个寄存器。只剩下三个累加量：栈字节、arena 里栈的字节、帧数。每一个都是无环图上的最长路数值：被调方的深度，是它所有调用方中「该调用方的深度加上该调用方自己的帧」的最大值，从主程序与每个异步回调处的 0 开始反复松弛，直到没有任何变化。然后把每个活跃子程序自己的累加量拿去和上限比较。

4. **帧数上限是什么，提高它要付什么。** 目前的上限是每条链 16 帧，在两处执行：那趟链遍历本身，以及主验证趟——后者为每个校验器状态准备了一个固定长度的帧数组。两处报的是同一条带帧数的消息。新的上限对编译型程序是 32 帧，16 帧保留为解释器栈所能承受的量，于是更长的链会置起那个让程序必须使用 JIT 的标志——这与计算式调用已经在用的机制相同。在 JIT 恒开的内核上，这个判断不改变任何行为。提高上限要动到位域：跳转历史项里的帧号从 4 位扩到 5 位，与它打包在一起的寄存器索引从 11 位缩到 10 位，活跃性分析里的帧掩码放宽到 32 位，还有一个参数跟踪结构被显式压缩对齐，好让它那个数组保持每条指令 10 字节。每个校验器状态还要多带 16 个指针。实测的内存代价是：自测集 4%、一个调度器项目 3%、一个大型生产加载器 1%，按同一批产物的峰值内存比较得出。校验器自己那一趟沿「把栈指针传下去」的链走的预分析，每帧递归一次，在某个编译器与架构下每帧 264 字节，所以最长的可接受链要占掉 16K 内核栈里约 8.25K。

5. **哪些判决会移动。** 真正改变规则只有一处：一个什么都不调用的异步回调里的尾部调用现在会被拒绝。原来那趟遍历从每个入口出发时都带着「还没见到尾部调用」，所以它从没有看过那个回调；这种尾部调用只可能是死代码，因为异步回调拿不到用来做尾部调用的上下文，而禁止在回调里做尾部调用的规则对其他每一个回调都成立。其余的差别都在日志文字上。递归的消息会点出环上的最后一次调用，当环上有多个子程序时，点出的可能是同一个环上的另一次调用。当多个子程序超过某个上限时，消息说的是程序中第一个超出的那个，并带上它最长那条链的数字，而不是那趟遍历先走到的那条链。一个同时违反两条规则的程序可能拿到另一条消息和另一个错误码，因为其中几项检查现在都在任何遍历之前执行。有一种过去完全没有文字的情形现在会自己报出来：一条把栈指针传下去、深度超过上限的链，过去从那个预分析返回错误却没有消息，现在会打印出问题出在哪一次调用，并给出与主验证趟相同的「帧数过多」消息和相同的错误码。还要注意两个计数器故意相差 1：主验证趟把主程序也算作一帧，深度检查不算，所以边界测试接受 32、拒绝 33，消息里出现哪个数字都容忍。

## 验证与排障路径

1. **量形状，别只量规模。** 造一个程序：每个生成的函数都从 `if` 的两个分支调用前一个，然后逐步加大 N 去加载。在当前内核上加载时间每多一个函数就翻倍，这就是特征：一个相对指令数验证得很慢的程序，多半正在为链付钱。送审的测试正是这么做的，同一批程序形状从 28 个函数 24 秒变成改动后的 0.7 毫秒。反过来，如果你的程序只有少数几个汇合点而不是网格，那这趟遍历不是你的瓶颈：送审的对比里，在两个大型生产程序上整趟遍历占验证时间不到 0.1%。

2. **读清你拿到的到底是哪条消息。** 三条上限各自报信：带帧数数字的那条帧数消息、带调用次数和字节数的合并栈大小消息、以及抱怨栈上已有字节数的尾部调用消息。这次移动的是第一条。另外两条数的是累加的栈字节，不受影响，所以被它们拒绝的程序并不在帧数上限附近。

3. **按校验器的口径数帧。** 这个上限是静态调用深度上限，按入口计算。一个全局函数会重新开始计数，所以真正要紧的是单个全局函数内部、或主程序内部那条静态调用链。尾部调用不增加帧；它把自己那一帧退掉，这正是尾部调用链可以很长而帧数不大的原因。

4. **依赖长链之前先检查 JIT。** 带上这个改动的内核上，超过 16 帧的链要求 JIT，而且这样的程序在编译失败时不会退回解释器——它会加载失败。测试更长链的自测正因为这一点被标成只在 JIT 下运行：关掉 JIT 时它们拿到的是关于 JIT 的那条消息。

5. **故意测边界。** 新增的自测把边界钉住了：正好 32 帧的链能通过加载；一条 32 帧、把栈指针传下去的链返回它的预期值；同样的形状到 33 帧就被拒绝。还有一个在最深层帧里失败、且位于第二条被验证路径上的用例，它只有当跳转历史和活跃性掩码里保存的帧号足够宽时才能工作——那就是能抓住位域写坏的那个测试，测试集里没有别的地方会用到大于 15 的帧号。

## 局限

- 这是投向开发树的送审，不是已发布内核。已发布内核仍是 16 帧，仍要走链，所以在它落地之前，指数级加载成本和 16 帧这条边界都还是活的约束。
- 32 帧上限只适用于编译型程序；解释器停在 16 帧。在 JIT 可以关闭的架构上，长链会变成加载失败，而不是变慢运行。
- 本窗口里有一个运行时问题仍未解决。唯一约束「编译型调用与尾部调用混合」的规则，是那个「会做尾部调用的子程序，其各层调用方累加的 BPF 栈必须小于 256 字节」的检查，而这个累加只数 BPF 栈——不数一个编译帧实际占用的内核栈，而某个架构上每个可达尾部调用的帧即使 BPF 栈为空也至少占 32 字节内核栈。由于一次尾部调用只退掉自己那一帧、而计数器是共享的，一条深链上的尾部调用可以把这份残留重复 33 次。本窗口的评审回复按 32 帧算了这笔账，得出大约是线程栈大小两倍的数字，指出这个缺口早于本次改动就存在，并问是否应当把可达尾部调用的链限制在解释器那 16 帧，或者把每帧成本加进那个 256 字节的检查。截至本窗口结束还没有人回复。
- 验证所用内存随上限增长，所以一个并行验证大量程序的加载器，即为从不使用长链的程序也要付这笔差额。
- 如果有工具去匹配验证器日志文字，要预期漂移：同时违反两条规则的程序现在可能给出另一条消息和另一个错误码，递归消息也可能点出同一个环上的另一次调用。
- 被引为提高上限动机的那些深嵌套程序，目前并非全都能加载；送审说它们还需要本次送审之外的进一步校验器改动。

## 当日社区讨论

本轮复核了六个清单内社区、十三个清单内频道。经批准的只读私有归档所能到达的那三个频道，在 24 小时窗口内没有任何消息，因此按「安静」而非「跳过」记录；在七天窗口内，归档内的可观测性那个工作区有五条消息，综合在下方。两个没有归档的聊天工作区里的十个频道本轮未覆盖：本环境没有它们的登录会话，可见浏览器停在登录页，所以记为不可到达，而不是无活动。一个内核邮件列表与一个实践者论坛通过其公开页面读取。合计：四个社区有内容或确认为空窗口，两个未覆盖。该论坛的旧版只读入口如今要求账号，因此本轮通过其普通公开列表页读取，并用页面自身的发布时间属性核对了最新两帖的日期。

邮件列表承载了上面回答的问题，它之外的窗口分成两条线索：一个是今天的安全只是靠时序侥幸的 map 操作，另一个是编译器漂移悄悄改变了校验器还能证明什么。第一条是一份前一天贴出、并在本窗口内被评审的小修复：在中断关闭的状态下往运行时哈希表 map 插入新键或做删除可能死锁，因为桶锁本来就关中断持有，同一个 CPU 的重入会自旋到永远。补丁加了一个中断状态检查，让这两种操作直接返回忙碌错误。评审回复认为这个检查过宽，而它列出的会被打破的对象，恰好就是实践者会挂上去的东西：采样程序、经断点陷入的 kprobe、调度器的上下文切换与唤醒 tracepoint、以及在运行队列锁下执行的调度器扩展回调。回复给出的替代方案是有条件的——调用方已经关中断时就去试取桶锁，否则照常自旋——而它那张表值得当作判定流程来读：桶没被锁住，今天能工作、之后也能；被别的 CPU 锁住，过去自旋，现在报忙碌；被本 CPU 锁住，过去死锁，现在报忙碌。同一份回复还点出替代方案仍留下的一个缺陷：扩容那条路径用带中断安全标记的分配，这在不可屏蔽中断里并不安全；它也改到了查找，因为一次从本 CPU 正在重排的链上出发的遍历，否则会永远重试。对实践者来说两种设计下的读法一样：在采样或调度上下文里，map 插入或删除返回忙碌错误都成了真实可能，两者的差别只是「与本次操作无关的关中断调用方要不要为一次罕见死锁付钱」。

第二条线索是编译器与校验器之间丢掉的证明。有一份报告是一个正确的程序无法加载：从内存读出的值做符号扩展之后，校验器在两个寄存器之间建立不起任何关联，于是对低半部做比较的收窄无法收窄那个最终返回的寄存器，拒绝信息里给出的是完整的 32 位有符号范围，而本该是很窄的值。修法是把等值跟踪做成作用于低 32 位，而不是 64 位全有或全无；它同时解除了一条自测从 2023 年起就记录在案的限制——一次条件判断收窄了一个寄存器，却收不到那个共享同一低半部的寄存器上。另一处两行的自测改动从反方向展示同一种漂移：一次编译器改动不再把全局函数的返回值折叠成 0，而校验器对全局函数返回什么一概不做假设，于是一个必须返回 0 的入口程序在退出时因「未知的标量值」失败，该测试套件的每个子测试都失败——而且只在一个变体上暴露，因为其余变体没有这个程序而直接跳过。第三条讲的是能力而非证明：用户内存那组内核函数的第二版送审，加入可睡眠的函数，可以往当前任务的地址空间拷数据，也可以创建或解除私有匿名映射并可选带上执行权限。动机很具体——在活进程里替换一个函数、改进程的环境变量——而边界是：现有的写用户内存辅助函数在拷贝期间会关掉缺页处理，因此它不能缺页；这些新函数跑在可睡眠程序里，可以缺页。最后一条是工具行为：map 转储使用批量查找的第九版送审，批量出错后从最后一个已打印的键继续逐个查找，而这一版的改动只在自测——把一个会增长的 map 预先定容量，免得异步扩容扰乱对顺序敏感的转储比较，以及更正哈希桶锁失败今天实际返回的是哪个错误号。

第三条线索来自归档：归档所及的频道在 24 小时窗口内是空的，而其中一个频道七天窗口里的五条消息共同构成一个主题——一段插桩归谁负责，以及一个属性要稳定到什么程度才值得采用。有三处评审请求在等维护者：一个针对本地模型服务的新插桩；一个采用「按操作成本」属性的请求，那套约定在约定仓库里已经开发了好几个月而仍未定稿；还有一个开关，用来关掉某厂商框架自带的 trace 导出，好让插桩成为唯一路径。最后一处引来的反对意见是，这个决定该由厂商框架自己的配置来定，而不是由插桩去读一个环境变量；给出的回答是，插桩在手动插桩那边已经带了同样的开关。这就是反复出现的形状：未定稿的约定之所以没人采用，是因为今天就想用这些属性的人无法预测它们改名之后叫什么；而一个消除重复导出的开关，争的是归属而不是机制。写下这一页时，三处请求都还没有结论，全部仍处开放状态，其中成本属性那处是存在时间最长的。

实践者论坛在 24 小时窗口内没有新帖：最新一帖发布于窗口打开前约 21 小时，再前一帖又早十小时。较新的是一个先学习机器「常态」、随后在内核里动手的安全代理：切断某进程的网络，以及把进程冻住而不是杀掉。冻住是可逆的选择，而且它的可逆有机制根据：停止信号把进程连同其状态留在内存里直到被恢复，而被终止的进程只能重新起一个，这正是作者能承诺误报不会把东西弄停的原因。评论越过了演示本身，落到任何「先学习」设计都要紧的两条边界上：学习窗口里已经潜伏着的入侵者会污染基线；而一次寻常的升级发布会恰好造出这套检测器被造出来要抓的那个信号——一个新二进制派生出陌生的子进程。回答说得很直：只告警的模式会把漂移直接吸收掉，真正的风险在发布窗口里执行策略，覆盖它的就是维护模式重新学习；同时承认一处空缺：这个工具看的是出站连接，暂时没把「新出现一个监听套接字」当成信号，而这恰恰是绑定监听端口那类入侵造成的漂移。另一帖是延续中的讨论，关于自建一个内核 rootkit 反过来评测检测工具，它未获回答的那一半仍然是那个没人能对陌生人给出的上手时间估计。

论坛里连载最久的是那个套接字层端口扫描器的报告，值得把话收尾，因为它留下的两个问题在文档里本就有答案。先说数字，因为它们是公开修正过的：作者最初那个加速来自一个缺陷——基准只扫了两台目标中的一台，报告的时间还低于程序自身限速推出的下限——于是数字被撤回，基准重建为每次运行都校验找齐了预期开放的端口，并记录 CPU 时间与丢帧数。重建之后的结论是：拷贝模式下这条路径与参照工具在墙上时间上打平，CPU 约为裸 socket 扫描的三分之一；而允许跨核展开时，裸扫描更快。背后有两个通用原因。绑核自旋的接收线程在空闲笔记本上无害，在负载机器上却主动有害，因为它在抢那唯一一个虚拟核；现在它只在零拷贝模式下启用，拷贝模式的路径改为在 poll 中阻塞。另一个是每个探测包一次发送调用，在慢机器上几乎就是全部墙上时间；把最多 64 帧批量进一次调用后基本消掉了它。剩下两个问题被问过两次。发送并行度有上限，是因为每个环都是单生产者单消费者，而且每个套接字自带一个发送环和一个接收环，所以要多路并发就得开更多套接字，再加上能驱动多队列的网卡——那正是作者手上没有的零拷贝多队列硬件。而那个可选的唤醒开关只存在于用户态作为生产者的那些环上，在发送环上的含义是：必须由用户态用 poll 或一次发送调用显式告知内核；于是在拷贝模式的环上，它只在内核本已空闲时才省下一次调用，而这恰好是批量提交已经消掉的那种情形。
