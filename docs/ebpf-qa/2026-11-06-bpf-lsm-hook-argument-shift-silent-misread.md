# Why does adding a mount idmap argument at the front of the inode LSM hooks silently shift every BPF LSM argument, and what can catch it?

Because a BPF LSM program does not name the arguments it receives. The `BPF_PROG` macro turns a declared parameter list into positional reads of an untyped array of 64-bit context slots, and the kernel types each slot from the *kernel* hook prototype at that index, not from the program's declaration. Inserting one new argument in position 0 of six inode hooks therefore moves every existing argument one slot to the right for programs compiled against older headers, and nothing in the load path notices: the program loads, the fields are read at offsets computed from the program's own type declarations, and the values come out of the wrong object. The kernel commit that did this is in 7.4-rc1; the same shape of change already happened to the `inode_setattr` hook in 6.9.

## The mechanism

1. **What the kernel changed.** One commit, whose message says the security layer could not tell an identity-mapped upper from an idmapped one in overlay-style operation, passes the mount idmap down to the inode-based hooks so security modules see what the VFS already sees. Its signature change is mechanical: `inode_create`, `inode_link`, `inode_symlink`, `inode_mkdir`, `inode_mknod`, and `inode_permission` each gain `const struct mnt_idmap *idmap` as the first parameter. The mode or mask argument, the dentry arguments, and the inode arguments keep their relative order but all shift by one position. The 6.9 precedent is the same: `inode_setattr` went from `(dentry, attr)` to `(idmap, dentry, attr)` when the hook definition was aligned with what EVM registers.

2. **How a program receives them.** For an LSM program, libbpf's `BPF_PROG` emits a wrapper `name(unsigned long long *ctx)` that calls an inlined helper, and the helper's parameter list is expanded by `___bpf_ctx_castN` into `ctx[0]`, `ctx[1]`, `ctx[2]`, and so on, in declaration order, cast to the declared pointer types with `-Wint-conversion` suppressed. The declaration is therefore a list of *slot indices*, not a binding by name or by type. Compiling the resulting object and dumping its BTF shows the program entry has exactly one parameter, `unsigned long long *ctx`: after inlining, the declared parameters exist only in the C source.

3. **How the kernel types them.** At load, only the kernel side has a prototype. `btf_ctx_access` maps a context offset to an argument index, reads the type of that argument from the attach target's function prototype, and for a pointer to a struct returns `PTR_TO_BTF_ID` with the BTF id of the *pointed-to* type at that position. So on a 7.4 kernel, slot 0 is an `mnt_idmap` pointer and slot 1 is an `inode` pointer, whatever the program believes. One slot past the last argument is reserved for the return value of the hook, which is why a program compiled with more parameters than the hook has still loads.

4. **Why the type mismatch is not caught.** A program that dereferences a context argument directly would at least be checked against the wrong type, and often rejected. A program that walks fields with `BPF_CORE_READ` is not checked at all: the macro lowers to `bpf_probe_read_kernel(dst, size, (const void *)__builtin_preserve_access_index(src))`, whose third argument is typed `ARG_ANYTHING`, so any pointer is accepted. The field offset is not taken from the kernel object at load time either; CO-RE relocates the offset of the field within the type the *program* declared, and that constant is added to whatever pointer arrived in the slot. A mismatch thus becomes a plain kernel-memory read at a valid-looking offset, and the helper reports success.

5. **Why the values come out as they do.** The offsets are known from the running kernel's own BTF. In the layout of the reporting machine, `i_ino` sits at offset 64 of `struct inode`, and `d_name` is at offset 32 of `struct dentry` with `qstr.name` a further 8 bytes in, so the string read is at offset 40. After the shift, the pointer that the program reads `inode->i_ino` from is an `mnt_idmap`, and 64 bytes into a 136-byte `mnt_idmap` is the second id map: `nop_mnt_idmap`, the static object the VFS passes when nothing is idmapped, initializes only its refcount, so that region is zero and the inode number prints as 0. The pointer the program reads a dentry name from is an `inode`, and 40 bytes into an inode is the superblock pointer, so the string helper is handed a pointer to a superblock and the reported name is empty. `bpf_probe_read_kernel_str` zeroes the destination when the copy fails, which is why the symptom is a clean empty string rather than obvious garbage.

6. **Why it is not just a CO-RE problem.** CO-RE relocates *field offsets* and type existence; it has no relocation for *which argument slot a parameter comes from*. A single binary is therefore wrong on one side of such a change by construction: compiled against 7.3-era headers it misreads on 7.4, and compiled against 7.4 headers it misreads on 7.3, because the new first parameter is then bound to the old first slot. Only a per-kernel build, or an explicit check at load time, closes that gap.

## How to verify and debug

1. **Print the hook prototype the running kernel actually exposes.** `bpftool btf dump file /sys/kernel/btf/vmlinux format raw | grep -A2 "FUNC 'bpf_lsm_inode_create'"` shows the `FUNC_PROTO` the verifier will use, in order. On a 7.3 or older kernel the first parameter is `struct inode *`; on 7.4 it is `const struct mnt_idmap *`. Do this before shipping any LSM program that is expected to survive a kernel upgrade, and diff it in CI against the kernel you test on.

2. **Do not trust the source declaration as documentation of the ABI.** Dump the compiled object, for example with `bpftool btf dump file prog.bpf.o format raw`, and confirm what the kernel sees: one `unsigned long long *` parameter. The parameter names and types you wrote are gone by then, which is exactly why no loader-side arity check exists to trigger.

3. **Distinguish a misread from a rejection.** A field offset that lands beyond the size of the wrongly-typed struct is rejected at verification with an access-beyond-struct message. An offset that lands inside it, as here, passes. So a program that loads is not evidence that its arguments are correct; only plausible-looking values in the wrong object can reveal it.

4. **Reproduce with a marker.** Return a constant for the hook, and print the two values the program reads against the values observed from a stable source, such as a kprobe on the same inode, for the same operation. A directory inode number of 0 for a file that demonstrably exists, plus an empty name, is the signature of the shift. On a kernel where the program is correct, the same print shows the real inode number and the created name.

5. **Treat a hook whose prototype changed as a new ABI.** Once you know the layout, rebuilding against the running kernel's `vmlinux.h` removes the ambiguity for that kernel, and adding a build-time assertion on the hook's arity, checked against the target kernel's BTF, turns the silent case into a load-time failure.

## The limitation

- This is not a runtime bug that a fix will make disappear; it is a property of positional context binding plus a signature change in the middle of a released branch. Until an explicit rule or check exists, every LSM program that names inode hook arguments is exposed whenever one of those hooks gains an argument anywhere but at the end.
- The kernel documentation states that arguments to BPF programs are part of the ABI, and then excepts tracing programs that walk kernel internals with helpers such as `bpf_probe_read`. An LSM program is a different program type but does exactly that, so the documented contract can be read either way; that ambiguity is the practical problem, not the mechanics.
- Fields that happen to exist at the same offset in both types cannot be told apart by any of the checks above. A misread can therefore be perfectly plausible: an inode number that is a small integer, or a name taken from a pointer that happened to hold a valid string.
- Adding the same argument at the end of the signature would have been harmless for existing programs, since too few arguments is accepted; that is a convention, not an enforced rule, so nothing stops the next change from repeating the pattern.
- The two remedies available to a program author are both per-kernel: rebuild against the target's headers, or verify the prototype yourself. Neither produces one binary that is correct across the change.

The mailing list carried the question answered above, and the rest of its window forms two themes: interfaces that vanish without an error, and ownership of a buffer on an error path. The first has a second instance today. A kfunc was missing from the vmlinux BTF of a build with a sanitizer enabled: the compiler reassigns the function parameter on one path, so its location list no longer names the entry value, and the BTF generator drops the parameter and then the whole kfunc. With warnings treated as errors that fails the build; without them the build succeeds and the subsystem simply does not register, returning a parameter error from its initcall, so its kfuncs are gone at runtime with no message. The reporter's workaround is to stop reassigning the parameter, and a reviewer's objection is the one that matters for anyone writing kfuncs: it makes argument reassignment look forbidden when the real defect is in the toolchain. The same theme runs through the answered question, and through a struct-ops patch in the window: state that should have been reset on one transition path was left alone, and the automated review reply argued both that the reset helper is not present in the tree the patch claims to be based on, and that calling it on that path would zero a default slice the scheduler had already set.

The second theme is buffer and state ownership when an operation fails. One series fixes an XDP redirect path where the core frees a zero-copy buffer after telling the driver that the redirect failed; the driver is supposed to still own it, and drivers that release it later, after the frame may have been reallocated, hand the same user-memory frame out twice. The patch moves the free to the callers that can do it safely and adjusts the drivers that relied on it. A second series extends a different page-accounting problem: a receive path biases every page refcount to the maximum, so one additional reference from a splice of received data overflows it, and the fix lowers the bias only after restoring a queue-format check that a later commit had dropped, since the redirect path it makes reachable is the one that cannot keep the reference. A third, on the same list, addresses map values that outlive their callbacks: cancelling task work, workqueue work, or a timer on a value being deleted does not stop a callback that already started, so the series re-checks membership by looking the value up again after publishing the callback context, and reports negative controls where the earlier revisions still set up work on a freed element.

The archive-backed observability channels were quiet on the day, and their seven-day window has one three-message thread, about who should own a switch that suppresses a vendor SDK's own trace export in favour of the instrumentation path. The technical content is a configuration-scope argument rather than an eBPF one: the objection is that the decision belongs to the SDK, and the answer is that the instrumentation already repairs the manual path, so the switch only removes a duplicate.
