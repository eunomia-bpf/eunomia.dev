# 为什么挂在套接字钩子上的 cgroup BPF LSM 程序运行在调用方任务的 cgroup 里，而不是套接字自己的 cgroup，提出的修复把 shim 选择改成了什么？

因为挑选 shim 的那段代码一直在比较两种不同类别的 BTF 标识符。程序以 cgroup LSM 类型挂上去时，内核要挑一个 shim，由它决定运行哪一份 cgroup 程序数组，挑选依据是钩子的第一个参数：套接字参数应当意味着套接字的 cgroup，其余情况意味着当前任务。比较时拿参数自身的类型 id 去对一张结构 id 表。参数的类型 id 命名的是指针类型，而表里存的是 `struct socket` 和 `struct sock` 本身的 id，所以两者永远不相等，两个套接字分支都取不到，每个 cgroup LSM 程序都走当前任务那条路。修复在比较之前先把参数的指向类型解出来，套接字分支这才可达。这条补丁投往修复树并请求稳定版回合，它会改变已经部署的程序的行为。

## 机制

1. **设计原本想怎么做。** 按 cgroup 使用 LSM 那套机制的说明直接写了规则：第一个参数是 `struct socket` 或 `struct sock` 的钩子，运行与该套接字相关联的 cgroup 上的程序；其余钩子运行当前 cgroup 的程序。有两个作用在刚分配、尚未关联 cgroup 的套接字上的钩子被有意列进当前任务那份名单。所以设计的划分是：套接字钩子按套接字的 cgroup，其余按任务的 cgroup，另有一小份显式例外清单。

2. **为什么这个比较永远不相等。** 挑 shim 的代码读出挂载函数 BTF 原型的第一个参数，拿它的类型 id 去对那张套接字类型 id 数组。数组是按结构声明建起来的，因此里面的条目是 `struct socket` 和 `struct sock` 的 id。而参数的类型 id 是指针类型的 id，指针类型和它所指向的结构在 BTF 里是两个不同的类型。id 相等意味着参数的类型*就是*那个结构，指针参数不可能满足。于是每个钩子的两个套接字判断都失败，落到兜底分支，两个套接字专用的运行函数在正常工作的内核里根本不可达。

3. **当前任务那条路做了什么。** 它取当前任务的默认 cgroup，运行那个 cgroup 的有效程序数组。于是被应用的策略是「恰好发起这次调用的人」的策略，不是套接字的策略。由此有两个后果。在一个 cgroup 里创建、被另一个 cgroup 使用的套接字，会被按使用者的策略检查而不是按自己的——借用监听套接字的进程、在自己继承来的套接字上发送的工作线程、在服务之间传递的共享套接字都属于这一类。而可能在软中断上下文运行的钩子根本没有有意义的任务：收包钩子、连接请求钩子、套接字安全 id 钩子，运行起来取决于中断恰好打在哪个任务上。内核分配套接字时甚至故意把中断上下文里创建的套接字关联到默认根 cgroup，理由正是别让被打断任务的 cgroup 漏进套接字的归属——这恰好说明当前任务这个选择对这类钩子有多要紧。

4. **修复到底改了什么，为什么还需要兜底。** 挑选代码现在先把第一个参数的指针类型解析成它指向的类型，再拿解析出的 id 去对那张表，套接字分支因此按文档所述被选中。让这个分支可达之后，一些「传了 socket 结构但内层 sock 还没有」的调用点就暴露出来。当前代码里有两个：接收侧的控制消息安全路径会以空套接字调用数据报对端安全钩子；轻量套接字创建路径在 `sock->sk` 被赋值之前就跑建后钩子，因为内层套接字要到协议创建内部才分配。修复因此加了一个空指针判断，这两种情况退回当前任务那条路而不去解引用。补丁说明带 `struct sock` 的那条路不需要同样的兜底：在套接字尚无 cgroup 关联时运行的那两个钩子本来就在当前任务名单上，其余第一个参数是内层套接字的钩子运行时套接字非空且关联早已设好。

5. **哪些钩子会搬家，对已部署的东西意味着什么。** 规则是机械的：受影响的是第一个参数为套接字或内层套接字的那些钩子。钩子原型表里这样的一共有三十个，其中两个留在当前任务名单上，于是会搬家的是二十八个。socket 侧包括创建之后、套接字对、绑定、连接、监听、接受、发送、接收、两个名字查询、选项读写、关闭，以及两个对端安全钩子；内层套接字侧包括收包、克隆、安全 id、连接请求、连接建立、netlink 发送、Unix 域的 connect 与 send、套接字嫁接，以及隧道和具体协议的那几个附加钩子，减去留在原地的分配与释放一对。这些钩子上的程序从「因为调用方任务在做什么而运行」变成「因为碰到哪个套接字而运行」。多数单 cgroup 负载里两者是同一个 cgroup，这正是这个缺陷能长期存活的原因：只有套接字跨越了 cgroup，或者钩子在软中断里触发时，选错才看得出来。

## 验证与排障路径

1. **刻意跨一次 cgroup 边界。** 在一个 cgroup 里创建套接字，把它交给第二个 cgroup 里的进程，让那个进程发起连接或发送。同一个钩子上在两个 cgroup 各挂一个计数程序。受影响的内核上，两个计数只在调用方那个 cgroup 下增长；修复之后，套接字自己的 cgroup 也会运行程序。

2. **把调用方和套接字对照。** cgroup LSM 程序可以用标准辅助函数读出当前任务的 cgroup id。从套接字钩子里把它打日志，再和你以为拥有这个套接字的 cgroup 对照。程序触发却报出不相干的 cgroup id，就说明它走的是当前任务那条路。

3. **单独测一个软中断钩子。** 挂到收包钩子或安全 id 钩子，在负载下重复同样的流量。运行次数跟随被打断的任务而不是跟随这条连接，即使没有跨 cgroup 的套接字也能定位这个缺陷；带上修复的内核上这种噪声会消失。

4. **确认受影响的版本范围。** 挑 shim 的那个函数从 6.0 标签起的已发布内核里存在，5.19 标签里没有；修复带着当初引入按 cgroup 使用 LSM 的那条提交作为被修对象。所以在这个范围内的内核，套接字钩子都选当前任务那条路。在下判断前先把你的内核和修复对照一次。

5. **别信挂载列表。** 挂载会成功，程序也会出现在那个 cgroup 的程序列表里，两种情况下都一样；列表不会告诉你将来运行的是哪一份数组。上面那个计数实验是最便宜也最确定的检查。

## 局限

- 修复是修复树里的送审改动，请求了稳定版回合，还不是已发布内核。落地之前，对套接字钩子唯一正确的假设是「按调用方的 cgroup」。
- 这只涉及统一层级上按 cgroup 使用 LSM 的那套机制，当前任务那条路读的正是它。
- 规则只看*第一个*参数。把套接字放在后面参数的钩子，修复前后都仍在任务的 cgroup 里运行。
- 行为变化是有意的但不是无声的：已有程序会搬到另一份 cgroup 数组。补丁本身就提出了一个悬而未决的问题——它是该进稳定版回合，还是该等下一个合并窗口，因为可能有人正依赖当前行为。
- 报告没有附带新的自测，所以回归只能靠行为发现，测不出来。

## 当日社区讨论

本次运行审阅了允许清单里的六个社区。两个接入存档的聊天工作区里的三个频道，24 小时窗口均无消息，属于安静而非跳过；七天窗口里其中一个频道有六条消息，摘要见下。另外两个聊天工作区的十个频道未被覆盖：读取需要已登录的浏览器会话，而本环境没有，因此记录为不可访问，不是安静。一个邮件列表和一个实践者论坛通过公开页面完整读取。合计：六个来源里三个有内容地审阅、一个审阅后为空、两个未覆盖。

邮件列表承载了上面回答的问题，其余窗口可以归到一个主题：交出或复用一块内存之后，校验器所记的状态与内存的真实状态不再一致。最清楚的一例是关于动态指针取片段辅助函数的两补丁修复。数据不连续时，这些辅助函数把它拷进调用方给的缓冲并返回那个缓冲，而校验器把返回值当作普通内存，不当作它其实就是那个栈槽。于是后来通过片段做的一次存储，会覆写校验器仍认为在槽里的东西——一个已知标量、一个压栈指针、一个动态指针、一个迭代器；反过来的一次加载则把这些字节当标量读回来。报告说这样的程序今天能加载，并可能让内核崩溃。修复把缓冲所在帧、偏移和大小记在片段上，并在每一次破坏「缓冲里没有受跟踪数据」这条不变式的事件上让片段失效：对这串字节的存储、在那里新建受跟踪数据、或者缓冲所在帧返回。由辅助函数填满缓冲被明确允许，因为它们留下的只是未受跟踪的字节。程序看到的拒绝是一条把内存访问抱怨成标量类型的消息，验证日志里也多了片段所指缓冲的渲染形式。这条线索的第二版把规则扩展到只读变体的只读片段——那正是评审者最可能假定安全的情形。同一窗口还有把包指针有效字节数保留在循环界分析里的第二版改动，以及修栈参数分析两处漏洞的四补丁第二版，都属于「校验器对某个位置的模型与机器的模型漂移」这一族。

窗口里另外两条修复讲的是生命周期而不是跟踪。一个两补丁改动把延迟释放 BPF 程序从公共系统工作队列上搬走，报告是这类容易误诊的很好的样本：释放一个分配组里最后一个程序会拿一把锁，然后进入改页权限的代码，那里可能往同一个 CPU 排一项工作并等它完成。别的释放工作线程都堵在同一把锁上，把队列的活跃槽占满，于是持锁的那个 worker 排的那项工作永远轮不到运行。看得见的症状是一条指向延迟释放 worker 的挂起任务告警，而不是一句 BPF 错误，这就是它看起来像调度或内存问题的原因。还有一个两补丁集合在评审之后接着修内存区域映射：一条让带固定地址的映射请求干脆不再被搬动，因为那条拒绝地址 0 的检查里的向上取整自己就可能回绕成 0；另一条把对应的映射测试改成串行并补上子测试。

第三组是工具链与构建健壮性，对任何要在带内核类型信息的内核上交付的人都相关：一条报告说，在以内联行信息构建调试信息时，解析内核代码里类型引用的工具会段错误，后续讨论把它定位到一个字符串表为空的模块上的一次释放后使用；两个架构改动，要么在生成内核类型信息前剥掉构建机的编译器调试记录，要么在产不出它的架构上干脆关掉；一条文档改动调整类型生成工具的最低版本；还有一个五补丁修复，处理指令打补丁与常量遮蔽、nop 删除相互作用的三个缺陷。另有十三补丁的第三版把打补丁的原语换成一份延迟补丁清单，根子是同一个问题——补丁被打在一个还在移动的指令数组上。

较小的条目都还在开放或早期评审阶段：socket map 判决、重定向、cork 与接收修复的十五补丁第二版，以及一份请求评审意见的提案，把在迭代器上下文里做的 socket map 更新限制给 socket map 迭代器；一行拒绝从跟踪程序调用调度器销毁辅助函数的改动；一个把新内存区域和 trampoline 配对的架构修复；一份性能报告，把一个系统调用密集型压力基准的大幅回退归因到一条无关的缺陷缓解改动；还有一条流程讨论，主张开发树里的 fixes 标签需要更认真——这正是本页面反复遇到的同一个问题的维护版本：一条记错对象的修复，就是一条谁也找不到的修复。

实践者论坛在 24 小时窗口里有一个新帖：一个学生在规划硕士论文，题目是用内核程序做一个 rootkit，再拿现有检测工具去评它，问学习路径、诚实的上手时间估计，以及会踩的坑。到的回答是标准且有用的那几个——入门书连同它的文档、给每种程序类型各做一个小项目，让底层概念在用到时自然出现，而不是先上一遍内核课；再看一件做安全强制的项目，而不是网络方向的例子。没人回答的那一半恰好是真实的工作量估计，也正是定题最需要的东西，而陌生人之间谁也答不了。往前几天仍开着的两条线索从另一面讲同一个取舍。一条问应用层解析有多少该放进内核、而不是交给用户态代理。最有内容的回答举出[一篇把七层负载均衡做进内核的公开论文](https://arxiv.org/abs/2602.09473)和它给出的边界：那套设计靠新的套接字层重定向来做连接管理，而不是靠程序本身的接口；按那位回答者的读法，这正是今天内核里做七层有意义的事多半只是观测与异步动作，而不是改向或自己造响应的原因。这是一条可用的界线——解析到够做判断为止，凡是需要自己握住连接的都交出去。另一条线程报告：把发送批处理修好之后，零拷贝包路径只是和传统扫描器打平，并且留下两个至今没人回答的问题——有没有人拿支持零拷贝的网卡量一下差别，以及在单条发送环上除了批处理之外还有没有别的办法，又不用改成多队列。实际的读法是：拷贝模式下的天花板是环，不是程序；而那条线程反复收到的诚实提醒是，收益取决于硬件，也取决于有没有内核工程师随叫随到。
还有一条主题来自一个接入存档频道的七天窗口，只不过是同一个边界问题在插桩侧的版本：一层的遥测责任到哪里为止，另一层从哪里开始。那六条消息里，一条是非技术公告，两条是评审请求——一个本地模型服务器的新插桩，以及对约定仓库尚未定稿的按次成本属性的采纳，后者正是这类采纳屡屡卡住的原因——还有一组三条的来回。那组来回讲的是某个厂商 SDK：它的 agent 框架会自己导出 trace，提案在插桩侧加一个环境变量开关，把那份原生导出关掉，好让插桩路径成为唯一来源；反对意见是，厂商专属的导出开关该待在厂商 SDK 里，而不该待在一个号称对所有 provider 一致的那一层。提案者的回答是，插桩本来就带手动路径，开关只是在两者之间做选择。没人把这条定下来，悬着的是那个普遍问题：SDK 自己发 span 的时候，插桩包装是去配置它，还是去适配它。
