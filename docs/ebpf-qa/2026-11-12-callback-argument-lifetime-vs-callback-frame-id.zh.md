# 交给 BPF 回调的指针为什么能在回调返回之后继续存在，而回调帧 id 又如何把它作废？

因为校验器记下了参数指向什么，却没有记下它能活多久。两个会调用回调的辅助函数会把自己栈上
局部变量的地址交给回调：用户态环形缓冲 drain 辅助函数交给回调的是它在取样循环里声明的描述符
地址，并在回调一返回就把样本释放掉；数组 map 遍历辅助函数交给回调的是它自己的循环计数器地址。
回调可以把该指针复制进调用者的帧，而回调返回时，校验器只清理属于回调帧自身的状态。被复制出来
的那一份保留着自己的类型和标识符，从栈上重新加载后仍然是同一个指针类型，并且在它所指的存储被
复用之后依然可以解引用。已经提交的补丁集把修复放在生命周期而不是访问点上：给回调帧一个 id，
让这个 id 同时成为该参数的 id 和父 id，并在帧弹出时把该 id 以及由它派生的一切作废。

## 机制

1. **参数是指向辅助函数栈的指针。** 用户态环形缓冲 drain 辅助函数在按样本的循环内部声明
   `struct bpf_dynptr_kern dynptr;`，用它初始化指向 peek 出的样本，用它的地址调用回调，之后才把
   样本还给生产者。数组 map 遍历辅助函数在整个循环之外声明 `u32 i, key;`，把下标写进 key，再用
   key 的地址调用回调。两种情况下，回调的第一或第二个参数都是某个内核栈帧里的地址，而该栈帧会
   被下一次调用复用。

2. **校验器记下类型，对 dynptr 还记下一个 id，但没有记录归属。** 用户态环形缓冲的回调参数设置
   用本地 dynptr 类型标记第一个参数，走的是一个从校验器 id 计数器里取新值、并把父 id 设为 0 的
   辅助函数。map 回调参数设置给第二个参数赋上 map key 指针类型、清零的已知标量偏移、map 指针和
   map uid，但完全没有赋 id；第三个槽位里的 value 寄存器倒是拿到了新 id，因为那个 id 追踪的是
   map value 的读取，而不是生命周期。所以 dynptr 参数带的 id 没有任何其他状态引用，而 key 参数
   根本没有任何 id。

3. **返回时清理的是回调帧，而不是调用者手里的副本。** 回调退出时，校验器先销毁回调帧自己栈槽里
   的 dynptr，再作废"记录的帧号是回调帧"的栈切片。两个过滤条件都是帧内的：切片检查会跳过任何
   记录帧号不同的寄存器，dynptr 检查只遍历被弹出帧的槽位区间。之后回调的寄存器文件被释放。落在
   调用者栈上的溢出副本、或者写进 map 的副本，都不在这两个集合里，因此带着类型和 id 存活下来。

4. **正是"允许溢出"把它变成了可触发的缺陷。** 2026 年年中之前，校验器判断一次溢出是否保留指针
   时，查的是一张允许溢出的指针类型表，其中并不包含常量 dynptr 指针。于是写进栈槽的 dynptr 指针
   落到把槽位标成杂项的支路，之后加载出来的是标量而不是指针，保存下来的描述符根本无法解引用。
   那次把允许表换成"凡不是标量、也不是未初始化"的提交，让溢出变成真正的指针溢出，跨存储和加载
   保留类型与 id。补丁集为那个提交单列了第二个 `Fixes` 标签，因为泄漏是在溢出变得可用之后才可用的。

5. **修复方式是回调状态自己持有的帧 id。** 该系列给回调的函数状态加一个字段，在第一次标记"帧
   作用域"参数时从校验器 id 计数器取值，并把参数的 id 和父 id 都设为这个值。它只标记指向辅助
   函数帧的参数：drain 辅助函数的 dynptr，以及数组与 per-CPU 数组 map 的 key。退出时，在原有的
   栈处理之后，它调用校验器在释放引用时早已使用的那个作废例程。该例程遍历当前状态里的每个寄存
   器和溢出槽，按标识符或父标识符匹配，把匹配到的寄存器自身的 id 压栈以便继续访问后代，把两槽
   一组的溢出 dynptr 成对作废，其余标记为未初始化。

6. **为什么参数是自己的父。** 作废图是按父标识符串起来的：`bpf_dynptr_data` 返回的切片把 dynptr
   的标识符记为自己的父，而按常规调用约定，这个辅助函数调用会覆盖参数寄存器。如果帧有独立于
   dynptr 的标识符，切片的父链就止于 dynptr id，而帧退出时没有任何东西作废它，被保存下来的切片
   依然可用。让参数自身的 id 等于帧 id 就闭合了这条链：参数是自己的父，任何由它派生的切片或克隆
   都继承自这一帧。

7. **状态比较必须用同一个身份，否则修复会被合并抵消。** 两个校验器状态是否等价，靠比较寄存器、
   溢出槽、栈参数和循环栈来判定，其中标量与引用标识符要通过一个双射做映射，从而保持"同一个值"
   的结构性。帧 id 就是比较里多出来的一个标识符：两个状态若来自不同的回调调用却到达同一条指令，
   帧 id 不同就不能合并，补丁集把这个映射加进帧比较。没有它，合并后的状态可能把一个值归到错误的
   回调帧上。

8. **哪些刻意没有纳入作用域。** 数组 key 是回调本地的，因为它是辅助函数帧上的一个 `u32`。哈希
   map 的 key 不是：遍历辅助函数交出的是指向已存元素的指针，而它活在 map 里；所有 map value 指针
   也都是 map 存储。补丁集两者都不纳入，并明确说明了这一点，这也是值得记住的边界：被修的性质是
   "存储位于辅助函数的栈上"，而不是"辅助函数调用了回调"。

## 如何验证

1. **读两处产生点。** 生命周期结论就是"局部变量声明 + 调用顺序"，所以直接读而不是相信二手总结：
   在环形缓冲辅助函数里，描述符声明位于取样循环内部，释放调用紧跟在回调调用之后；在 map 遍历
   辅助函数里，计数器和 key 声明在循环之外，回调收到的是 key 的地址。

2. **确认校验器没有记录归属。** dynptr 回调参数设置调用的标记辅助函数，其 id 参数是校验器 id
   计数器的前置自增、父参数是 0；map 回调参数设置赋了 key 的指针类型、map 指针和 map uid，但没
   有赋 id。检索这两个参数设置函数，以及那个带 id 与父 id 两个参数的标记辅助函数的定义。

3. **确认返回时只清理回调帧。** 读回调退出路径：dynptr 扫描以被调方分配的栈为界，切片作废接收
   被调方的帧号，并跳过记录帧号不同的寄存器。之后没有任何步骤再遍历调用者的帧。

4. **编译"保存描述符"的程序，让校验器裁决。** 回调把 dynptr 参数存进传给它的上下文，调用者在
   之后通过这个存下来的指针调用 `bpf_dynptr_read`，这就是完整的复现程序。在未修复的内核上它可
   以加载；打上补丁集后，它会以新 selftest 断言的报文失败。对保存下来的描述符，校验器会报告该
   参数期望的类型是帧指针或 dynptr 指针，而它看到的却是标量；对保存下来的切片，以及保存下来的
   数组或 per-CPU 数组 key，报文是 `invalid mem access 'scalar'`。哈希 key 与 map value 的用例
   仍然成功。

   ```console
   $ clang -O2 -g -target bpf -D__TARGET_ARCH_x86 \
       -I/usr/include/x86_64-linux-gnu -c park.c -o park.o
   $ bpftool prog load park.o /sys/fs/bpf/park type raw_tracepoint
   ```

5. **直接问正在运行的内核带不带这个字段。** 修复给校验器的函数状态加了一个字段，所以内核自身的
   BTF 就能回答版本问题，不需要编译：

   ```console
   $ bpftool btf dump file /sys/kernel/btf/vmlinux format c \
       | grep -A6 "struct bpf_func_state {"
   ```

   只打印出诊断用的帧标识符、没有第二个字段的内核，就在该系列之前，无论它的版本号里周边校验器
   代码是什么形态。

## 局限

- 该系列尚未合并。第一版得到了维护者"这些修复看起来没问题"的评价，随后被要求重做：补丁集已经
  不再适用，作者的两个系列被要求针对 bpf-next 合并成一个。请把这里的形态读作预期方向而不是已
  发布行为，引用行号前要重新核对补丁。

- 修复是按辅助函数逐个启用的。每个回调参数设置函数都要自己标记帧作用域参数，所以一个把栈地址
  交给回调的新辅助函数会继承同样的缺陷，直到它也被标记。机制本身不会通用地发现这个模式。

- 这两个辅助函数保护的是指针，而不是值。把 key 指向的八个字节复制走的回调不受影响；想在辅助
  函数返回后继续使用描述符的程序，必须在回调内部用完，或者把字节复制出去。

- 数组 key 只是四字节泄漏，因为 key 的加载是只读的：校验器直接拒绝通过 map key 指针类型的写
  入。更危险的一半是 dynptr 描述符，因为它描述的内存在回调返回时就还给了生产者，该系列把后果
  描述为任意内核读写。

- 新增的标识符参与状态比较，因此帧 id 不同的回调状态不再合并。这正是目的，同时也意味着本来会
  合并的状态现在可能被探索两次；读者唯一能察觉的代价，是本已接近状态或复杂度上限的程序加载变慢。

- 与一个待落地的校验器改写（把状态相等判定换成独立文件里的合并例程）之间的关系尚未确定：作者
  已把一版让合并比较认识帧 id 的补丁片段发给维护者，落在哪里要等重做结果。基于 bpf-next 树的
  读者需要那个片段，基于发行版的读者两者都没有。

- 用来核对本页的环境能编译复现程序却无法加载：进程没有 `CAP_BPF`，也无法提高锁定内存上限，内核
  连一个最简单的程序对象都拒绝，所以本页的校验器判定来自该系列自己的 selftest 断言，而不是实测。

### 回调参数的生命周期，以及校验器为什么看不见它

被回答的线程是本窗口里"校验器缺少词汇表"的最佳例子：一个类型已知、存储属于别人栈、有效区间
只有一次回调调用的值。对写回调代码的人最有用的，是该系列明确列出哪些情况**不受影响**的第二半：
哈希 key 指针指向已存元素，活过回调；map value 指针指向 map，也活过回调；复制字节而不是保留
指针的回调同样不受影响。这给出一条具体判断规则：回调收到的指针，当且仅当辅助函数为了调用你而
构造了那个对象时，才是回调本地的。线程的另一半是与待落地校验器改写的交互——状态相等判定变成
独立的合并例程，帧身份必须教给它；两个系列现在要合并重做，提醒我们：一个生命周期性质的可信度
取决于每一个会合并状态的地方。

### 标量演化进了树，代价是以指令数写明的

本窗口有一个十二补丁的校验器系列被应用到 bpf-next。它针对的不是正确性缺陷，而是用户能感受到
的成本：栈活跃性丢掉传给辅助函数的指针的偏移量，整个帧保持活跃，而没有任何指令再加载的溢出
指针会把状态分开。说明信给出了两个生产程序上的测量值（一条 Falco 接收路径和一个 Tracee 安全
钩子），约为七倍和两倍的指令数下降，其中还有一个补丁专门阻止"只被按字节读取"的溢出指针被保留。
值得记下的是这个数字而不是机制：这是一次以指令数为回报的校验器表示变更，所以它出问题时的症状
是加载变慢或撞上复杂度上限，而不是运行时给出错误答案。

### 可抢占程序的按任务递归检查，以及先于它存在的丢事件类别

一个五补丁的修订版论证：追踪程序的递归检查是 per-CPU 的，而程序本身可被抢占，于是某任务在
程序内被抢占后，同一 CPU 上的下一个任务看起来就像递归调用，它的事件被丢弃并记为 miss。对成对
的入口/出口程序来说风险很具体：丢掉一半就会让有状态的解析失同步。该系列给出了在标准内核、HTTP
负载下测得的丢事件率，并把"从自愿抢占变成惰性与完全抢占"这一变化指为它开始产生影响的原因。
值得记住的诊断是 miss 计数上升而程序自身没有嵌套，边界是该检查在第一条指令之前执行，任何程序
都无法绕过。本窗口另一个补丁把同一类计数改成 CPU-aware，用于 per-CPU 辅助函数和 map 回调——
此前一位维护者指出三条回调路径都已经校验 CPU，新增检查里有一条是死代码。

### 迭代器、耗尽状态，以及保住 ABI 的哨兵值

一个针对数据缓冲迭代器的单补丁修复，把"已耗尽"状态做成独立的哨兵值而不是空指针，因为底层链表
遍历在表尾也返回空指针，而校验器的迭代器约定要求 next 方法一旦返回空就必须一直返回空。一位
维护者建议采用邻近迭代器已有的更简单写法，随后一条消息补上了 selftest。状态结构为什么不能直接
变大，这一点值得记住：迭代器状态结构属于生成的内核头文件，它的大小就是 ABI，哨兵值是把它保持为
一个指针宽度的最便宜办法。

### 影响面很大的小修复

本窗口还有几个普通的 bug 修复，其边界值得注意。向已满的消息环 push 时读到了空闲槽的长度，而它
是 0，于是一个字节都没复制、环看起来是空的；该补丁已应用到 bpf 树，它同时需要 BPF 与网络管理
能力，这也是复现程序要用文件能力运行的原因。某个 map 释放路径只在配置的最大条目数范围内断言
条目为空，在较大的 map 上运行得足够久，以至于在延迟工作项里触发了 soft lockup 看门狗；修复加了
一个调度点。cgroup link 更新在内核内存不足的 detach 留下占位条目之后，可能把替换程序写进错误的
有效程序槽位，这是生命周期问题：该数组不持有引用，旧程序可能在仍被发布时就被释放。还有一条
sockmap 接收路径在持有套接字锁时睡眠，可能与投递 worker 死锁并让该 worker 上所有接收流量停摆；
修订版在等待期间释放锁，并把非等待状态、零长读取和带外读取重新走回不睡眠的辅助函数。
