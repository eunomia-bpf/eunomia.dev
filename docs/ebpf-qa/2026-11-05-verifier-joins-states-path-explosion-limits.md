# Why do large eBPF programs hit the verifier's instruction and jump-sequence limits when the instruction count fits, and what changes if the verifier joins states instead of following paths?

Because the cost of verification is not the number of instructions in the program but the number of paths through it. The verifier today walks paths: at each branch it forks the abstract state and explores both sides independently, and it only stops a path when it arrives at an instruction whose saved state is at least as general. A loop whose exit condition is a counter, or a function called from several places, therefore multiplies the work by the number of distinct ways of reaching the same instruction. A proposed series removes the walk entirely: where two paths meet, it builds one state that covers both — `r1=1` and `r1=5` become `r1=[1,5]` — and repeats until no state changes. The two user-visible limits that cause most of the failures, 1,000,000 processed instructions and a jump sequence of 8,192, are replaced by limits on the number of states. The tricky part is not the join itself but the states that must *not* be joined, because a later check would otherwise lose information it needs.

## The mechanism

1. **What the current limits actually count.** `BPF_COMPLEXITY_LIMIT_INSNS` is 1,000,000 and is checked against `env->insn_processed`, a counter incremented once per instruction *executed by the verifier*, not per instruction in the program. `BPF_COMPLEXITY_LIMIT_JMP_SEQ` is 8,192 and is checked against `env->stack_size`, the number of pending branch states the verifier has pushed but not yet resumed. Both are therefore measures of exploration, and both are independent of the program's static size. A 3,000-instruction program can cross either one; a 500,000-instruction straight-line program crosses neither.

2. **Why a program with few instructions explodes.** The verifier keeps a state per (instruction, call chain) and pushes the not-taken branch whenever it forks. If a helper or a static subprogram is called from several sites, or if a loop is bounded by a value the verifier can only represent as a range, the same instruction is verified once per path that reaches it. Paths are pruned only when an identical or more general state is already recorded at that instruction, which for a loop requires the state to converge; a loop whose induction variable the verifier widens instead of solving keeps producing new states until an iteration cap rejects it. That is the shape behind the reported failures: 1,000,001 processed instructions on a scheduler callback, and the "sequence of 8193 jumps" error on a vector push/pop helper.

3. **What a join is.** Instead of two states at a merge point, keep one whose each register holds the union of the two ranges: `r1` becomes `[1,5]`, and any fact true of the union is true of both inputs, so verifying the union is sound for both. Because the union is weaker than either input, a check downstream may fail that would have passed on one branch alone; the fix is to keep the two states apart when a later check can distinguish them. That is a correctness requirement, not an optimisation: joining too eagerly rejects valid programs.

4. **Which states must stay apart.** A later conditional jump comparing the register with a constant, or a check of its range at a call or at exit, makes it *tested*. If two tested ranges leave a gap — `-155` and `0`, but not `0` and `1` — joining them would fabricate values that no path produces. The same applies to two tested registers with no common value, to a register that only one side initialises (the join would claim it is readable when one path leaves it unset), and to a constant that becomes a stack offset. Some checks need an actual constant rather than a range — the size argument of `bpf_ringbuf_reserve()` is the standard example — so the registers and stack slots feeding such checks are found once, ahead of the main pass, and states differing in them are not joined.

5. **How loops are handled.** A loop that the verifier can count with scalar evolution gets a single state covering all iterations. A loop it can walk to its end gets a state per iteration while a constant decides the exit. Every other loop is joined at the head, widened, and given a `may_goto` edge. `may_goto` is an instruction the verifier already knows: the JIT turns it into a bounded backward jump whose budget is a per-invocation time slice. In the current tree the runtime check compares against a quarter of a second (`NSEC_PER_SEC / 4`) and the budget counter is `BPF_MAX_TIMED_LOOPS`, so the machine is present; the series makes the verifier *insert* these edges rather than requiring the author to write them.

6. **What this replaces in the diagnostics.** The removal of path walking removes the machinery that only existed to make walking cheaper: precision tracking, jump history, and the strongly-connected-component bookkeeping. `mark_chain_precision()`, the `mark_precise:` log lines, the `N: safe` and `depth=` output, and the SCC column all disappear, which is why the log format changes at level 2 — merges are reported as `joined`, `widened`, or `within` instead of as a pruned path. The statistics line keeps its format, so tooling that parses `processed N insns (limit ...)` still works; `BPF_F_TEST_STATE_FREQ` remains accepted and becomes a no-op.

7. **Why static subprograms and recursion follow from the same change.** A static subprogram is currently verified inside the frames of each caller, so two callers with different frames have no join and the subprogram is re-verified per call chain. Verifying it once for the set of states at its first instruction removes that multiplication, and the same machinery allows recursion: a recursive subprogram is verified for its entry states with widening, and depth is bounded by a runtime check on the stack pointer rather than by a static frame count. That is why the proposal can allow recursion where the current verifier rejects it.

## How to verify and debug

1. **Read the counters, not the instruction count.** The verifier's statistics line prints `processed %d insns (limit %d) max_states_per_insn %d total_states %d peak_states %d mark_read %d`. A rejection at the limit with `max_states_per_insn` in the tens and `processed` at a million means exploration, not size. `insn_cnt` from the program header is the number to compare against; if it is far below 1,000,000, the program is a path-explosion case and shrinking the instruction count is the wrong remedy.

2. **Distinguish the three limits by their message.** "BPF program is too large. Processed N insn" is the instruction budget; "The sequence of N jumps is too complex" is the pending-branch stack; "infinite loop detected at insn N" is a loop whose state stopped changing in a way the verifier cannot prove terminating. They have different causes even when they appear on the same program, and raising one reveals the next.

3. **Find the instruction where the cost concentrates.** Level-2 logs show the flow of verified states; a single instruction with a large state count is the merge point that is being re-verified per path, and the subprogram or loop reaching it is the thing to restructure. Because `max_states_per_insn` is a maximum rather than a sum, it identifies the location but not the total cost; the `processed` counter is the total.

4. **Restructure before shrinking.** Moving a shared computation out of the branches, making a helpered path straight-line, or replacing an unpredictable loop bound with a counted one reduces paths without changing behaviour. Cutting instructions until the program fits changes what the program does, which is why the reported case was a corpus of generated Rust code that could not simply be trimmed.

5. **Test the join semantics with a small program.** The decisive experiment for the proposed behaviour is a merge where the two branches assign different constants that a later check distinguishes, and its complement where no check distinguishes them. The first must stay unjoined and verify, the second joins and still verifies. A verifier that joins both looks correct on the second case and is wrong on the first.

## The limitation

- The series is a proposal under review, not released behaviour. Until it is merged, the limits a program meets are the ones in its running kernel's `kernel/bpf/verifier.c`, and the counts above are from the current tree.
- A join is sound but not complete in the direction authors care about: it can reject a program that path-by-path verification accepted, because the union of two states is weaker than either. The listed examples — a range losing the relation between two scalars, `r0` being `2` or `3` collapsing to `[1,2]` and forcing egress-only attachment — are real verdict changes, not bugs to be fixed by widening later.
- The comparison numbers come from the author's corpus and harness, with the usual caveats: sums over different program sets, a best-of-three timing, and a state definition that counts arrivals at a basic block rather than saved states. Read them as an order of magnitude, not a benchmark.
- The runtime side of `may_goto` remains bounded by a time slice, so a program whose loop is now accepted can still be cut short at run time; the difference is that it returns instead of failing to load. Programs that relied on the load-time rejection of a non-terminating loop lose that early diagnostic.
- Recursion being allowed on x86-64 and arm64 is explicitly an exception list, so a program that recurses is portable across those two and not necessarily beyond them.

This run reviewed six allowlisted communities. Two are Slack workspaces reachable through the approved private read-only archive, covering three allowlisted channels; in this window one carried no message in 24 hours and the other carried none in 24 hours and three in the seven-day window. The two chat workspaces with no archive were not covered, because this environment has no authenticated session for them and their visible pages land on a login page; they are recorded as inaccessible, not quiet. The kernel mailing list and the practitioner forum were read through their public pages.

The mailing list carried the question above and four other threads, which form three themes. The first is a bound that is checked against the wrong predicate. Two helpers that take a CPU id as an unconstrained `u32` validated it only against `nr_cpu_ids`, while per-CPU memory exists only for *possible* CPUs; on a machine with a hole in the possible mask, an id in the hole passes the check and `per_cpu_ptr()` is computed from an uninitialised offset for that CPU. The reported consequence is a fault inside `memcpy` when a map value read through the returned pointer is passed to an update, and the same path can be writable for per-CPU objects. Two details make it more than a missing check: the verifier rewrites a lookup on a known map into a direct call to the map callback, so a check in the helper wrapper alone does not cover JITed programs; and the verifier drops `PTR_MAYBE_NULL` from the return of the per-CPU allocation helper, so a program that skips the NULL test passes verification and faults later. The review response on the thread was to shorten an over-long commit message rather than to dispute the analysis.

The second theme is a helper that loses information silently rather than failing. A stack-capture helper has a faulting and a non-faulting implementation: the non-faulting one cannot fault in a page, so a return address whose backing file is not resident degrades to a bare instruction pointer instead of resolving a build id. Only probe programs are routed to the faulting variant today, so the other program types that can sleep keep losing build ids for non-resident pages, with no error to indicate it. The proposed fix routes those types to the sleepable variant and marks the prototypes as possibly sleeping, which also makes the verifier reject the call from an atomic context — so programs that load today can start failing, which the author calls out as intended consistency rather than collateral damage.

The third theme is a lifetime assumption inside a kfunc. A path-resolution kfunc can run for a file being released at task exit, after the task's filesystem context has been cleared, and the underlying resolver then dereferences the null pointer; the fix is an early error return and a selftest that crashes without it. A fourth thread extends the same class in the owner direction: BPF programs were being freed from a shared workqueue, and the series gives them a dedicated one so that a slow free cannot delay unrelated work.

The archive-backed observability channels were quiet in the 24-hour window; their seven-day content is a three-message thread about who should own a switch that suppresses a vendor SDK's own trace export in favour of the instrumentation path. The technical content is a configuration-scope argument rather than an eBPF one — the objection is that the decision belongs to the SDK, and the answer is that the instrumentation already repairs the manual path, so the switch only removes a duplicate — and it is open, with the pull request waiting on its author rather than on a maintainer objection.

The question answered here came from the public mailing list within this window, and its claims were checked against the current kernel sources and the patch series' own text rather than against the thread alone.
