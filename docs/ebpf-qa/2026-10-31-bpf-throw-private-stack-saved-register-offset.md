# Why does a BPF program with a private stack crash the kernel after it throws an exception, and why does the fix adjust the saved-register pointer by eight bytes instead of changing the generated code?

Because on x86-64 a JITed program that uses a private stack has no frame-pointer register, so the JIT keeps the private frame address in a reserved register and pushes that register around every call. When such a program throws, the throw helper records the stack pointer of the main program's frame and the exception callback pops its saved callee registers starting at that address, which is where the pushed frame address sits, not where the first saved register sits. Every register therefore receives its neighbour's value, and the innermost one receives the address of the private stack. The kernel crashes when it returns and uses those registers. The fix adds the eight bytes of that pushed register to the stack-pointer adjustment the exception path already carries. The instruction stream the JIT emits is unchanged.

## The mechanism

1. **Which programs get a private stack.** `bpf_enable_priv_stack()` in the verifier grants one only if the JIT supports it and the program type is kprobe, tracepoint, perf event, or raw tracepoint — the program type for classic uprobes is the kprobe type — or if the program is a tracing, LSM, or struct ops program that either asked for one or needs recursion checking. A subprogram is then given the private stack only when its rounded stack depth reaches the 64-byte minimum, no program in the object uses a tail call, and, on x86-64, it passes no arguments on the stack. That last rule exists because the same register is argument six in the native calling convention.

2. **What the private stack does to the frame.** A normal JITed program starts with `push rbp` and `mov rbp, rsp` and addresses its program stack below that frame pointer. A program with a private stack instead keeps the frame address of its per-CPU stack area in the reserved register, leaves the native frame pointer and stack pointer alone, and emits a push of that register before and a pop after every helper, kfunc, direct, and indirect call, because a call may overwrite it. The prologue also sets the program's own stack-depth field to zero, since the program stack no longer lives in the kernel frame.

3. **What a throw hands to the callback.** The main program of an object that can throw saves its callee registers unconditionally at entry: rbx, r13, r14 and r15, plus one register that is mapped to no BPF register because a throw can happen after the kernel has clobbered it. `bpf_throw()` walks the stack to the frame whose program is the marked exception boundary, records that frame's stack pointer, and calls the exception callback with that pointer plus a stored adjustment. The callback prologue sets its stack and frame pointers from those arguments, pops the saved registers, and then resets the frame. So the whole handoff depends on one integer: the distance between the recorded stack pointer and the saved register area.

4. **The off-by-eight.** Without a private stack, the innermost slot of the main frame at the recorded stack pointer is the last saved register, and the pops are aligned. With a private stack, the innermost call left its pushed frame address at exactly that slot, one entry below the saved registers. The callback then pops the frame address into the first register and shifts every other register by one, so one register ends up holding the address of the per-CPU stack. `stack_arg_sp_adjust` already moves the pointer from outgoing stack arguments up to the saved registers; the fix adds eight bytes to it whenever the main program was JITed with a private stack. A constant is sufficient: every kind of call emits the push, a program with a tail call has no private stack, a callback cannot throw, and only the main frame is recovered, since subprogram frames are dropped either way.

## How to verify and debug

1. **Read the crash location.** The fault is not inside the BPF program. It appears just after the program returns, in the code that entered it, because that is where the corrupted callee-saved registers are consumed. A reported example is a null-pointer dereference in the program test-run path.

2. **Confirm the private stack is really in use.** Dump the JITed image with `bpftool prog dump jited` and look for the prologue that loads the private frame address and the push and pop pairs around calls. Two cheap controls remove them: one tail call into an empty program array, or a frame small enough to fall below the 64-byte rounded minimum. If the crash disappears with either control, the private stack is the variable.

3. **Match the trigger conditions.** Tracepoint, raw tracepoint, perf event, fentry and fexit, and struct ops programs that request it are affected once the main program's stack passes roughly 48 bytes of raw depth, which is what rounds up to the 64-byte threshold. The throw may be in the main program or in a subprogram. Iterators are excluded from private-stack selection.

4. **Understand why the combination survived testing.** The selftests that pair a private stack with an exception are fentry programs. The test loader does not attach them, and running a tracing program through the test-run syscall reports that it is unsupported without calling the program, so the objects were loaded and never executed. The fix adds raw tracepoint variants, which the test-run path does execute; without the fix they crash the kernel, and the variant where only a subprogram has a private stack passes before and after, which is what makes it a regression guard.

## The limitation

- The defect and this fix are specific to the x86-64 JIT. The arm64 JIT had a separate bug in the same handoff, where the callback never received a frame pointer and kept whatever value the throw left in that register; that one is already fixed upstream and tracked as a security fix, and its mechanism is a missing frame-pointer setup rather than an eight-byte offset.
- As of this run the x86-64 change is a posted fix against the current development tree, not yet released. A kernel with private-stack JIT support and a program that throws can still hit it.
- The adjustment is derived from what the JIT emitted, not from the source. A future change that stops pushing the frame register around calls, or that moves the saved registers, must revisit the same constant.

The ten channels in the two chat workspaces were not covered, because reading them needs an authenticated browser session and none was available in this environment; they are recorded as not covered, not quiet.

The mailing list carried three substantial threads. The first is the private-stack question answered above, and it is only one corner of a wider unresolved problem: a series that disables the private stack for sleepable programs is still in review, and a production report posted in this window measured the same frame corruption on non-sleepable probes. Its numbers are the useful part. Corruption appears only where a run path can be preempted: several released kernels and the current development tree showed roughly one corrupted frame per few hundred to per thousand instrumented calls under full and lazy preemption, while voluntary-preemption builds and a kernel whose JIT has no private-stack support showed none, and the controls — a single tail call, or a small frame — showed none everywhere. The report also identifies why the probes are exposed: the uprobe run paths disable migration and take a read-side lock that does not stop preemption on preemptible-RCU builds, and the comment above one of those paths has always claimed it disables preemption for the program even though the code never did. Three fixes are on the table and each has a cost the reviewer flagged: narrowing eligibility, which cannot tell a classic uprobe from a kprobe at load time without a new marker; an attach-time rejection for unmarked programs, which measures as a bare invalid-argument failure for every program built by an older loader or by a loader outside libbpf; and a runtime preemption guard around the run, which the maintainer rejected outright, pointing out that the same approach had already been rejected earlier in the thread. That last exchange, including the reply accepting the correction, is the current end of the thread, so the boundary is still open: a per-CPU stack plus a preemptible run path needs either a barrier or no per-CPU stack, and the question is which users the fix is allowed to break.

The second thread is a reworked series that changes how the bounded-loop instruction enforces its 250-millisecond limit. The count and the deadline live in the stack frame of the function containing the loop, so the limit applies to one call of a subprogram rather than one invocation of a program: loops that nest across calls multiply the budget, and the posting demonstrates nine instructions that hold a CPU. The series moves both values into per-CPU program memory set once at entry, so the limit becomes per invocation, a function called after the deadline makes no iteration at all, and `bpf_loop()` and the map-element iteration helper stop early when the time is up. The measured trade is small but explicit — a little more JITed code for the small share of scheduler-extension programs that use the instruction, noticeably less stack, a slightly cheaper call and a fraction of a nanosecond per empty iteration — and the honest caveat is that a second concurrent invocation of the same program on the same CPU shares the counters, which biases the limit long rather than cutting a run short. Anyone whose reasoning was "each frame gets its own slice" needs to update it.

The third is a build and memory series that keeps the kernel's own type information compressed until first use instead of parsing it at boot, saving about six megabytes on systems that never touch it at the cost of roughly fifteen milliseconds once for the first user. It is off by default and limited to two architectures for now, because on others the boot image carries an uncompressed copy anyway. It matters to this audience because everything from compile-time field relocation through fentry, kernel functions, struct ops, scheduler extensions, and LSM hooks depends on that type information, so the discussion is a distribution-config trade rather than a change in program behaviour. A separate report in the same window, a build tool crashing under a related debug-information option, was answered the same day with a concrete mechanism: a use-after-free triggered when copying strings from a base whose raw data the copy frees, with a proposed one-file fix and a byte-for-byte comparison of the tool's output as evidence.

Smaller items in the window, all still open or in early review: a data race between concurrent sockmap updates that change a socket's protocol and its attached programs; a verifier fix for how stack-argument analysis joins a frame-pointer offset of zero with a value that is not a pointer into the stack; a networking series that has to discard a validated checksum after a BPF program runs inside a segment-routing behavior; two XDP driver fixes, one freeing frames as socket buffers on interface teardown and one reporting the wrong receive queue to the program; a fourth revision of the multi-buffer transmit checksum fix for the zero-copy packet socket family; and continued review of a tooling series that moves per-record relocation attributes into generated C output. One dispute about whether two recently fixed bugs in the new indirect-jump feature deserve the same security and stable-backport treatment as three earlier fixes in that same feature was still running at the end of the window; the maintainer's objection was about searching the archive before asking, so the underlying question of where the unprivileged threat model ends is still not written down anywhere.
