# 开放编码 BPF 迭代器耗尽之后为什么必须一直返回 NULL，而 next 方法重新开始时又会发生什么？

因为校验器正是靠这个假设来验证迭代器循环的：在每一次 next 调用处，它分出一份状态把返回值当成 NULL 并把迭代器标为已耗尽，再分出另一份把它当成有效指针。在耗尽那条路径上，返回值是常量零，而且不会再分叉，因此程序其余部分是按"此后 next 只会返回 NULL"来验证的。一个把"已耗尽"和"尚未开始"当成同一种状态的 next 方法会重新开始，并交回一个校验器早已不再跟踪的真实指针。恰好有三个开放编码迭代器是这个形状，11 月 10 日发出的三个补丁分别修掉一个。

## 机制

1. **文档里的契约。** 迭代器文档把它写得很直白：next 方法"保证在元素耗尽时最终返回 NULL。一旦返回了 NULL，后续的 next 调用应当继续返回 NULL"。同一节还要求构造函数即使在失败时也要把状态初始化成"接下来的 next 会返回 NULL"，并要求状态结构体足够小能放在栈上且 ABI 稳定，因为它的大小和布局属于用户可见 API 的一部分。

2. **校验器为什么需要它。** 一个退出条件取决于内核数据的循环无法穷尽验证。所以在每次 next 调用处，校验器运行 `process_iter_next_call()`，把当前状态一分为二：一份带着"仍然活跃"的迭代器入队、迭代深度加一、返回寄存器标为非 NULL；当前这一份则切换为已耗尽，返回寄存器置为常量零。入队的那份被验证，如果它以等价状态回到同一个 next 调用，循环就被认定为收敛；而耗尽的那份负责证明出口可达。这两半论证都依赖"迭代器不会复活"。

3. **已耗尽的迭代器对其余验证意味着什么。** 对已处于耗尽状态的迭代器再调用 next 不会分叉，只是把返回寄存器再次标为常量零。于是所有检验该寄存器的条件跳转都由 `is_branch_taken()` 静态决定：它只走一边，把另一边作为推测执行路径压栈。

4. **没被走的那一边会怎样。** 只能从被剪掉的分支到达的指令，即便被验证也是在推测执行下进行的，而推测执行有意不把指令标为"已见过"。验证结束后的两个阶段据此动作，用哪个取决于加载时的特权：带特权的加载里，把死分支硬接线的那个阶段会把条件跳转改写成跳向校验器保留的那一边的无条件跳转，再由 `bpf_opt_remove_dead_code()` 删掉另一边；非特权加载里，`sanitize_dead_code()` 把每条没见过的指令换成跳向自身的跳转，也就是一个陷阱。两种情况下，加载后的程序编码的是校验器的信念，而不是对该寄存器的检验。

5. **于是运行时一旦重启就会分叉。** 内核的 next 返回一个有效指针，但加载后的代码不再检验它。带特权的形态里分支已被删除，执行无条件走耗尽那一边，元素被静默跳过——如果程序还要继续循环，它就在一条固定路径上循环。非特权形态里条件跳转还在，重启把执行送进校验器从未探索过的分支，那里的每条指令都是自跳转：程序卡在校验器的陷阱里，直到看门狗报告。

6. **两种形态在加载时就能区分。** 如果程序在耗尽那次调用之后再次调用 next 并循环回到它，就没有新状态可供分叉，于是 `is_state_visited()` 看到等价状态，加载以"infinite loop detected"失败。树内对应的自测就叫 `iter_remake_drained`，它预期的正是这条信息。也就是说，同一个实现缺陷要么表现为程序被拒，要么表现为程序被接受但行为错误。

7. **三个迭代器共有这个缺陷。** 一个 dma-buf 迭代器用"元素指针为 NULL"表示"迭代尚未开始"，而该链表的结尾同样是 NULL，于是耗尽之后的那次调用从头重新开始；修复用一个无效指针值作为耗尽哨兵，并在析构函数里跳过它，这样状态仍只有一个指针宽。一个 cgroup 迭代器在耗尽时清掉了位置却保留了起始指针，而每个 `css_next_*()` 辅助函数在位置为 NULL 时都会从起始处重新开始；修复在耗尽时清掉起始指针，而该析构函数本来就是空操作，所以没有别的东西依赖它。一个调度器 DSQ 迭代器在队列末尾把游标从链表里摘掉，下一次调用看到空游标便又从队头开始；修复把耗尽状态记在一个空闲的游标标志位上，BPF 可见的迭代器布局保持不变。三个互不相关的迭代器，同一个从未被写成实现要求的契约。

8. **已经正确的迭代器展示了应有的形状。** 数字迭代器在越过区间后把游标和终点都置零，此后一直返回 NULL。任务迭代器在位置为 NULL 时立刻返回 NULL。只有"用 NULL 表示尚未开始"这种编码会丢掉这个区别，而一个哨兵值、一次清空起始指针、或一个标志位就能把它补回来。

## 验证与排障路径

1. **在校验器日志里读迭代器状态。** level 2 的日志把每个迭代器栈槽打印成 `iter_<类型>(id=N,state=…,depth=N)`，并明确给出三种状态名：active、drained、invalid。用 `log_level` 为 2 加载程序，找到状态第一次变成 drained 的那一行；日志里此后每次 next 调用，都是校验器不再分叉的调用。

2. **看那个分支变成了什么。** `bpftool prog dump xlated` 给出验证之后的指令流。你自己写的、针对 next 返回值的条件跳转，在带特权的加载里会变成一条无条件跳转，另一边的指令已经消失；在非特权加载里，没走的那一边会变成跳向自身的指令。

3. **刻意复现。** 写一个程序，在 next 返回 NULL 之后再调用一次并用它的结果。如果这次多余调用在循环里，加载时得到"infinite loop detected"；如果是直线代码，程序会被接受，然后你运行它，会看到被保护的分支被跳过，或者非特权构建卡在陷阱里。

4. **用三个问题审自己的 next。** 构造函数留下的状态，第一次 next 会返回 NULL 吗？耗尽和"尚未开始"能区分吗？耗尽之后还有东西会重置位置吗？一个"在返回 NULL 后再调一次并断言仍是 NULL"的一行自测就能同时抓住这三种情况，而树内的注册表并不做这项检查。

## 局限

- 三个补丁都在 11 月 10 日发出，描述的是一类缺陷，而不是一条已合入的不变量。窗口内只有调度器那个被合入到一条修复分支；cgroup 那个带了一个 ack 和一个"由哪棵树接收"的开放问题；dma-buf 那个当时还没有回复。现网内核仍可能同时带着这三个缺陷。
- kfunc 注册时并不强制这条契约。校验器信任实现，文档把要求写成散文，所以新增的迭代器可以在没有任何加载期提示的情况下重新引入同样的重启。
- 修复受 ABI 约束。迭代器状态结构体的大小通过生成的类型信息对程序可见，所以 dma-buf 的修复花掉一个哨兵值而不加字段，调度器的修复用一个空闲标志位。
- 从程序内部看，重启是不可见的：寄存器里是真实指针，而加载后的代码不再检验它，程序也无法知道自己被哪一种验证后改写编译过。

## 当日社区讨论

本次运行检查了六个白名单社区。其中两个是通过已批准的私有只读归档访问的 Slack 工作区，覆盖三个白名单频道：一个频道在 24 小时窗口内没有消息，七天窗口内同样没有；另外两个频道 24 小时内没有消息，七天内共四条，而这四条都属于同一个讨论某个会议活动订桌子的主题——纯事务性，没有技术内容。两个 Discord 工作区（共十个白名单频道）未被覆盖：本环境没有已认证会话，两个公开邀请链接都返回"邀请无效"页面，因此按不可访问记录，而不是按安静记录。从业者论坛本次可以访问，但窗口内没有帖子，可见的三篇帖子都在两天或更早之前。内核邮件列表通过其公开归档阅读，上面的问题与下面的主题都来自它。

第一个主题就是上面回答的那个：三个迭代器的 next 方法在返回 NULL 之后又重新开始，在同一周被发现并分别修复。有三个细节让它不只是三个小补丁。这个缺陷对直线代码在加载时不可见，只在运行时致命，所以程序行为取决于它是以带 `CAP_BPF` 还是不带的方式加载的。修复受迭代器状态属于 ABI 的约束，这就是为什么一个花掉一个哨兵指针值、另一个花掉一个标志位，而不是加字段。而这条要求本身住在文档里、不在注册期检查里，这正是三个独立实现都能漏掉它的原因。

第二个主题是校验器在运行时对其余系统做了什么。一个校验器循环在调试内核上报告 rcu_tasks 停顿超过二十分钟（每次加载）：主循环调用 `cond_resched()`，而它在开启抢占的内核上是空操作，而非自愿抢占不是 tasks-RCU 的静止状态，所以加载任务在加载返回之前一直是 holdout，与此同时每个 `synchronize_rcu_tasks()` 调用方都在等——报告里举的例子是一次动态 ftrace 关闭。修复换成了 `cond_resched_tasks_rcu_qs()`，即使不需要真正让出也会上报静止状态；它同时去掉了多余的 `need_resched()` 判断。值得记住的诊断是：停顿报告里点名一个位于校验器内部的任务，并不是程序卡死，而报告里的栈显示的是当时正在进行的哪次校验器分配，而不是正在验证的那条指令。

第三个主题是注册成本。一个十三补丁的系列把已注册 kprobe 按代码地址索引进 rbtree，并为 static-call 与 jump-label 的保留检查增加按地址排序的索引，使指令恢复与优化不再逐个地址查找；在 20,000 个探针上量到的结果是周期数和耗时都降到大约十分之一。其中两个决定值得照抄：排序索引分配失败时代码保留线性扫描而不是让注册失败；模块的保留检查保持线性，因为成本不在模块那条路径上。它给出的动机是内联函数追踪，那会比今天注册多得多的探针。

第四个主题是一个把递归和抢占混为一谈的每 CPU 计数器。一个不可睡眠的 fentry 或 fexit 程序在执行第一条指令之前先取每个 CPU 的递归计数器。如果运行它的任务被抢占，计数器就一直处于占用状态，该 CPU 上进入同一个函数的下一个任务看到计数不是一，就增加 recursion-miss 统计并跳过程序。在发行版内核上，这一点在自愿抢占还是默认值时被掩盖了，因为不可睡眠程序里没有自愿抢占点；x86 和 arm64 上只剩 lazy 和 full 抢占之后，每个发行版内核都会表现出来。量到的跳过率是几十个百分点，对成对的入口/出口探针而言实际后果是其中一半被丢掉，从而让由它们构建的任何状态机失去同步。提案在调用周围关掉抢占，与 kprobe 和 perf tracepoint 对齐；评审者提出的"只放宽为同一任务"被否决，因为那样同一 CPU 上的第二个任务就会共享同一份每 CPU 私有栈，以及既有的每 CPU 暂存缓冲区用法。这个线程的开放点是程序自己绕不过去：计数器在第一条指令之前就被检查，而从 BPF 内部关抢占又跨不过尾调用。

第五个主题是错误注入可以挂在哪里。一个十八补丁的系列用 BTF 声明标签加一个扫描 IR 的编译器插件，替换掉"fmodret 程序可以修改哪些函数"的静态名单：候选是那些通向一个无副作用的 `return -errno` 的函数。有两个边界被明说而不是假定：这个选项默认关闭，需要较新的编译器，且只支持 x86-64 与 arm64；某个函数是否适合注入失败则交给运维者判断，理由是这类运维者本来就能对内核做实时的热补丁。

更小的信号，形状相同——某个性质只对某一类调用方成立。`bpftool` 的 map 转储加入批量查找，并在批量出错时从最后打印的键回退：批量遍历可能在键被删除时丢掉游标，从而把一次短遍历报告成 map 的结尾。BPF CI 当天停摆，因为 patchwork 实例封掉了把系列复制到 CI 的机器人，于是新系列没有 CI 结果，建议是不要重发而是跑本地 VM 测试脚本。一个给每个 cgroup 加带宽 runtime 文件、把它接进 BPF 调度器、再让调度器把任务计费回去的 `cpu.max.runtime` 系列被评为对未证明的用例过于激进，建议在需求明确前把调度器侧的额度留在调度器自己的 map 里。还有一处从错误的函数进入的能力检查：设置进程 securebits 时用的是朴素的能力检查而不是带命名空间的那种来检验 `CAP_SETPCAP`，于是通过 capable 钩子限制能力的 LSM（包括 BPF LSM 程序）无法拒绝一次带特权的 securebit 变更，而 `PR_CAPBSET_DROP` 却允许它拒绝；修复把两者对齐，并请 BPF LSM 一侧核对还有哪些操作会因此变得可拒绝。
