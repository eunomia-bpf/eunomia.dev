# 为什么校验器会拒绝一个用循环计数当键的数组查找，而提出的修复把可空性检查改成了什么？

因为校验器允许对数组查找省略 NULL 检查时，判断依据选错了性质。数组和 per-cpu 数组的查找返回 NULL 只有一个原因：键不小于 `max_entries`。自从支持省略可空性那次改动起，校验器就知道这一点，但它只在键是编译期常量时才给这个豁免。像 `cpu & 3` 这样掩过位的键，以及有界循环的计数，都不是常量，它们带的是一个区间。于是程序为一个根本走不到的 NULL 分支支付了代价；如果程序干脆不写 NULL 检查，就会被拒绝，报的是 `map_value_or_null`。送审的修复保留其余全部条件，只把「是不是常量」换成「有没有上界」：读出被压栈的键寄存器可能取的最大值，只有这个最大值小于 `max_entries` 时才省略可空性。

## 机制

1. **NULL 检查为什么存在。** 这个辅助函数的声明返回类型是「指向 map value 的指针或 NULL」，所以校验器给 0 号寄存器就是这个联合类型。让它穿过一次非空判断会分裂状态：真分支保留普通的 map value 指针，假分支得到一个常量空指针且不允许解引用。没有这次判断，任何经 0 号寄存器的读取都会被拒绝，因为校验器必须假设空指针分支可达。数组查找自身只有一条失败路径：拿索引与 `max_entries` 比较，不小于它就返回 NULL。

2. **今天省略检查需要什么。** 只有数组和 per-cpu 数组、而且只有 `bpf_map_lookup_elem()` 会尝试静态证明这个键。当前代码里的每个条件都必须成立：程序具备 `CAP_BPF`；键参数是指向栈的指针且偏移是常量；被覆盖的栈字节要么全是零字节（意味着键为 0），要么是一次恰好覆盖数组键那四个字节的标量压栈；并且被压栈寄存器的值是常量。满足这些，校验器就清掉返回类型上的可空标志，程序可以直接解引用。由于结论现在取决于这个值，该栈槽会被标记为精确，从而阻止校验器在「键未知」的假设下做状态剪枝。任何一种不满足——是区间而非常量、槽位未对齐或被部分覆写、内层 map——都让返回值保持可空。

3. **循环计数为什么以前能通过。** 有界循环过去是一次一次迭代展开状态来验证的，于是每次加固定值的计数会走到值恰好已知的状态，那种状态下四个字节的压栈就是常量。最近一次关于循环界计算和寄存器跨迭代加宽的改动，改为给计数一个对所有迭代都成立的区间。现在没有任何状态持有常量键，静态判断失败，本来能加载的循环就被拒绝了。送审的修复把这个提交标为它所修复的对象。掩码那种情形更早：`cpu & 3` 从来不是常量，所以不带 NULL 检查、用掩码键的查找，从省略机制存在那天起就会被拒。

4. **修复真正改了什么。** 读键的辅助函数不再问「值是不是常量」，改为把寄存器的无符号最大值与 map 的 `max_entries` 比较；调用方保存的也不再是精确值而是最大值。别的一动不动：能力判断、常量偏移的栈上键、四字节压栈或零字节、内层 map 的排除、以及精确标记，全部保留。省略仍然只施加在 `bpf_map_lookup_elem()` 上，因此还要额外接收 cpu 参数的那个 per-cpu 查找变体拿不到它。生成的代码不变：查找仍在运行时把键与 `max_entries` 比较。

5. **为什么按 64 位读这个最大值。** 栈槽继承的是被压入的那个 64 位寄存器的区间，而键只有四个字节，`max_entries` 是 32 位值。这在有用的方向上是可靠的：任何小于 `max_entries` 的值都装得进四个字节，辅助函数读到的就是校验器推理的那个值。它同时把看起来带符号的区间处理对了。一个区间为负一到零的键可以取 `0xffffffff`，这个值永远不会小于合理的 `max_entries`，而它的无符号最大值极大，于是省略被拒绝、空分支保留——这是正确答案，不是保守的巧合。

6. **为什么结论开始依赖区间。** 一旦省略取决于区间，两个键寄存器区间不同的状态就不再等价，已按省略空检查验证过的状态不能替另一个状态代表。送审的测试用强制状态展开的标志把这一点钉住：一条路径在一个分支上键区间在界内、另一个分支上出界时，程序必须被拒绝，因为界内那条路径本来会替另一条背书。这也解释了为什么有一小部分程序的指令数不降反升。

## 验证与排障路径

1. **先读拒绝信息。** 报的是对 0 号寄存器的内存访问错误、类型名里带着 map-value-或-null，位置在查找之后的那次解引用，而不是查找本身。这个形状说明校验器保留了空指针分支而程序没有判断它。

2. **一次只改一个条件。** 把键换成字面量：如果程序能加载了，问题就在键上。接着把字面量换成同宽度的掩码值，再换成循环计数，看清自己落在三种情形里的哪一种。再加一个 NULL 检查作对照：带判断的程序不论键的形状都能通过，所以「判断则通过、不判断则失败」这一对能把变量隔离到省略机制本身。

3. **检查四个静默的失格条件。** 没有 `CAP_BPF` 的程序永远拿不到省略。栈上的键分几次写入、或者偏移不是常量，就不是一个被完整跟踪的压栈槽。带内层 map 属性的 map 被有意排除，因为运行时内层数组的元素数可以少于校验器看到的原型。还要额外接收 cpu 编号的那个 per-cpu 查找变体，即使在数组 map 上也不在省略范围内。

4. **确认校验器看到的区间。** 整个检查就是键寄存器的无符号最大值是否小于 `max_entries`。掩码是造出这种区间最省事的办法；只被一个与很大值比较的循环约束着的计数不算，因为它的最大值就是那个界。

5. **对比验证成本。** 送审数据是好的参照：某个调度器工作负载上约百分之六的程序发生变化，指令总数减少几个百分点，另有少数程序变多；在一大批生产网络构建上完全没有变化。变多的程序正是键现在必须作为区间被跟踪、而不能再当作未知值被剪枝的那些。

## 局限

- 这个修复是对开发树的送审改动，尚未发布。合入之前，带区间的键仍然要么改成常量键，要么写 NULL 检查。
- 它只帮到区间能被证明落在 map 内的情形。某条路径上键可能不小于 `max_entries` 时，那条路径上的返回值依然可空，程序必须处理。
- 省略 NULL 检查不改变运行时行为。越界的键仍然会返回 NULL；校验器只是证明了对这个程序而言这件事不会发生。
- 同一窗口报告的另外两个缺口不在本次修复范围内：对静态子程序或回调的调用可以覆写调用方压在自家栈帧里的指针，这会破坏同一类栈参数分析；内核函数隐式参数的分析把一个程序根本到不了的寄存器标成活跃。两者都还在评审中。

## 当日社区讨论

本次运行审阅了六个社区。两个接入存档的聊天工作区里的三个频道，通过获准的只读存档分别按 24 小时和 7 天窗口读取，均无消息，属于安静而非跳过。另外两个聊天工作区的十个频道未被覆盖：读取需要已登录的浏览器会话，而本环境没有，因此记录为未覆盖，不是安静。一个邮件列表和一个实践者论坛通过公开页面完整读取。合计：六个允许清单来源里两个有内容地审阅、两个审阅后为空、两个不可访问。

邮件列表承载了上面回答的问题，但它只是一场更大规模修复工作里的一条补丁；把本窗口读成一次有组织的清理更容易看懂：BPF 代码会改动状态，然后忘记重新校验。当前稳定线的 27 个修复补丁分成三类。第一类是在把长度当作偏移使用之前先夹紧它，涉及栈回溯辅助函数的两个位置——回溯长度的上限，以及跳过判断——和未检查的包偏移是同一类缺陷：调用方给出的尺寸在某次截断之后仍被信任，而被调用方看不见那次截断。第二类关于内存区域：拒绝把 arena 映射到地址 0、拒绝比 map 自身页数更长的映射、不让释放例程看到一个只设了一半的用户区间、去掉映射钩子里的一条告警。这些是程序真正把 arena 当数据用、而不是当多出来的一种 map 用时才会碰到的锋利边缘，修复手段一律是「更早拒绝」而不是「稍后处理」。第三类也是最大的一类，是段路由与轻量隧道辅助函数，也就是 BPF 程序改写包头的那些地方：网络偏移必须保持有符号；封装请求必须拒绝不是预期协议族的包；调整头部的辅助函数必须连同链路层头一起移动、并且不能留下过期的一份；封装之后要复位套接字缓冲的控制块；程序改了协议就必须要求重新路由标志；传输层头要跟着被移动的头部一起走。合起来读，这对任何写改写包头程序的人是一条教训：BPF 程序改包之后，套接字缓冲里有若干派生指针和缓存值同时失效，每个忘记其中之一的辅助函数产生的都是错误校验和、错误长度或直接故障，而不是一句干净的错误。整类问题最可能的机制是这些辅助函数当初都是针对单个字段的本地改写，而它们破坏的不变式在另一个结构里。可操作的排障路径是让改写包头的程序同时在发送和接收路径上跑，并把「改协议」与「改长度」分开测；仍未解决的是这些不变式目前没有任何集中检查，一个新辅助函数可以重新引入同类问题。

第二批是 socket map 与 socket 消息处理的十五个修复，主题相关但不同：判决与重定向的状态活过了设置它的那次操作。报告描述的症状包括一次丢弃判决粘到后续流量上、一次放行判决覆盖了下一条消息、被停住的 socket 留下未清的重启状态、每次发送前没有重新检查重定向目标、塞入数据时复制位置没有复位、向已满的缓冲塞入零字节、以及一次重定向丢掉已塞入数据余下的部分。对实践者来说，症状是某个服务在一次异常接收——一次部分读、一次向用户态拷贝时的缺页、一次阻塞的发送——之后的行为与干净流量下不同，这正是这类缺陷能活过测试的原因。每个情形的机制都是一个按 socket 存放的字段在一条路径上被设置、却在一条更窄的路径上才被清除。诊断路径是用一个轮流返回各种判决的程序驱动失败操作，比较下一条消息的行为，并且在一次阻塞发送之后也检查该 socket 的状态，而不只在成功之后检查。仍不确定的是覆盖面：修复以单个提交到达，窗口里没有把判决、塞入、重定向三种状态当作矩阵来跑的测试计划。

第三条持续更久的线索是给程序在 arena 里放一个栈的 14 个补丁提案。它的动机很具体，也正是人们反复询问「能不能把通用优化编译器编出的代码当 BPF 程序跑」的原因：一个持有普通指针的数据结构并不说明被指向对象位于哪块内存，于是同一条加载指令必须同时对堆内存、只读与全局数据、以及被取了地址的局部变量有效。这只有当三者位于同一可寻址区域时才可能，因为一条指令编出来只有一种形态。第二个动机是大小与重入：这类程序动辄需要几十 KB 栈，而现有的私有栈是每个函数每 CPU 一个帧，既不支持递归，也不支持同一 CPU 上的第二次运行。提案加入一个专用的栈寄存器、arena 中按程序的栈区、一种让存在 arena 里的指针可重定位的方式、以及一个本地原子操作，并覆盖两个主要指令集。本窗口的评审集中在边界而不是思路：不在 arena 里的指针做类型转换时该怎么处理、map 未声明大小时 arena 的默认尺寸该是多少、新寄存器允许出现在哪些位置。对本文读者相关的结论是：一个栈或指针布局越过当前模型的程序未必是写错了，是区域模型在限制它。同一窗口还有一个请求，希望把两个早先的跨子程序跳转修复按安全缺陷处理并补上稳定树标签，答复是流程性的——纯文本投递、已解决的问题不必惊动安全邮件列表——这也是一名需要把 JIT 修复回溯到发行内核的人真正会撞到的门槛。

较小的条目都还在开放或早期评审阶段：一个零拷贝包 socket 的修复，在接收环满时不再释放接收缓冲，也就是恰好在环压力下会泄漏；一个轻量隧道修复，在发送路径无法扩展头部空间时释放套接字缓冲，属于同一类错误处理问题；一个发送队列修复，拒绝负的传输层头偏移，又是头部偏移的符号问题走到了算术路径上；一个工具改动，在生成内核类型信息之前剥掉构建机的编译器调试记录；第三个版本的改动让两个工具转储枚举值时尊重其符号性，并附带一个数据转储的对应修复；以及一份报告说拆分 BTF 对象重新挂到另一个 base 之后，序列化缓存可能返回重定位之前的字节。最后这一条的评审变成了一个真正的边界问题而不是行或不行：对从文件解析出的只读对象，内存里的类型数据与序列化形式指向同一块缓冲区，那个缓冲区并不是缓存，把它作废会强制一次拷贝、让按名字查找退化成线性扫描、并让带较新头部字段的格式直接失败，而真正会过期的只有字节序翻转后的那份拷贝。报告者用自包含的复现程序和回归测试演示了故障，评审者则要求更窄的作废范围、并换一个目标分支，所以这是一个机制已达成一致、修法形状未定的开放评审。

实践者论坛在 24 小时窗口内没有新帖。最新的实质讨论是几天前的，一个基于零拷贝包 socket API 的构包扫描器的实地报告，它留下的两个开放问题恰好是工程师会按同样顺序遇到的。作者先报告过一个其实错了的加速数字：一个 bug 让基准只测了一个目标主机，而它报告的时间低于该程序自身限速推出的理论下限；重建后的基准会检查每次运行是否找齐了预期端口，并记录 CPU 时间与丢帧数。随后有两个发现。绑核加忙轮询在空闲笔记本上无害，在负载重的虚拟机上却是主动有害的，因为自旋的接收线程在抢唯一一个 vcpu；现在它只在零拷贝模式下启用，拷贝模式的路径改为阻塞。更大的收益来自批量提交：这个 API 只有一个发送环，在慢主机上每发一个包一次提交调用，系统调用开销几乎就是全部墙钟时间，于是改为每次提交最多 64 个帧，时间追平传统扫描器，而 CPU 大约是原始 SYN 扫描的三分之一。诚实的开放边界是：剩下的加速取决于在多队列设备上真正跑零拷贝，而作者手边没有这样的机器，两个问题分别是唤醒标志在单发送环的拷贝模式下是否值钱，以及忙轮询循环能否挣回它绑走的那个核。决定这两点的填充、完成与唤醒语义在内核的包 socket 文档里有说明；目前可操作的答案是，批量提交这一步可以照搬，而忙轮询的取舍是一机一测的结果，不能当默认值。

本次运行接入的存档来源在两个窗口都没有消息，所以上面的问题来自允许的公开邮件列表，并对照补丁线索与已发布内核源码做了核实；除论坛那一段外，本节所有主题都来自该邮件列表。
