# Why does a cgroup BPF LSM program attached to a socket hook run in the cgroup of the calling task rather than the socket, and what does the proposed fix change in shim selection?

Because the code that picks the shim has been comparing two different kinds of BTF identifier. When a program attaches with the cgroup LSM attach type, the kernel chooses a shim that decides which cgroup's program array to run, and it chooses by looking at the first argument of the hook: a socket argument should mean the socket's cgroup, anything else means the current task. The comparison tests the argument's own type id against a table of structure ids. The argument's type id names a pointer type, and the table holds the ids of `struct socket` and `struct sock` themselves, so the two are never equal, neither socket branch is ever taken, and every cgroup LSM program runs through the current-task path. The fix resolves the argument's pointee before the comparison, so the socket branches become reachable. It was posted to the fixes tree with a stable backport request, and it changes behavior for programs that are already deployed.

## The mechanism

1. **What the design intended.** The per-cgroup LSM flavor documents its rule directly: for hooks whose first argument is `struct socket` or `struct sock`, run the programs attached to the cgroup associated with that socket; for the rest, run the programs of the current cgroup. Two hooks that operate on a freshly allocated socket with no cgroup association yet are deliberately listed as current-task hooks. The intended split is therefore socket-cgroup for socket hooks, task-cgroup for everything else, with a small explicit exception list.

2. **Why the comparison never matched.** The shim chooser reads the first parameter of the attach function's BTF prototype and compares its type id against an array of socket type ids. That array is built from structure declarations, so its entries are the ids of `struct socket` and `struct sock`. A parameter's type id is the id of the pointer type, which is a separate BTF type from the structure it points at. Equal ids would mean the parameter's type *is* the structure, which cannot be true of a pointer parameter. So both socket tests fail for every hook, the fall-through branch wins, and the two socket-specific run functions are unreachable in a working kernel.

3. **What the current-task path does.** That path takes the default cgroup of the current task and runs that cgroup's effective program array. So the policy that gets applied is the policy of whoever happened to make the call, not of the socket. Two consequences follow. A socket created in one cgroup and used from another is checked against the user's policy rather than its own — a process that borrows a listening socket, a worker that sends on a socket it inherited, a shared socket passed between services. And hooks that can run in softirq context no longer have a meaningful task at all: the packet receive hook, the connect-request hook, and the socket security-id hook run against whichever task the interrupt happened to hit. Kernel socket allocation even assigns a socket created in interrupt context to the default root cgroup on purpose, precisely so that an interrupted task's cgroup cannot leak into socket ownership — which shows how much the current-task choice matters for these hooks.

4. **What the fix changes, and why it needs a fallback.** The chooser now resolves the first argument's pointer type to the type it points at and compares that resolved id against the socket id table, so the socket and sock branches are selected as documented. Making that branch reachable exposes call sites that pass a socket without an internal socket structure. Two of them exist in current code: the receive-side control-message security path calls the datagram peer-security hook with a null socket, and the lightweight socket creation path runs the post-create hook before the internal socket is assigned, since the socket structure is allocated later inside protocol creation. The fix therefore adds a null check that falls back to the current-task path for those two cases instead of dereferencing. The patch states that the sock-argument path needs no such fallback: the two hooks that run while a socket has no cgroup association are on the explicit current-task list, and every other hook whose first argument is an internal socket runs with a non-null socket whose association is already set.

5. **Which hooks move, and what that means for existing deployments.** The rule is mechanical: the affected hooks are the ones whose first parameter is a socket or an internal socket. The hook prototype table lists thirty of them, two stay on the current-task list, so twenty-eight move. On the socket side that is post-create, socketpair, bind, connect, listen, accept, sendmsg, recvmsg, the two name queries, option get and set, shutdown, and the two peer-security hooks; on the internal-socket side it is packet receive, clone, security-id, connect-request, connection-established, netlink send, the Unix-domain connect and send hooks, socket graft, and the tunnel and protocol-specific attach hooks, minus the allocation and release pair. Programs on those hooks stop running because of what the calling task is doing and start running because of the socket they touch. For most single-cgroup workloads the two are the same cgroup, which is why the bug survived: the wrong choice is invisible until a socket crosses cgroups or a hook fires in softirq context.

## How to verify and debug

1. **Cross one cgroup boundary deliberately.** Create a socket in one cgroup, hand it to a process in a second cgroup, and have that process call connect or send. Attach a counting program at both cgroups on the same hook. On an affected kernel, both counters move only under the calling cgroup; after the fix, the socket's own cgroup runs the program too.

2. **Compare the caller to the socket.** A cgroup LSM program can read the current task's cgroup id with the standard helper. Log it from a socket hook and compare against the cgroup you expect to own the socket. A program that fires while reporting an unrelated cgroup id is running through the task path.

3. **Test a softirq hook specifically.** Attach to the packet receive or security-id hook and repeat the same traffic under load. Run counts that follow the interrupted task rather than the connection identify this bug even without a cross-cgroup socket, and the noise disappears on a kernel with the fix.

4. **Confirm the affected range.** The shim-selection function exists in released kernels from the 6.0 tag onward and not in the 5.19 tag, and the fix carries that per-cgroup LSM commit as the one it repairs, so any kernel in that range selects the task path for socket hooks. Check your kernel against the fix before assuming a policy is being applied per socket.

5. **Do not trust an attach listing.** The attach succeeds and the program shows up in the cgroup's program list either way; nothing in the listing reveals which cgroup's array will be run. The counting test above is the cheapest decisive check.

## The limitation

- The fix is a posted change in the fixes tree with a stable backport request, not yet a released kernel. Until it lands, a null test on the caller's cgroup is the only correct assumption for socket hooks.
- This concerns the cgroup LSM flavor on the unified hierarchy only, which is what the current-task path reads.
- The rule is decided by the *first* argument. A hook that carries the socket in a later argument still runs in the task's cgroup, before and after the fix.
- The behavior change is intentional but not silent: existing programs move to a different cgroup array. The posting itself raises the open question of whether it belongs in a stable backport or in the next merge window, since users may be relying on the current behavior.
- The report carries no new selftest, so a regression would be caught by behavior, not by the test suite.

The mailing list carried the question answered above, and the rest of the window fits one theme: code that hands out or reuses memory whose true state the verifier no longer tracks. The clearest example is a two-patch fix for the helpers that return a slice of a dynamic pointer. When the data is not contiguous, those helpers copy it into a caller-supplied buffer and return that buffer, which the verifier treats as plain memory rather than as the stack slot it is. A later store through the slice therefore overwrites whatever the verifier still believes is in the slot — a known scalar, a spilled pointer, a dynamic pointer, an iterator — and a load reads those bytes back as a scalar. The report says such a program loads today and can crash the kernel. The fix records the frame, offset, and size of the buffer in the slice and invalidates the slice at each event that breaks the invariant that the buffer holds no tracked data: a store into those bytes, the creation of new tracked data there, or the return of the buffer's frame. Helpers that fill the buffer are explicitly allowed, because they leave only untracked bytes. The rejection a program sees is a memory-access complaint naming the scalar type, and the verification log gains a rendering of the buffer a slice points at. The second revision of this thread extended the rule to read-only slices of the read-only variant, which is the case a reviewer is most likely to assume is safe. The same window also carried a second revision of a change to keep a packet pointer's valid byte count inside the loop-bound analysis, and a second revision of a four-patch fix for two holes in the analysis of stack arguments — both the same family of "the verifier's model of a location drifts from the machine's".

Two fixes in the window are about lifetime rather than tracking. A two-patch change moves deferred program freeing off the shared system workqueue, and the report is a good illustration of a class that is easy to misdiagnose: freeing the last program in an allocation pack takes a lock and then calls into code that changes page permissions, which may queue work to the same CPU and wait for it. Other freeing workers blocked on that same lock fill the workqueue's active slots, so the worker holding the lock can never see its own queued work run. The visible symptom is a hung-task warning naming the deferred free worker, not a BPF error, which is why it looks like a scheduler or memory problem from the outside. A separate two-patch set follows up on the memory-region mapping fixes after review: one stops a fixed-address mapping request from being relocated at all, because the rounding in the check that rejects address zero can itself wrap to zero; the other makes that mapping test serial and adds subtests.

A third group is toolchain and build robustness, and it matters to anyone shipping a kernel with kernel type information: a report of the tool that resolves type references in kernel code crashing when debug information is built with inlined line info, which a follow-up reply traced to a use-after-free on a module whose type information has no string table of its own; two architecture changes that strip a build machine's compiler debug records before generating kernel type information or disable it on an architecture that cannot produce it; a documentation change to the minimum version of the type-generator tool; and a five-patch fix for three bugs where instruction patching interacts badly with constant blinding and nop removal. A separate thirteen-patch third revision replaces the instruction-patching primitive with a list of deferred patches, which is the same underlying problem — patches applied to an instruction array that is still moving.

Smaller items, all open or in early review: a fifteen-patch second revision of the socket-map verdict, redirect, cork, and receive fixes, together with a request-for-comments proposal to restrict socket-map updates made from an iterator context to socket-map iterators; a one-line rejection of a scheduler destroy helper being called from tracing programs; an architecture fix pairing the new memory regions with trampolines; a performance report of a large regression in a syscall-heavy stress benchmark attributed to an unrelated bug-mitigation change; and a process thread arguing that fixes tags in the development tree need more care, which is the maintenance-side version of the same problem this page keeps running into — a fix recorded against the wrong thing is a fix nobody can find.

The unanswered half is the workload estimate, which is exactly what a topic decision needs and what nobody can give a stranger. Two older threads in the seven-day window stay open on the same trade-off from the other side. One asks how much application-layer parsing belongs in the kernel rather than in a userspace proxy. The most substantive answer cites [a published in-kernel layer-7 load balancer](https://arxiv.org/abs/2602.09473) and its stated limit: the design carries its connection management through new socket-layer redirection rather than plain program facilities, and on the commenter's reading that is why meaningful in-kernel layer-7 work today is mostly observation and asynchronous action rather than redirection or crafted responses. That is a usable boundary — parse enough to decide, and hand off anything that has to own the connection. The other thread reports a zero-copy packet path that merely tied a conventional scanner once its sends were batched, and asks two questions still without answers: whether anyone with a zero-copy network card will measure the difference, and whether anything beats batching on a single transmit ring short of going multi-queue. The practical reading is that the ceiling in copy mode is the ring, not the program, and the honest caveat that thread keeps receiving is that the win depends on the hardware and on having kernel engineers on call.
