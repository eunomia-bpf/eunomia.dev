# 为什么 BPF ring buffer 的消费者会在记录已经入队时睡下去，又需要什么顺序保证唤醒握手成立？

**简短回答：** 内核不是在「有新数据」时通知，而是在「消费者正好追赶到刚提交的那条记录」时通知，而这个判断是一次对消费者位置寄存器的读。用户态的消费者做的是镜像动作：先发布自己的消费者位置，再去读生产者位置，决定要不要睡。只要发布与探测之间没有一道完整的 StoreLoad 屏障，两侧就都可能读到对方最新那次写之前的值。release 存储并不为之后的加载排序，所以缺了屏障时，消费者会认为环是空的，而其实记录已经提交；生产者会认为没人在等，于是消费者睡下去，谁都不会再叫醒它。libbpf 的消费循环正好有这个缺口，正在评审的修复就是在「发布消费者位置」与「下一次读生产者位置」之间放一道完整栅栏，并在栅栏之后把 busy 记录再重试一次。

## 机制

### 1. 通知是按位置相等的边沿触发

`bpf_ringbuf_commit()` 先清掉记录的 busy 位，然后决定要不要唤醒消费者：

```c
xchg(&hdr->len, new_len);

rec_pos = (void *)hdr - (void *)rb->data;
cons_pos = smp_load_acquire(&rb->consumer_pos) & rb->mask;

if (flags & BPF_RB_FORCE_WAKEUP)
        irq_work_queue(&rb->work);
else if (cons_pos == rec_pos && !(flags & BPF_RB_NO_WAKEUP))
        irq_work_queue(&rb->work);
```

比较是相等，不是「生产者领先于消费者」。只有恰好位于消费者当前位置的那条记录会发出通知，而且只在消费者没有落后时才发。内核文档把这套做法称为自我调速：提交之后「只在消费者已经追赶到所提交记录的位置时才发通知；如果没有，消费者无论如何都要追赶，因此不需要额外的 poll 通知」。这个推理成立的前提是：消费者下一轮**确实**能看到数据。上面那次读是生产者的半次握手，而它可能拿到旧值。

### 2. 消费者的那一半是「先写、后读」

当前 libbpf 的消费循环，骨架如下：

```c
cons_pos = smp_load_acquire(r->consumer_pos);
do {
        got_new_data = false;
        prod_pos = smp_load_acquire(r->producer_pos);
        while (prod_pos - cons_pos > 0) {
                len_ptr = r->data + (cons_pos & r->mask);
                len = smp_load_acquire(len_ptr);
                if (len & BPF_RINGBUF_BUSY_BIT)
                        goto done;
                /* 调用回调，然后 */
                smp_store_release(r->consumer_pos, cons_pos);
                if (cnt >= n)
                        goto done;
        }
} while (got_new_data);
```

每消费一条记录就用一次 release 存储发布 `consumer_pos`，紧接着循环又去读 `producer_pos`，判断是否还有数据。这一对「存储—加载」就是消费者的半次握手：生产者那次相等比较读到的正是它。

release 存储与 acquire 加载构成 release-acquire 对，它保证记录数据在声明该记录的位置之前可见。它不负责把**之后的加载**排在这次存储之后。内核内存屏障文档说得很直接：`smp_store_release()` 与 `smp_load_acquire()` 背后的弱指令「并不要求在所有情况下把先前的存储排在随后的加载之前」。把存储排在随后的加载之前的，是 StoreLoad 屏障。

### 3. 究竟哪个窗口会丢记录

两次存储可以同时在途。消费者的 release 存储还没传播到生产者的 CPU；生产者的保留操作已推进了生产者位置，但消费者自己的那次加载仍返回旧值。于是：

- 生产者提交，读到的 `consumer_pos` 是消费者那次存储**之前**的位置，按它自己的规则正确地判断「消费者还没追上」，因此不排 `irq_work`；
- 消费者这一轮收尾时认为环是空的，然后在 `epoll_wait()` 里睡下。

两侧读到的东西都没错，而再也没有什么去叫醒消费者。这就是缺陷的全部：丢的不是记录，是通知。

libbpf 把 map fd 注册为**水平**触发（`e->events = EPOLLIN`），所以 `ring_buffer__poll()` 进入内核时会重新判断一次就绪状态，这把窗口压缩到「这次就绪检查之后、真正睡下之前」：记录必须在检查之后提交，且通知必须被跳过。窗口再窄也是挂死，而该系列在自测里补了一个边沿触发的就绪用例，每次调用只消费一条记录，让握手在每一次有界返回上都真正被走到，而不只在启动时走一次。

### 4. 修复是在发布与探测之间放一道完整栅栏

该系列的第 3 个补丁把循环改成「发布、栅栏、探测」：

```c
if (!got_new_data)
        return cnt;

/*
 * Order the published consumer position before the next
 * producer-position load, whether below or in a later invocation.
 */
__atomic_thread_fence(__ATOMIC_SEQ_CST);
```

并且在各个提前返回的路径上同样执行这道栅栏，使**下一次**调用里的加载完成同一个握手。它还把 busy 位的处理从「直接退出」改成「发布、栅栏、重试一次」：生产者可能正好提交了消费者刚读成 busy 的那条记录，并且因为读到旧的消费者位置而跳过了唤醒；在栅栏之后重试这次加载就把这个变体也关掉了。

有两个细节说明这不只是风格问题。第一，栅栏必须是完整的，不能再是一个 acquire。Aya 遇到过同一个 bug，并在提交信息里写清了为什么这对操作不可移植：x86-64 上 LLVM 为这次存储发出 `xchg`，顺序是顺带得到的；AArch64 上 `STLR`/`LDAR` 给出 RCsc；但在 powerpc64 上「LLVM 把 `sync` 放在存储之前、`isync` 放在加载之后，两者之间没有完整屏障」。他们的修复形状相同：release 存储，然后一道显式的顺序一致栅栏，再去读生产者位置或重试 busy 记录。第二，修复属于消费者，不属于生产者。生产者已经有它需要的完整屏障——提交记录时那次 `xchg` 就排在读消费者位置之前。

### 5. 提前停下是漏掉通知的第二种方式

因为通知是边沿触发的，一个已经被告知「就绪」却没收完就停下的消费者，不会再被告知第二次。`ring_buffer__consume_n()` 的上界，以及回调返回负值中止消费，都会让调用结束时环里还有记录；而提交这些记录的生产者当时看到的是一个没追上的消费者。所以该系列给两个消费入口和回调类型都加上了这条规则：「达到请求的上界并不说明环是空的。记录可能已经入队而不会再有新的就绪通知。在等待 map fd 之前，一直 consume 到返回 0。」在水平触发注册下，`ring_buffer__poll()` 本身仍会重新报告尚有数据；但如果程序等的是回调喂出来的某个条件，或者在自己的 epoll 集合里把 map fd 注册成边沿触发，就不会。

同一个补丁还写清了返回值的约定。回调返回 0 或正数都继续消费，返回值本身被忽略；只有负数才中止。早前有人提议用正数表示「提前结束」，被否掉了，因为正数一直是被忽略的，改动它会破坏已有用户。真正回应这个需求的是同系列里那个调用方持有的迭代器：每次调用返回一条借用记录，用普通的循环控制代替「怎么才能停下」的技巧；而一个未耗尽就被销毁的迭代器仍保留唤醒握手。

## 验证与排查路径

1. 从用户态证明「已入队但没有通知」。对单个环比较 `ring__producer_pos(r)` 与 `ring__consumer_pos(r)`，然后调用 `ring_buffer__poll(rb, -1)`。如果两个位置相差至少一整条记录、而 poll 再也不返回，那条记录就是已提交且等不到唤醒。libbpf 里两个访问器都是 acquire 加载，所以即使唤醒路径坏了，数字也是真的。
2. 把 busy 记录与丢失的通知分开。读 `data + (consumer_pos & mask)` 处 8 字节的长度字；如果 busy 位为 1，说明记录已预留但尚未提交，按设计此刻本来就不该有通知。等它提交，或者跳过它继续消费。
3. 把竞态与提前停下分开。在回调里计数并记录结束上一次 `consume_n` 的上界或负返回值。如果挂死只发生在有界返回或回调失败之后，那是文档里写的「先排空再等待」规则，不是顺序 bug。
4. 确认顺序。在消费者位置存储与下一次生产者位置加载之间插入一道完整栅栏（或直接打上该系列），重跑能复现挂死的压力测试。对这四个访问——消费者存储后加载、生产者存储后加载，都落在两个位置字上——跑一遍内存模型，可以看到「双方都读到对方旧值」的那个结果确实存在，去掉栅栏时它被允许，加上 `SEQ_CST` 栅栏后它消失。
5. 如果暂时不能改 libbpf，就不要只依赖通知。用有上限的超时 poll，并在睡下之前用 `ring_buffer__consume()` 一直消费到返回 0；或者把两个位置访问器算出的「生产者领先」当作就绪条件。两者各多一次系统调用或一些自旋，但不依赖那道缺失的屏障。

## 限制

- 这个修复是仍在评审中的补丁系列，不是已发布的 API。对旧版 libbpf 编出来的消费者就有这个缺口；真正的修复只能是升级，因为栅栏必须落在消费循环内部。
- 握手假定只有一个消费者。多个线程或进程消费同一个环会共用 `consumer_pos`，它们之间会把相等判断破坏掉，有没有屏障都一样；要么每个消费者各用一个环，要么只让一个线程消费。
- 内核的通知路径是 `irq_work`，不是直接唤醒，所以即使它会触发也有延迟。在负载下测「每条记录唤醒几次」，量到的是 `BPF_RB_NO_WAKEUP`/`BPF_RB_FORCE_WAKEUP` 策略与这个握手的合体，不是消费者本身的速度。
- overwrite 模式的 map 目前仍不支持基于回调的消费，这个系列里调用方持有的迭代器也没有扩展到它们。

### 唤醒握手，以及 API 为什么长出第二种形状

上面的问题是贯穿多个主题的一类问题的一个实例：边沿触发的通知，是对**下一次检查**的承诺，因此每一条提前返回的路径都必须让另一侧还能继续推进。该 ring buffer 系列从三个方向描述了同一个边界——跨有界返回的握手、允许中止消费的回调，以及「已提交但尚不可见」的记录而它的生产者凭旧位置跳过了唤醒。负载下见过读取端挂死、并把它归咎于生产者、环大小或回调的人，多数遇到的是三种里的最后一种。

同一系列也暴露了 API 的薄弱处。回调只能靠返回负值停下，这把「我已经够了」和「环坏了」混在一起；用正数表示提前结束的捷径其实早就名存实亡，因为调用方多年来一直忽略正数。评审中的答案是调用方持有的迭代器：每次返回一条借用记录，`next` 结束上一次借用，是否立刻发布已消费记录由调用方决定。对今天写读取端的人，实用结论是：把「发布消费者位置」和「决定是否等待」放在同一条代码路径上，并且只要这条路径可能提前结束，就在阻塞之前先排空。

### 一个「先跑完再判断」的校验器

窗口内最大的系列把校验器的主分析换成「先合并、出错后回溯」。动机很具体：现在的设计在每个汇合点猜测是合并两个状态还是保持分开，而猜测是终局的——合并可能丢掉一个事实从而拒绝合法程序，分开又会让状态数增长到触顶。提案的顺序相反：全部合并、跑一遍，只在出现错误时用状态里的等式把错误真正依赖的那些状态区分开。

封面信给出了量化结果，覆盖 6005 个程序、331763 次构建：平均指令数在 7.4 候选版是 18110，bpf-next 是 2716，该系列是 1750；平均验证时间 23.2 ms、10.3 ms、5.2 ms；平均峰值状态数 562、143、18。它还直接删掉了标量演化那个文件，因为「每个计数器一个范围」变成了挂在状态上的等式。对实践者来说有意义的差别在诊断方向：现在被拒绝时，你知道是哪个模式的猜测判错了；按提案被拒绝时，会连错误真正依赖的路径和数字一起给出。

### 可抢占上下文里的 per-CPU 暂存槽并不安全

三个辅助函数共用三个按嵌套计数选择的 per-CPU `pt_regs` 槽。raw tracepoint 与 tracing 程序可能被抢占，任务离开这些槽的顺序就会乱，一个任务的样本于是拿到另一个任务的寄存器。报告里的测量没有歧义：在可抢占内核上，两个 raw tracepoint 程序加一个实时线程强制抢占，5 轮各 10 秒，每个程序有 7 到 18 个样本的返回地址是错的，362 到 535 个空内核栈，168 到 364 个空栈 id；修复后三项全为零。修法是在每次辅助函数调用时于栈上构造一份 `pt_regs`，并把那些槽删掉。

删掉槽也删掉了一个嵌套上限，所以该系列显式把它补回来，并说明它为什么存在：`bpf_perf_event_output()` 在一个 CPU 上第四次进入时会告警，而栈辅助函数里收集构建 id 会调用 `mmap_read_trylock()`，后者会触发 mmap 锁的 tracepoint，于是挂在这些 tracepoint 上的程序会像程序数量那样层层嵌套。只做「删掉槽」这一半时，构建 id 栈辅助函数的实测嵌套深度从 4 升到 6，调用次数从 150 万升到 590 万；把显式上限加回来后，同一测量的深度回到 4、调用次数回到 150 万，`bpf_perf_event_output()` 的告警也不再从 kprobe 或 raw tracepoint 程序触发。对正在排查「栈里出现别的任务的帧」的人，诊断是同一条：确认那份内核上下文是否来自可能被抢占覆盖掉的 per-CPU 暂存缓冲。

### 两个作者自己说清的边界

一个把 classic BPF 过滤器 JIT 一次、在进程间共享的 seccomp 缓存提案，被否的理由不是性能，而是两点：「不可变还不够。镜像取决于加载该过滤器的任务的权限」，以及任何任务都能通过给 `seccomp()` 计时得知别人装着这个过滤器，而目前读回过滤器需要 `CAP_SYS_ADMIN`。评审者给出的替代很朴素——`fork()` 本来就共享过滤器，启动器装一次公共过滤器再 fork 各个沙箱即可。这里的一般边界是：一份 JIT 镜像的可移植性，只等于它生成时所依据的权限与指针布局。

另一个 arena 系列把第一版方案换成了一个原语：把不是自己分配的页映射进 arena，每次映射成为一个由页的提供方而非 arena 拥有的引用，整体释放、不计入 arena 的内存用量，若在提供方退出后仍被访问则以 `SIGBUS` 报告。第一版是把固定的 arena 通过来宾 NUMA 节点共享，评审指出的问题恰好是这种形状必然带来的：页会回来宾的 buddy 分配器，而主机仍可写；块粒度还让共享一页要花 16 MB 来宾内存。两版值得对照阅读，因为它们是把同一个问题问了两遍：页归谁，以及那个归属者一停下会发生什么。

### 彼此不一致的调度器入口路径

两个 `sched_ext` 修复都源于「本该动的计数器没动」。在 fork 路径上，`wake_up_new_task()` 会查询 CPU 选择，但在激活新任务时没带上「已选定 CPU」的标志，于是 ext 调度器在 fork 路径上永远看不到这个情形，回退计数器也从不递增。用一个强制回退的探针在基线上跑 4 万次 fork，回退事件计数为 0，而唤醒路径正常计数。第二个是状态约定问题：`rt_mutex_setprio()` 是进入 sched_ext 的唯一不先阻塞保留捐赠者的入口，于是一个被 RT 等待者提权、又在第二个互斥锁上阻塞的任务，回 ext 时带着调度器自身状态转换代码保证「不会出现」的「已入队且已阻塞」状态。一个驱动模型触发器在基线上 4 万次优先级继承循环里造出约 39966 个这样的捐赠者，修复后为 0。对写调度器的人的教训是：把每条入口路径都当作独立的状态生产者，并且按路径分别看计数器，而不是只看总数。

### 较小的条目

无符号 32 位枚举重定位系列在窗口内推进到第四版和第五版，仍在打磨「修复必须接受哪些指令形式」。一个 49 个补丁的校验器改写以两个修订在同一天出现。一个 perf 核心系列修了软件事件样本数据在事件之间被复用、以及 BPF 程序读到未初始化的样本地址，最后去掉那个结构 256 字节的清零：开着软件计数器时，这些计数器在约 627 ns 的一次上下文切换上占 54 ns，改动后降到 44 ns。符号查找系列推进到第三版，用按名字排序的索引，并给标记密度加了一个内核参数。网络侧，一个接收路径系列把「挂载 XDP 时排除硬件接收合并」的规则从各驱动上移到核心，因为驱动彼此不一致：有的拒绝挂载，有的清掉特性，至少一个在挂载期间保留着合并；改完之后这些特性应留在 wanted 集合里，并在 detach 后恢复。
