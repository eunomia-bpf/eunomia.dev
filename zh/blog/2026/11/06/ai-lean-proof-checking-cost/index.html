为什么复查某些 AI 写的 Lean 证明，几乎和重新编译一样贵？

复查一个已经存好的 Lean 证明，通常可以跳过当初找证明的搜索；但如果证明本身是一次计算，内核就要把计算重新跑一遍。我们在 OpenAI 公开的 163,096 个模块的 AI 生成 Lean 库上测量了这两种情况，也统计了 AI 证明对计算的依赖程度、编译整个库的代价，默认构建漏掉了多少内容，以及 Lean 自带的检查器实际重新检查了什么。

OpenAI 公开了一个 AI 生成的数学仓库，里面的结果都附带 Lean 证明。在我们研究的版本里，它有 163,096 个 Lean 模块，文件数大约是它所依赖的 Mathlib 快照的十九倍。要复用这样一个库，总得有人在生成它的环境之外重新检查一遍。一般的预期是这一步很便宜：Lean 的策略（tactic）可能要搜索好几分钟才找到证明，但 Lean 只保存最终的证明项，独立检查器验证这个证明项时并不重复搜索。

对普通的数学证明，这个预期成立。但 AI 生成的 Lean 代码大量使用另一种写法：用计算来证明。这类证明的意思相当于“把这个有限的检查算一遍，确认结果是 true”，存下来的证明项很短，可 Lean 内核每次检查都要把整个计算重新跑一遍。对这类证明，检查就等于重算。

我们在这个库上把两种情况都测了一遍：逐个编译了其中 162,170 个模块并记录每个模块的代价，选取若干模块比较内核检查和编译的时间，统计计算式证明出现的频率，并对比默认构建实际编译的文件和仓库里的全部文件。本文介绍我们在 Lean 和 AI 生成证明上的发现。六页的技术报告可以在这里下载 PDF。

复查一个 Lean 证明时发生了什么

Lean 编译一个源文件分两步。先由繁饰器（elaborator）运行 simp、omega、linarith 这类策略，它们可能搜索、回溯、调用判定过程，最后产出一个证明项，也就是一个完全显式的对象，只记录走通的那些步骤。然后内核对这个证明项做类型检查，Lean 再把结果写进 .olean 文件。独立检查，比如 Lean 自带的 leanchecker，或者 Lean 4.35 新增的 lake check，会加载这些存好的证明项，让内核再检查一遍。第二次检查不会运行任何策略，当初搜索花掉的时间也就省下了。

用计算来证明，存下来的东西不一样。对一个可判定命题 p，decide 策略产出的证明说的是“decide p 求值得到 true”。证明项很短，但内核要接受它，就得把 decide p 一路归约到 true，也就是在真实的有限对象上把判定过程跑完：组合命题的每一种情形、表格的每一项、小图的每一种着色。普通的 decide 在编译时要求值两次，繁饰器一次、内核一次；decide +kernel 跳过繁饰器那一次，只让内核求值一次。两种写法里，内核的这次求值都属于证明检查的一部分，所以每次复查都会重跑一次。

两类证明，检查代价相差悬殊

为了看清差别，我们在同一个测量口径下比较了四个模块：依赖都已加载之后，读取并用内核检查这一个模块的时间，除以从源码编译这个模块的墙钟时间。所有运行都用 Lean 4.34.1，在同一台 Intel Core i9-14900K 的 8 个性能核上一次只跑一个任务。

模块证明类型复查时间占编译时间的比例
Grid（AI 库）计算式证书80.28%
Amplitudes（AI 库）计算式证书82.35%
Mathlib Nat.Basic普通证明6.54%
NearPin（AI 库）普通证明0.46%

Grid 和 Amplitudes 的复查分别用了 255.5 秒和 110.0 秒，几乎全部花在内核的重放调用里。两个普通模块的复查只占编译时间的一小部分，和预期一致。而两个证书的复查重做了大约五分之四的编译工作，因为编译的大部分时间本来就是在做这次计算。

把范围扩大到更多模块，两类之间的界线就模糊了。在 31 个我们完整测量了编译进程和检查进程的模块里，检查用掉的 CPU 时间中位数是编译的 45.1%。源码里显式写了 decide +kernel 的模块中位数是 49.8%，没写的是 39.1%，两组的分布互相重叠。一个原因是普通的 decide 和其他策略也可能在证明项里留下大量求值。一个源码里没有 decide +kernel 的 Ramsey K10 证书，检查用了 356 CPU 秒，编译用了 1,725 CPU 秒（20.7%）。源码里的标记可以提示检查代价，但最终要靠测量确定。

整个项目的平均值会把这些模块掩盖掉。检查 Falconer 这个子项目的完整依赖闭包，只花了编译 CPU 的 6.31%，因为大量便宜的依赖把少数昂贵的证书稀释了。规划复查时，应当按单个证书来估算预算：项目整体的比例说明不了某个证书要查多久，一个很短的源文件也可能是最难查的之一。

AI 写的 Lean 对计算的依赖远超 Mathlib

为了知道这类证明有多常见，我们在屏蔽注释和字符串之后统计了 decide +kernel 的调用次数。AI 库里有 1,354,379 处，分布在 5,848 个文件中；它所依赖的 Mathlib 快照里只有 7 处，分布在 8,529 个文件中的 4 个。按源码体积归一化，AI 库使用这种写法的密度是 Mathlib 的 10,668 倍。

我们没有专门验证原因。一个可能的因素是，AI 库里有很多命题针对的是具体的有限对象，穷举求值是搜索能稳定找到的证明，而 Mathlib 以一般性的定理为主。这里的统计是词法层面的：它指出计算可能出现在哪里，某一处调用实际花多少 CPU 仍然需要测量。

编译整个库要花多少

我们在上面那台 i9-14900K 上逐个模块编译了整个库，用了全部 8 个性能核和 16 个能效核中的 14 个，并单独记录每个模块的 CPU 时间。163,096 个模块中有 162,170 个（99.43%）编译完成，没有模块最终失败。剩下的 926 个被我们暂缓：PadicHodge、Ramsey.CycleClique.Construction、BigCrystalline 等几个模块族在这台 64 GB 内存的机器上反复耗尽构建任务可用的内存，于是我们把这些模块族和所有依赖它们的模块放到了最后不做。

完成的部分用了 31.5 小时墙钟时间，在性能核上用了 169.0 CPU 小时，在能效核上用了 302.4 CPU 小时。两种核我们分开报告，因为它们一小时能做的工作量不同，我们也没有把一种折算成另一种。这两个数字都只是整个库的下限：暂缓的正好是最吃内存的模块，很可能也是最贵的一批；而且编译顺序按依赖关系排列，并不是随机抽样，完成的部分不能用来估算剩下的部分。

代价集中在少数模块上，而文件大小很难说明是哪些模块。在性能核上，中位数模块只用了 4.0 CPU 秒，而最贵的 1% 模块用掉了大约四分之一的 CPU 时间。含有 decide +kernel 的 5,848 个文件占已编译模块的 3.6%，在两种核上都用掉了约 18% 的 CPU。全库最贵的单个模块 OAI.Analysis.FreeWords.UltraExpectationFull 是一个 15.9 KB 的文件，没有 decide +kernel，在能效核上用了 9,314 CPU 秒；而一个 5.3 MB、含 11,114 处 decide +kernel 的 Ramsey 证书文件，在同类核上只用了 2,241 CPU 秒。那个 15.9 KB 文件的代价有多少会在复查时重现，我们没有测量。

此前一份针对同一个库的独立报告在 32 个云端 vCPU 上用 13.8 小时构建了较早版本的 122,458 个模块，估计总计约 410 CPU 小时，其中约 330 小时的编译时间是从 26 个计时模块外推出来的。版本、硬件和范围都不同，两组数字没法直接比较。逐模块普查补上的，是 162,170 个模块各自的实测代价，而不是外推值。逐模块的记录在代码仓库里。

构建成功只覆盖了库的一部分

lake build 成功，通常被当作一个 Lean 项目通过检查的证据。默认构建只编译从项目声明的根目标出发能到达的模块。在这个库里，这些根目标能到达 163,097 个源单元（含构建配置）中的 130,834 个。其余 32,263 个文件，占总数的 19.78%，默认构建从来不会编译。这些文件里有 1,354,379 处 decide +kernel 中的 451,008 处，占 33.30%。也就是说，库里三分之一的计算式证明，位于一次成功的默认构建根本不碰的文件里。

此前那份报告在它的版本上看到了同样的现象：默认依赖图之外有 30,697 个文件，约占它源码清单的四分之一。谁要说这样一个库“通过了检查”，都应该说明自己构建了哪些根目标，这些根目标覆盖了多少文件。

检查大型库之前值得了解的 Lean 行为

Lean 的 -M 内存上限在计算式证明上代价很高。 构建或检查服务需要防止内存失控时，很自然会用 Lean 的 -M 选项，即以 MB 为单位的内存上限。设置了 -M 之后，Lean 的内存检查每运行 200 次就调用一次 getrusage，而内核在归约过程中会不断执行这个检查。getrusage 要汇总进程内所有线程的资源用量，每次调用都有实际开销。用 8 个线程编译 Grid 时，一共调用了约 400 万次 getrusage。去掉 -M，在 Lean 进程外用 cgroup 保持同样的 15 GiB 上限之后，Grid 的编译时间从 622 秒降到 306 秒，系统态时间从 436 秒降到 107 秒（三次运行的中位数）。UMoments9 从 142 秒降到 88 秒，而普通模块 EnvelopePsiB 几乎没变（64.4 秒到 63.5 秒）。所有输出逐字节相同。对计算密集的证明，在 Lean 进程外部限制内存，能得到同样的保护，又没有这份记账开销。

leanchecker 可能把几乎全部时间花在找文件上。 默认模式下，Lean 自带的检查器先枚举搜索路径上所有的 .olean 文件，把每个文件名解析成模块名，然后才挑出要检查的根模块。在 AI 库的构建环境里，搜索路径有 90 项，枚举出 203,273 个 .olean 路径条目（其中有重复的根），检查 Mathlib 的 Mathlib.Data.Nat.Basic 用了 322.9 秒，其中系统态 CPU 234.6 秒；换成只包含这个根所导入的 1,330 个模块的搜索路径，同样的检查只用了 0.39 秒。一个只运行这两步发现过程的探针，枚举目录用了 2.6 秒，解析模块名用了 271.4 秒。这些都是在一个格外庞大的环境里的单次观测，补救办法却很简单：只把待检查闭包放进检查器的搜索路径。

默认模式和 --fresh 回答的是不同的问题。 默认模式信任导入，只重新检查目标模块自己新增的声明；--fresh 则把最终合并后的环境，也就是根模块能看到的全部常量，重放进一个空的内核环境。同一个产物，两种模式的结论可能不同。删掉某个模块的 .olean.private 分片之后，默认模式照样接受，--fresh 则因为读不到这个分片而失败。用已弃用的原生求值桥接 Lean.ofReduceBool 写成的证明，默认模式通过，--fresh 失败，因为它没有把内核执行这次求值所需的编译代码带过去。

检查合并后的环境，和逐个检查每个模块，是两回事。 两个模块证明了同名、同命题的定理时，同时导入它们只会留下一份证明体，即最后导入的那个模块里的那一份。我们直接修改其中一个模块的序列化文件，弄坏了它的证明体，正常编译不会产生这样的文件。把坏模块单独作为根检查，两种模式都拒绝了它。一个先导入好模块、再导入坏模块的根，被 --fresh 拒绝；导入顺序反过来时，好的证明体在合并环境里替换掉了坏的，--fresh 接受了这个根。默认模式不重新检查导入，两个根它都接受。要确认每个模块的证明都能通过内核，就要把每个模块分别作为根来检查。

这些例子都不涉及正常编译的源码证明出错误命题，它们说明的是每条命令实际重新检查了什么。三个例子的最小输入和脚本都在代码仓库里。

几点经验

如果要复查一个 AI 生成的 Lean 库，应当预期两种代价。普通证明的复查只占编译时间的一小部分；计算式证书会把计算重跑一遍，需要逐个估算，而不是相信项目平均值。估算任务规模之前，先统计库里有多少内容依赖计算；报告结果时，说明构建或检查实际覆盖了哪些根目标；内存上限放在 Lean 进程外部执行。

适用范围

所有测量都来自同一台机器、同一个库的同一个版本，以及 Lean 4.34.1。代价对比只用了少数几个选定模块，31 个模块的对照也显示两类之间是连续分布，而不是界线分明的两类。decide +kernel 的计数是计算的词法代理指标，不是运行时测量。全库编译代价是一个按依赖顺序完成、排除了最吃内存的模块族的子集上的下限，本文没有把它外推到缺失的模块上。

工具

我们把这套流程整理成了开源命令行工具 ProofServe，0.1.0 版提供预编译的 Linux x86-64 安装包。proofserve check 用 Lean 自己的内核并行、可断点续跑地复查一个已编译的 Lean 项目，并生成一份回执，列出接受了哪些模块、这些模块声明了哪些公理；在我们的测试项目上，用 8 个工作进程时墙钟时间快了 1.7 到 2.1 倍，但总 CPU 开销更高。proofserve audit 报告默认构建漏掉了哪些源文件和哪些 decide +kernel 调用。README 说明了它的信任边界，包括默认设置为了速度而不与官方检查器完全一致的地方。六页的技术报告在这里。

把 GPU 服务的请求循环搬进内核，能省下 CPU 吗？

bpf-gpu-server 让 eBPF 和 iouring 接管 GPU 服务的 TCP 路径，稳态下没有任何用户态线程处理请求。和驱动同一个 GPU 执行器的高效 epoll 服务器相比，它的 CPU 消耗和延迟都与对照组持平。本文解释每个请求的开销到底花在哪里。
