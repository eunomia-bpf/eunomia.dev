在 Linux eBPF 中运行 Qwen3-0.6B：内核到底做了什么？

真实的 Qwen3-0.6B 前向计算已在 Linux eBPF 中运行。本文从零解释内核与用户态怎样分工、速度如何，以及 verifier、内存和数值限制怎样影响实现。

用 eBPF 观察模型服务，与让 eBPF 自己执行模型计算，是两件不同的事。qwen3-ebpf 探索的是后一件事：把真实 Qwen3-0.6B 模型的前向计算放进通过 Linux 内核验证的 BPF 程序。当前程序完成全部 28 层 decoder 计算、输出词表分数，并在内核里选出下一个 token；C 程序仍负责文本处理、模型加载和算子调度。

这不是一个新的高吞吐推理服务。减少调度和权重转换开销后，测试主机上探索性的单 token 运行仍需约一秒。实际服务模型应当使用成熟的 CPU 或 GPU 推理引擎。这个项目的价值在于验证另一件事：真实 Transformer 前向路径可以拆成内核 verifier 接受的有界整数算子，同时让我们看清这种边界的代价。

这里的“在 eBPF 中”是什么意思？

eBPF 允许向 Linux 内核加载受限程序。程序运行前，verifier 要检查执行是否有界、内存访问是否安全等性质。普通 C 进程可以自由组织的大循环和数据结构，放到 BPF 中就要换一种写法：界限必须让 verifier 看得见，单个程序也不能复杂到难以验证。

语言模型先把 token ID 变成向量，再通过多层 decoder 变换向量，最后给词表中的候选 token 打分。本项目让矩阵向量乘、RMSNorm、SiLU、RoPE 向量旋转、残差和门控运算、因果注意力在 eBPF 中执行；对最终 151,936 个词表分数求最大值的 argmax 也在 eBPF 中。驱动通过 bpf_prog_test_run_opts 运行这些 socket-filter 程序；程序不挂载网络接口，也没有安装常驻模型服务。

外围工作仍在用户态。C 驱动读取官方 BF16 Safetensors 权重，把当前需要的权重和激活转换成定点数，提供 RoPE 的三角函数输入，并按模型顺序调用 BPF 程序。另一个 C 模块根据单独提供的官方 tokenizer.json 完成 ByteLevel/BPE 分词，再把生成的 ID 解码为文本。权重没有整体常驻 BPF arena。因此这里的“内核内推理”指前向算术和下一个 token 的选择，不指完整的文本输入输出应用，更不意味着用户态和内核态之间没有切换。

一个 token 怎样走完整条路径？

分词之后，C 找到输入 token 的 embedding，并把工作向量放到可映射的 BPF map 中。每一层依次运行归一化、Q/K/V 投影、Q/K 归一化和 RoPE、读取历史 KV 的注意力、输出投影，以及门控 MLP。新算出的 K/V 向量进入可映射的 BPF 数组，供后续 token 复用。经过 28 层后，词表投影和 BPF argmax 给出下一个 ID。较长的提示词需要逐位置经过模型；继续生成时，KV cache 可避免重新计算以前位置的 K/V。

有界循环减少了驱动调用，但没有把模型变成一次内核调用。矩阵程序的一次 bpf_loop 最多计算 16 行；单个 RMSNorm 程序内的两段循环分别处理最多 8 个、每个 128 元素的 tile；注意力的一次循环最多扫描 256 个历史位置。不同矩阵批次、归一化调用和后续层仍由 C 依次调度。把矩阵批次从 4 行增至 16 行后，同一单 token 测试中的 bpf 系统调用数从 143,667 降至 50,667；归一化改成单次调用后，又降至 43,171。32 行矩阵实验版也能加载且输出一致，但单次计时没有显示进一步收益，因此保留了占用更小的 16 行工作 map。

为什么不把整套模型塞进一个 BPF 程序？

verifier 必须分析它接受的程序。早期 RMSNorm 把累加和带分支的整数平方根放在一起，在测试内核上超过了一百万条指令的处理预算。先拆成 accumulate、finalize、apply 三个 BPF 程序后，计算得以运行；当前版本再用有界的 bpf_loop 回调包住平方根步骤，在测试内核上通过了单程序验证。另一项尝试把 BF16 到 Q24 的转换放进 3,072 列的 BPF 循环，加载时遇到“The sequence of 8193 jumps is too complex”。这些是具体实现的实验结果，不是任何更大 BPF 设计都不可能的证明。

程序复杂度之外还有数据量。读取、转换 Qwen3-0.6B 的权重，再为每个 token 运行大量矩阵批次，会造成显著的数据移动。把工作 map 变成内存映射后，驱动不必每批都调用 map 更新和查询；把 BF16 模型文件只读映射一次后，也消除了旧版本中数十万次逐行文件 seek/read。BPF 程序目前只看到复制进共享工作 map 的活跃权重行，并不能直接读取整份模型文件。要让权重常驻 arena，还需要重新设计权重格式和加载过程。测试过的全量 Q24 格式把文件从 1.5 GB 扩大到 3.0 GB，而测试主机当时可用内存约 4.6 GiB；在证明收益之前就分配如此大的内核可访问内存，可能只是把转换成本换成内存压力。arena 改变寻址方式，不会自动压缩权重，或让 28 层变成一次调用。

文本处理还有另一种工作形态。准确分词需要解析大型 JSON 词表、使用正则切分和动态 BPE 结构，最后还要把 token ID 还原成字节。保留在 C 中，可以避免为这些输入输出任务额外承担 BPF 的验证和有界内存限制。即使将来把分词和解码移入内核，也需要独立实现和验证，而且不会消除最昂贵的稠密矩阵运算。顶层算子调度也是类似的边界。

精度和内存还有哪些限制？

BPF 中的计算使用定点数，而不是直接沿用模型的 BF16：激活采用 Q16，矩阵权重采用 Q24，RMSNorm 的 scale 采用 Q20。部分官方 scale 超出 Q24 可表达的范围，所以归一化不能直接使用同一格式。SiLU 和注意力 softmax 使用整数近似；C 提供位置相关的三角函数值，BPF 执行 RoPE 旋转。一次真实权重行实验表明，把点积简单换成 Q8，会在抵消较强的输入上产生明显误差。更小的量化格式必须经过全模型精度验证，不能只看文件大小。

权重准备本身耗时。当前实现用约 512 KiB 的查找表，将 BF16 位模式映射成 Q24 值，使活跃矩阵行不必反复做浮点转换。穷举测试覆盖全部 65,536 种位模式：可表示的有限值与原公式一致，非有限值和越界值被拒绝。三组交替进行的单 token 测试，查表路径用时 1.154/1.258/1.049 秒，修改前为 1.425/1.576/1.476 秒；全词表 logits 逐字节一致。这只是同机少量测试，不是稳定吞吐量结论。

另一种捷径是把所有二维 BF16 张量预转换成独立的 Q24 Safetensors 文件，但它没有带来加速。单 token logits 保持一致，文件却从约 1.5 GB 增至 3.0 GB；交替测试中预转换路径用时 5.18/3.93 秒，原 BF16 文件路径为 3.22/2.37 秒。当时主机可用内存约 4.6 GiB，缓存压力可能是原因之一，但未被单独证实。这个性能回退的版本没有保留。

打包存储的 INT4 权重更值得作为下一项实验，但现在还不能说它一定更快。每个权重用 4 bit，原始权重数据理论上只需 BF16 的四分之一；分组缩放系数和元数据会增加体积，embedding 或敏感矩阵也可能需要保留更高精度。合理的做法是预先打包权重，采用分组缩放，并实测 BPF 点积直接使用打包权重时，解包和缩放开销会不会抵消减少内存传输与 C 端转换的收益。此前 Q8 的问题来自一次简单的单行量化实验，不能用来证明经过校准的 INT4 可行或不可行。要把 INT4 设为默认格式，至少应对比全词表 logits、多种提示词的生成结果、verifier 是否接受、峰值内存和同机延迟。KV cache 占用与数万次 BPF 调用是另外两个瓶颈，单靠权重量化解决不了。

KV cache 通过内存映射的 BPF map 共享，不必在每个注意力步骤都经系统调用复制。当前布局每个位置预留约 224 KiB；若为模型配置的 40,960 个位置全部分配，仅 KV 就约需 8.75 GiB。现有测试没有验证完整长度的运行和生成质量。注意力使用 bpf_loop 按最多 256 个历史位置分段处理，但上下文增长带来的内存和计算开销依旧存在。

测试到底证明了什么？

在 Linux 6.17、arm64 主机上，BPF 程序通过了 verifier 和算子测试。使用官方模型及 tokenizer 时，文本 Hello, world! 被分成预期的 [9707, 11, 1879, 0]，随后生成 This（ID 1096）；词表分数最高的五个 ID 与官方 BF16 Transformers 参考结果一致，全词表 logit 平均绝对误差为 0.035。项目还比对了几个 token-ID 输入，以及一次复用 KV cache 生成第二个 token 的过程。验证确实穿过全部层与注意力，但样本仍少，不能推断普遍生成质量或任意长上下文的表现。

批处理让驱动调用更少：同一单 token 输入的一次 4 行批次测试用时 2.695 秒，16 行批次测试用时 1.605 秒，全词表 Q16 logits 逐字节一致。之后的查表改动缩短了权重准备时间，内核算术本身没有变；单程序 RMSNorm 则减少了系统调用，但在少量交替计时中没有显示明确的单 token 延迟收益。这些仍是零散观测，不是吞吐量分布。更准确的结论是：在 verifier 约束下，BPF 能承担真实模型算术；程序复杂度、调用次数、定点误差和内存布局则决定这条路线能走多远。

项目源码和验证记录 提供构建方法与实测数据；Qwen3-0.6B 官方仓库 给出模型配置；Linux verifier 文档 解释程序结构背后的安全约束。
