为什么一个 BPF 修改返回值的程序能让内核从未列入清单的函数失败，又是什么决定跳过它是否安全？

因为挂载规则正从一份手工维护的允许清单，变成构建期可以检查的性质。今天一个修改返回值的程序 只能挂到错误注入清单里的函数上，而那份清单来自显式的标记宏，或者挂到名字以 security 前缀开头 的函数上；其余一律被拒绝，报错为"该函数不可修改"。本周合入 BPF 树的一个系列把这一步换成构建期 扫描：打开新选项后，链接阶段那个给 BTF 打补丁的工具会读入链接后的机器码，找出所有返回寄存器 上可能出现错误码的函数，把这些错误码作为声明标签记在函数上。此后程序可以挂到任何带标签的函数 上，校验器要求它的返回值是 0（照常调用该函数）或该函数标签里的某个错误码（跳过调用，把错误 交给调用者）。决定"跳过是否安全"的并不是扫描，而是一条刻意写得很窄的规则：函数在返回这个错误 之前已经做了什么。如果通往该错误的每条路径都以"对函数自己收到的某个指针调用一个返回 void 的 函数"结束，这个错误就不作为目标开放，因为跳过会让那件工作没做。按作者自己的注入实验台，对一个 带标签的函数注入一次错误，大约每 180 个函数里有一个会损坏内核。

机制

  1. 现在的门禁是一份清单，不是一个证明。 校验器给修改返回值程序的挂载路径做判断：函数的地址 在错误注入表里，或者名字以安全钩子的前缀开头，就放行。这张表在内核初始化时从一个装载器段里 的标记填充而来：系统调用包装宏给每个系统调用符号放一个，少数子系统给自己关心的函数放一个， 模块在加载时贡献自己的。这解释了为什么声明出来的目标大约有 957 个系统调用入口、312 个安全 钩子，其余只有约 21 个，也解释了为什么这张表对"某个函数是否适合在此失败"一言不发。

  2. 跳过一次调用并不是函数失败。 蹦床把这个区别摆得很清楚。它依次运行每个修改返回值的程序， 把程序的返回值存到一个栈槽里，然后拿这个槽与零比较；非零就直接跳过对原函数的调用，直接进 fexit 程序。调用者随后把程序给的值当成函数的返回值。所以返回错误的程序并没有让函数失败， 它让函数从未运行，而调用者的清理路径作用在一个被调用者根本没碰过的对象上。

  3. 构建期到底找出什么。 扫描发生在 BTF 已经在被后处理的地方：调试信息经 pahole 生成 BTF 之后， 同一个 ELF 也交给这个打标签的工具，它用 LLVM 的 MC 层解码每个函数的机器码。反向数据流收集 能到达返回值寄存器的、落在 -4095..-1 区间的常量；正向的 may 分析再问：通往该返回的某条路径 是否没有经过例外规则所禁止的那类调用。结果是挂在函数上的一条声明标签，值是这些错误码排好序的 清单。

  4. 哪些常量算错误。 -512 及以下、以及 -EAGAIN、-EMSGSIZE、-EINPROGRESS 被丢掉：前一组 到不了用户空间，后一组是要调用者重试、继续或等待，而不是"这次调用失败了"。唯一常量是 -1 的函数完全不打标签，因为机器码分不清权限检查的 -EPERM、"没找到"的 -1 与比较器的 -1。 返回宽度决定剩下的部分：mov $0xffffffea,%eax 在 4 字节返回上是 -22，在 8 字节返回上是 4294967274，所以返回 long 的函数的错误必须符号扩展满整个寄存器。

  5. 哪些函数在扫描之前就被排除。 程序根本挂不上去的函数不打标签：BTF 必须说它返回 4 或 8 字节 的整数或枚举，恰好一个 ELF 符号用这个名字，参数至多十二个、每个至多十六字节、没有变参， 不在 init 段，入口上带着 ftrace 会改写的那条 nop 或对 __fentry__ 的调用（因此 notrace 函数被排除）。在作者自己的构建里，这个系列给 clang 编译的 x86-64 打了 12096 个标签，GCC 是 11432 个，arm64 是 10954 个；其中一个中间步骤的构建报告 78350 个函数里打了 12076 个标签， 而它扫描的 35445 个函数里没有一个解码失败。

  6. 例外规则针对的是副作用，不是错误本身。 规则是：如果一个错误的所有路径都以"对某个指针调用 返回 void 的函数"结束，而这个指针是函数的某个参数、或者是某个参数的成员地址（不是从它里面 载入的指针），那么这个错误不被允许。写成代码就是先解掉锁、放下引用、释放或初始化一个对象， 然后 return -EBUSY。从函数本身拿到 -EBUSY 的调用者知道工作已经做完；从被跳过的函数拿到 -EBUSY 的调用者会发现锁还持有着。工具在机器码里看到这一点，所以源码既不需要 __releases() 注解，也不需要名字清单。具体地，在系列自己的例子里，编译器发出：载入参数、 用 lea 取锁字段、调用一个 BTF 说返回 void 的函数、把 -EBUSY 搬进返回寄存器；-EBUSY 被去掉，而它又是这个函数唯一的错误，于是函数最后一个标签都没有。

  7. 校验器随后检查什么。 挂到带标签的函数上会为这个程序装上一条清单。在每个出口，程序的返回 寄存器必须是一个标量，其整个取值范围都落在"0 加上这条清单"里；检查针对范围而不是观测到的值， 所以一条可能产生未列入值的路径在加载时就失败。尾调用被直接拒绝，因为程序数组对后继程序返回 什么没有任何约束。目标返回 8 字节时，程序还要求 JIT，因为解释器只传出低 32 位，-14 这样的 值到调用者手里会变成 4294967282：非零，于是调用被跳过，而且也不是一个错误。目标返回 4 字节 时，只有当寄存器高半部分已知为零，才由 32 位范围来判定，这与这类函数的调用者实际读的位数一致。

  8. 标签在哪里被找到。 只搜索发起挂载的那个 BTF 对象自己的类型。一个模块可以用到内核 BTF 里 同名的函数，而内核里的标签对模块里那份副本什么都没说，因为那是不同的机器码。又因为构建会把 BTF 按名字排序，这些标签挨在一起，二分查找就能找到第一个。

验证方法

  1. 问运行中的内核打了哪些标签。 编入选项后，标签就是函数 FUNC 条目上的一条声明标签，原始 转储里直接可见。真正有意思的是"返回错误却没有标签"的函数：先核对第 4 到第 6 步的规则，再判断 是不是缺陷。

    标签的 type_id 就是它所描述的那个 FUNC 条目，按这个编号再转储一次就得到函数名。

  2. 问未打补丁的内核接受哪些函数。 旧的门禁不需要重建内核就能观测：打开函数级错误注入后， 这张表通过 debugfs 导出，每个标记一行，带地址和标记声明的那种错误类型。

  3. 读拒绝信息，而不是猜。 目标既不在表里、名字也不带安全前缀的程序，加载失败的消息里会写出 函数名；返回值范围越出清单的程序，加载失败时会把清单本身打印在日志里。两种错误分别告诉你 违反了契约的哪一半。

  4. 预期 BTF 类型编号会移动。 这些标签是 vmlinux BTF 里的新类型，所以第一个标签之后的所有编号 都会位移。系列自带一个例子：某个 helper 的编号从 95497 变成 106933，弄坏了一个按固定列宽匹配 日志的自测。任何跨"选项开与关"硬编码 BTF 编号的代码，依赖的是巧合而不是接口。

  5. 先核对蹦床的契约，再怀疑程序。 是否跳过，是在生成的蹦床里、原调用之前、拿程序的返回值与 零比较决定的。如果一个程序看起来运行了而函数的副作用缺失，该看的就是这次比较；fexit 程序 事后读的也是同一个栈槽。

边界

  • 这在 BPF 树里，不在发行版里。 这个系列在本文当天被合入 BPF 的 next 树；选项没有默认值， 不在 defconfig 里，主线还没有。标签格式与这些数字都应当读成提案当前的形状。

  • 损坏率是一次测量，不是保证。 对 net、fs、mm 的 4401 个函数各注入一次错误，工作负载是 530 个 测试与脚本、大部分是自测：50 例以 panic、oops、BUG()、挂死或 lockdep 报告结束，例外规则去掉 其中 27 例。全部 8027 次注入中，48% 只给用户空间一个错误，50% 什么都没给。作者明确说这条规则 不追求完全安全。

  • 例外规则刻意写窄，仍留下约 114 个会造成损坏的函数。 四轮里共有 169 个函数损坏过内核，例外 规则拿掉其中 55 个，剩下的留给一份不在本系列里的按名字维护的拒绝清单。清理动作经过一个返回 值的函数时，标签会保留，因为那次调用本身可能就是失败的那一次。

  • 有标签不等于这次失败无害。 一个函数可以合法地返回错误，却仍不适合对某个特定调用者跳过： 让调用者本以为会成功的调用失败，就是功能损失，而标签看不到这一点。这既是声明的目的，也是声明 的风险。

  • 代价与覆盖面。 构建主机无论用什么编译器编内核，都需要 C++17 编译器与 LLVM 17 或更新版本的 头文件和库；选项只覆盖 x86-64 与 arm64；vmlinux 的 BTF 增长约 2.8%；pahole 用掉 4.3 秒之后， 工具在 vmlinux 上的时间从 0.31 秒变成 0.9 秒。

今天的社区讨论

本次运行通过批准的只读归档查看了两个加入制的工作区，共三个允许频道，并用可见浏览器读了公开的 bpf 邮件列表和一个实践者论坛。归档在严格意义上为空：24 小时窗口内没有消息，七天窗口里一个工作区 有十条、另一个没有，全是某次会议维护者聚会与同地活动上项目演讲的日程，其中一条提到有第三方把 网络追踪与持续采样剖面结合起来做威胁检测。没有一条是技术提问，所以上面的回答来自邮件列表—— 它当天窗口里有 31 个新线程根。四个允许清单里的聊天工作区完全读不到：两个 Discord 邀请只会打开 一个只有成员数的加入表单，没有任何频道内容；两个 Slack 邀请打开的是接受邀请的页面。因此四个都 记为"不可访问"而不是"安静"。论坛可读，但它最新的帖子是公告（18 小时前的一份征稿、18 天前的 一个大会页面），最新的技术帖已是七天前；其中两篇放在最后一段，用来说明用户到底卡在哪里。

被回答的那个系列，以及真正起作用的规则

这个修改返回值系列里有意思的不是扫描而是例外，因为扫描是个数据流技巧，而例外是关于内核编程的一句 判断。它要防的失败很具体：一个函数在错误路径上解掉锁然后返回错误，于是从"跳过"里拿到这个错误的 调用者发现锁还被持有，下一次解锁下溢、或下一次加锁死锁。工具只靠机器码就判定出来了——对参数某个 成员取 lea、调用一个 BTF 说返回 void 且收指针的函数、然后搬常量进返回寄存器——既不需要源码注解 也不需要名字清单，这正是"审阅者能审计的规则"与"会腐烂的清单"之间的差别。仍然开着的，是例外之后 剩下什么：作者自己的几轮运行留下约 114 个会造成损坏的函数，等一份按名字的拒绝清单；而例外声明的 盲区，是清理动作经过一个返回值的函数，此时"跳过"看起来真的很像"失败"。

没人需要的宽限期

另一个线程主张 BPF 链接聚合器在每次挂载时都等一个完整的 RCU 宽限期，包括对刚建好的设备的第一次 挂载，而这个等待发生在网络配置锁内部，于是批量创建容器会把整台机器的控制面排在每设备两个宽限期 之后。审阅者的回复是对前提的有益纠正：宽限期保护的是前一个条目而不是新条目，所以修法不是删掉它， 而是借用同一个钩子里队列规则那部分已经在用的方案——交换之后启动一个宽限期，下次写回旧缓冲区之前 再等；新的 bundle 从一个"尚未完成"的标记开始，因此第一次挂载什么都不用等。据其表格，这样一来 首次挂载的等待消失，队列规则先挂过之后的第二个程序也不再等待，其余情形缩到"上一次变更不到一个 宽限期"才等。教训可以推广：当一个系列声称某个等待不必要时，先看清它保护的是对象的哪一代。

一个按子系统拆的互斥锁，以及支撑它的数字

一个已被合入的系列把 cgroup 的 BPF 状态从全局 cgroup 互斥锁上挪开。它的动机值得当作"如何论证 拆锁"的范式保存：来自一个机群的每日挂起任务计数——上千台主机卡在程序查询路径、数十台卡在链接 信息、数百台卡在释放工作，而持锁者几乎总是卡在兄弟锁上的目录创建或删除。拆开之后 BPF 状态有了 自己的互斥锁，attach、detach、replace 仍留在全局锁下因为要遍历后代，同时修掉了新锁暴露出的两个 顺序缺陷：读到一个已经释放的有效数组，以及往一个正在被删除的 cgroup 上挂载。当性能系列带着每台 主机的真实停顿计数到来时，评审的讨论通常就落在正确性上，而不是"问题是否真实"。

一个上报的宽度与产生的宽度不一致的上下文字段

一个已合入的修复关掉了套接字缓冲区上下文字段上的校验器模型不符。远程端口的转换载入 16 位成员， 在小端上把它移到 32 位寄存器的高半部分；它通过通用 helper 上报的宽度却是成员的两个字节，于是 两字节读被归类为"对两字节字段的更窄访问"，那条用左移加掩码把窄读加宽的步骤被跳过。校验器于是 相信值至多为 0xffff，而寄存器里是 0xffff0000 加上端口号，把校验器折叠成常量的算术变成相对 map 值的越界访问。修复只有一行意图：上报转换真正产生的宽度。值得留下的诊断习惯是，拿上报的宽度 比对转换真正发出的指令，因为这两样东西住在不同文件里，没有任何机制检查它们一致。

补丁是对的，缺陷却不在那里

窗口里有两个线程是同一形状的不同尺寸。一个主张对绝对包载入的地址做掩码，理由是短暂越界的偏移 可能解引用到秘密；它被驳回，理由是经典绝对载入的转换在回退到 helper 之前的快速路径里已经内联了 自己的边界检查，于是这个补丁不改变任何可观测行为。另一个是同一分歧的窄版本，报告者的证据来自 一个在分支前插入了缓存刷新指令的"被插桩"内核，审阅者的回答是没人跑那样的内核。两者都提醒：被 评审的对象是转换之后的程序，不是作者写下的程序。

开头同一个帧出现两次的调用链

一个三补丁系列修掉 arm64 内核调用链里重复的调用者帧，并给构造这些调用链的路径加了自测。机制是： 捕获调用者寄存器的 helper 把程序计数器设成调用者的返回地址，却把帧记录寄存器指向当前函数自己的 记录，而那条记录里保存的链接寄存器正是同一个返回地址；栈展开器于是先报程序计数器，再展开到重复 的那一帧。修复改用调用者的帧记录，也就是展开器自己的初始化本来就在用的做法，而 x86-64 上同样的 缺陷多年前已经修过。它直接影响 BPF 用户：tracepoint、原始 tracepoint、带类型的 tracepoint 与 fentry 程序里的栈 helper 都走这条捕获路径，所以重复出现在采集到的栈顶，而不是 perf 的某个角落。

与校验器脱节的文档

窗口末尾是两份文档补丁和一处编码器修复。文档补丁记下一件在校验器里存在多年却从没写下来的约束： 套接字 map 的修改限制——只有迭代器追踪、sock-ops 的删除、reuseport 与 socket-lookup 程序可以 更新或删除，其余一律以具名错误拒绝。编码器修复则是对本周早些时候报告的一个缺陷的直接跟进：被 标记为内核函数的那些函数现在豁免于会把它们从 BTF 里丢掉的位置列表检查，并且在每次编码 BTF 时都 被收集，而不是只在一个特性开关下收集，于是两个丢失的函数回来了，blob 的其他部分没有任何变化。 两者都属于便宜的那类修复：缺口在代码与文字之间，或在同一次构建的两个阶段之间。

内核列表之外的实践者在问什么

论坛近期的技术帖有两种反复出现的形状。第一种是"没有签名的强制"：一个项目拦截某个非特权进程的 文件、网络与执行操作，学习正常行为的基线，然后必须决定如何反应而不把主机弄坏——它明确不去碰 SSH 会话与服务管理器，就是这个原因。第二种是入门曲线：一个研究生级别的问题想要一条从追踪工具走到 "自己写程序对付一个隐蔽的内核植入物"的路径，而这个问题里有用的部分，是提问者意识到真正吃时间的 是校验器与类型格式的报错，而不是钩子机制。两者都没有窄到可以在这里作答，也都不带读者需要的身份 或部署细节。

为什么 i386 上的有符号除法与符号扩展搬移会算成无符号结果，又怎么越过校验器证明的范围？

因为 BPF 指令集用 off 字段来选中三条指令，而 32 位 x86 JIT 只按操作码决定要发射哪条指令。 有符号除法与有符号取模是 DIV、MOD 配 off = 1；符号扩展搬移是 MOV 配 8、16 或 32 的 偏移。解释器按这个偏移分派，校验器按它推导范围，x86-64、arm64、RISC-V 与 s390 的 JIT 也都按 它分支，但 i386 的发射函数只拿到操作码，于是发出一条普通的 div
