为什么 i386 上的有符号除法与符号扩展搬移会算成无符号结果，又怎么越过校验器证明的范围？

因为 BPF 指令集用 off 字段来选中三条指令，而 32 位 x86 JIT 只按操作码决定要发射哪条指令。 有符号除法与有符号取模是 DIV、MOD 配 off = 1；符号扩展搬移是 MOV 配 8、16 或 32 的 偏移。解释器按这个偏移分派，校验器按它推导范围，x86-64、arm64、RISC-V 与 s390 的 JIT 也都按 它分支，但 i386 的发射函数只拿到操作码，于是发出一条普通的 div 和一次普通搬移。结果就是： 一个通过校验的程序拿到被它自己的范围证明排除在外的值——w0 = -1; w0 s/= 2 得到 0x7fffffff 而不是 0，r0 = (s8)0x80 得到 128 而不是 -128。这个缺口本身还不是校验器绕过； 当程序把这个值当作边界使用时它才成为绕过，这也正是它值得被检出的原因。

机制

  1. 偏移就是操作码的扩展位。 指令集文档说得很直接：只有 SDIV、SMOD 与 MOVSX 带非零 偏移，而偏移正是 dst s/ src 与 dst / src 的区别、符号扩展搬移与普通搬移的区别。解释器 把它实现为 ALU_MOV_X、ALU_DIV_X、ALU_MOD_X 以及对应 ALU64 分支里的 switch (OFF)， 所以这个偏移对执行是承重的，不是提示。

  2. 校验器的证明也建立在同一个字段上。 check_alu_fields 对 DIV、MOD 只接受 0 或 1， 对 32 位 MOV 的寄存器形式接受 0、8、16，对 64 位接受 0、8、16、32。范围推导随后按它分支： off == 1 时除法走有符号范围辅助函数，搬移走符号扩展的收窄函数。对 -1 s/ 2，辅助函数算 出 res1 = -1 / 2、res2 = -1 / 2，于是目标寄存器被证明恰好是 0。这就是接下来 JIT 被要求 兑现的那个范围。

  3. JIT 家族的分界线在"在哪里读偏移"。 x86-64 的发射器既在常量除数的强度削减里按 insn->off == 1 分支，也在寄存器路径里按它分支：off == 0 发 xor edx, edx 加 div，另一 支发 cdq 或 cqo 加 idiv；带非零偏移的寄存器搬移交给符号扩展搬移的发射函数。arm64 发 SDIV，RISC-V 发 divw/remw，s390 发 dsgfr/dsgr，parisc 则走 libgcc 的有符号辅助 函数，全部以 off == 1 为键。也就是说，凡是实现了它的架构都认识这个机制。

  4. i386 的辅助函数看不到指令。 emit_ia32_div_mod_r 接收一个操作字节、目标、源和两个栈标 志，调用方传的是 BPF_OP(code)。它装载操作数后无条件发 xor edx, edx 与 div ecx，因为 32 位无符号除法只需要这一种形式。MOV 的情形一样：BPF_ALU | BPF_MOV | BPF_X 与 BPF_ALU64 | BPF_MOV | BPF_X 走的是普通搬移的辅助函数，它接收 is64 却不接收 off。两条 路径都没有读过 insn->off。

  5. 只有 32 位的有符号除法被编错，因为 64 位的根本到不了 JIT。 i386 发射器把 BPF_ALU64 | BPF_DIV 与 BPF_ALU64 | BPF_MOD 送到它的"尚未支持"标签，返回 -EFAULT，编译 循环于是把程序原样返回、不做 JIT。编译失败会退回解释器，除非程序必须 JIT——内核编译成 JIT 常开，或者程序本身需要它，例如使用 arena，或子程序返回一对寄存器。因此在 i386 上，64 位除 法慢但正确。带 off = 1 的 32 位除法命中 BPF_ALU 分支，被当成无符号发射；32 位与 64 位的 有符号搬移都被当成普通搬移。危险形态正是这一种：JIT 接受了这条指令，却编错了，而不是拒绝。

  6. "越出证明范围"能换来什么。 校验器只知道它证明过的东西，因此之后每一个建立在该范围上的 检查都不再可靠。辅助函数的参数长度是最典型的例子：如果程序用 32 位有符号除法或符号扩展算 出长度，校验器可能证明这个长度非负且很小，而实际发射的代码产出 0x7fffffff，随后那次长度 检查是程序在校验器模型里本来就已通过的一次检查。该系列报告的就是这个：在未打补丁的 i386 内 核上，三个通过校验的测试程序给辅助函数传入了超出证明界限的长度，辅助函数按那个长度写了相 应字节数。

  7. 修复比缺陷的类别小得多。 提交的系列在两个发射函数内部读 insn->off：off == 1 时发 cdq 与 idiv 取代 xor/div；搬移时对 8 位与 16 位发 movsx，对 32 位用 cdq 提供高 半字，64 位情形填上高半字，32 位情形在校验器没有插入零扩展时把高半字清零。它刻意不新增任 何指令支持，这就是它小的原因。

  8. 这里的 idiv 不会陷入，也正因如此修复才能这么简单。 让裸 idiv 不安全的有两个例外： 除数为零，以及 INT_MIN / -1（或 LLONG_MIN）时商装不下。两者都在 JIT 之前被去掉：有符号 运算上的常量 -1 除数被改写成取负或清零，寄存器形式则被包进一个检查，把除数为零变成 0、 把最小数除以 -1 变成最小数本身。解释器依赖的也是这个前提。

如何验证

  1. 先从规范确认偏移语义。 读指令集文档里的算术表：SDIV 与 SMOD 标的偏移是 1，MOVSX 是 8、16 或 32，其余算术条目都是 0。没有这一步，"JIT 忽略偏移"就只是在断言一个看起来可选 的字段。

  2. 把两个发射函数并排读。 在 32 位 x86 JIT 里找到除法辅助函数，看它的参数表：如果里面没 有指令指针，它就不可能按偏移分支。再找 64 位 x86 发射器的除法分支，注意那个把 xor/div 与 cdq/idiv 分开的 if (insn->off == 0)。两个文件的差别就是整个缺陷。

  3. 跑 selftest，而不是自己写一个合成程序。 指令遍历测试里有一个 movsx 子测试，把 JIT 的 输出与各符号扩展宽度的期望值做比较；校验器自带的有符号除法与符号扩展测试覆盖范围检查。在 32 位 x86 内核上，指令遍历的六个子测试、盲化遍历的四个、以及五十个有符号除法用例会失败； 符号扩展那个补丁清掉五个符号扩展的校验器用例。剩下六个遍历失败在没打这个系列时也照样失败。

  4. 对在跑的机群，比对解释器与 JIT。 这不需要读源码，也不需要编 selftest：在 32 位 x86 主机 上，用同一个带 s/= 与 (s8) 转换的程序，分别在关掉和打开 JIT 时运行，比较结果。出现差异 就是缺陷；差异的大小则说明这个值是否被当成边界使用。

  5. 判断某个内核是否带上修复。 两个发射函数都很小、修复也很局部，所以可靠的检查是看代码树 而不是发行版号：在 32 位发射器的除法辅助函数里搜 cdq 的机器码（0x99），在搬移辅助函数 里搜 movsx 形式。辅助函数仍然硬写 xor edx, edx 的内核，早于这个系列。

局限

  • 该系列尚未合并。它以 bpf 树的修复形式提交并带两个 Fixes 标签，patchwork 状态是 new。请把它 读作预期形态；引用它读取的偏移值之前，重新核对补丁。

  • 这个编错只发生在 i386，而 i386 是一个在收缩的目标。系列讨论里记录了"32 位 JIT 还该不该继续 接活"这个问题。读这个结果的有用方式是缺陷类别而不是架构：一条指令的含义住在它编码的某一个 字段里，而分派时看的偏偏不是那个字段。

  • 偏移为 0 的普通 MOV，和校验器处理过之后的普通 MOV 不是一回事。校验器会给某些 32 位定义 打上"需要零扩展"的标记，32 位 x86 JIT 用一条立即数为 1 的 MOV 来回应这个标记。在发射器里 grep 搬移分支的读者会先看到这个特殊形式，把它误当成缺失的符号扩展。

  • i386 上的 ALU64 除法正确，但没有 JIT。需要它的程序要付解释器的代价，因此在 i386 上测出的 性能结果混了 JIT 与解释器，不能与 64 位内核上的结果相比。

  • 本页的判定来自源码与 selftest 断言，而不是本地加载。写这页的环境能编译，但内核关了非特权 BPF、进程也没有 CAP_BPF，所以无法加载程序直接观察差异。第 4 条里的复现路径，要拿到能加载 程序的主机上跑。

今日社区讨论

本次运行通过批准的只读归档读了两个聊天空间、共三个允许频道，并把公开的 bpf 邮件列表作为第二 个公开面。归档是安静的：一个空间在 24 小时与七天窗口内都没有消息，另一个七天窗口内十条、最近 24 小时没有。十条全是某次会议维护者聚会与同场活动上项目演讲的安排，外加一条提到第三方把网络 追踪与连续 profile 结合起来做威胁检测。它们都不构成技术问题，所以上面的回答取自今天窗口内的公 开列表线程；读取时该列表的滚动索引在窗口内显示 19 个线程根、49 条消息。有三个面完全无法覆盖， 记为不可访问而不是安静：两个聊天空间（合计十个允许频道）的公开邀请都返回"邀请无效"页面，从业 者论坛则用人类验证页拦住了普通浏览器会话。

用偏移字段选中的指令，是今天反复出现的缺陷

窗口内有两个线程是同一个形状。被回答的 i386 系列修的是两条 JIT 已经接受、但编错了的指令。它的 后续在几小时后发到 PA-RISC，发现该架构的两个 JIT 都把符号扩展搬移发成普通搬移，于是各自补上扩 展，并把 32 位那一半的发现归功于对更早一个"有符号除法"系列的自动审阅。那个更早的系列其实已经 让同一个缺口的除法与取模部分在两个 PA-RISC JIT 上工作起来，所以这个模式在一个架构内部重演了： 先修好那两条除法，漏掉了同样由这个字段选中、但在别处读取的搬移。机制自始至终相同：解释器按偏移 分派，校验器按它证明范围，而只按操作码分派的 JIT 悄悄发出另一条指令。实用的诊断规则可以推广到 任何移植：在 JIT 里 grep 读取偏移的地方，如果发射函数的签名里没有指令指针，它就读不到偏移。真 正还开着的不是某个单独缺陷，而是覆盖审计：校验器不会拒绝一个编错的 JIT，所以一个移植的正确性， 最终靠它自己的 selftest 遍历。

当"边界修复"其实已经在别处

一个提案主张对转换后的绝对报文加载做地址掩码，理由是一次瞬时越界的偏移可能解引用到秘密。回复是 干脆的拒绝：报告者大概没有复现，因为补丁什么也没改变——经典绝对加载在转换时，快路径里已经内联 了自己的边界检查，然后才轮到辅助函数兜底。这个推理在一个函数里就能核对：快路径把剩余包头长度与 访问大小相比，越界就跳过加载；辅助函数返回负值时，转换后的程序把它变成零。结论是流程性的，而且 值得记住：当一个补丁声称某次加载会离开允许范围时，要读生成程序的那段转换，而不是作者写的那段 程序。

为本来就不该可挂载的函数做返回失败

一份大型提交把内核里每个会返回错误的函数都标成修改返回值的目标，共 12633 个，于是持有两个 BPF 能力的程序可以在通往缺陷的调用上让它失败，并返回该函数自己的某个错误。设计功夫在规则里：一个函 数只有在其所有错误本来就能被调用者收到时才合格；而如果通往某个 return 的每条路径都用函数收到 的某个指针释放了东西，这个错误就被排除，因为跳过该函数会留下被占有的资源。实测结论很直白：在 网络中、文件系统与内存子系统的 4401 个函数上每个函数跳过一次调用，每 180 个函数里有一个会损坏 内核，这就是提案按名字维护一份拒绝清单的原因。审阅中作者同意去掉 537 个根本无法挂载的函数标签， 因为校验器会拒绝任何对它们的挂载。还开着的边界是：按返回值的数据流打标签能否完备，以及拒绝清单 如何在代码树移动中维护。

让每个属主的值少一次加载

一份请求意见的系列提出一个 map 标志，把本地存储的值放进属主自己的存储对象，而不是单独的 element， 从而在属主冷的时候每次查找少一次依赖加载。数字把取舍摆了出来：内联区是存储结构末尾的 840 字节， 64 位内核上最大的值是 832 字节，每种属主类型最多十六个内联 map，map 创建按首次适配领取槽位，失败 时返回"空间不足"或"参数过大"。对实践者来说有意思的是正确性部分：固定偏移上的值可能比认领它的 map 活得更久，所以每个槽位带一个取自认领编号的标签，并用 acquire 加载来比较；能持有内联值的对象 活到属主死亡，并在 tasks-trace 宽限期之后释放；存储迭代器拒绝内联 map；不可屏蔽上下文里的删除 返回"不支持"，与普通 map 一样。另外两件小事随行：该标志需要 64 位内核；库不再在缺少类型信息时 重试创建存储 map，因为那次重试一直失败，还掩盖了真正的错误。

一个读过给定缓冲区末尾的 dump 辅助函数

一个库修复关掉了类型 dumper 里的越界读。判断"整个值是否为零"的扫描会递归进结构体成员与数组元素， 却不检查调用者给的数据末尾，于是传入小于类型大小的调用者会走过缓冲区末尾，而不是拿到接口承诺的 "数据太大"错误。修复把 dump 路径本来就会做的溢出检查放到零值扫描的入口，并把数组分支里直接比较 字节的做法换成现在受检查的元素递归。它加的测试才是关键部分：一个全零 union 以比类型小一字节的大 小传入，必须返回错误而不是读取。残留的边界是：检查是按每次递归做的，将来若新增一条不经过受检入 口的递归，缺陷就会回来。

一个无处安放的类型标签

一个让 per-CPU 注解不再打到变量声明上的请求，建立在一个结构性事实上：聚合类型的每个变体共享同 一个调试条目，所以声明上没有地方安放逐变量的类型标签，而编译器对这个位置的处理并不一致——一个静 默丢弃，一个告警。审阅者在两个编译器上确认了效果，并要求删掉一句容易误解的话；量化收益是内核镜像 里少了 280 个类型、约 3 KB 类型信息。还开着的问题是标签是否该放到指针使用点上，那才是读 per-CPU 访问的人真正需要知道的位置。

一个会被重入探针覆盖的私有栈

一份早先系列的修订缩小了拿到私有栈的程序范围，理由是私有栈按程序和按 CPU 共享，所以普通内核探针 或用户探针被抢占的那次调用，其栈会被抢占它的那次调用覆盖。当前代码树给所有探针、tracepoint 与 perf-event 程序都配了私有栈；补丁只保留给 multi 与 session 这两种附加形式，因为它们的附加类型本身 就说明可能递归，并新增覆盖确认没有标签的形式拿不到私有栈。审阅中作者要求给这个改动加 stable 标 签，因为一个原本有保护、现在失去保护的程序，行为是变了的。值得记住的是缺陷的形状：一项以"资源在 每个 CPU 上独占"为前提的优化，被一个能在同一个 CPU 上重入的程序类别推翻。

回调帧，再修订一次

本站昨天的问题就是"回调参数活得比拥有它的帧更久"，回答它的系列在这个窗口里被 rebase 到了当前代码 树。修订保持设计不变，只改记账：把早先清理回调寄存器设置的工作并进来，在 join 路径里配对帧标识 符，使两个被 join 的状态不会对"哪个帧拥有这个参数"产生分歧，并为这个配对加了测试，同时丢掉了 Fixes 标签与 stable 请求。丢掉修复标签是个有意思的编辑选择：缺陷允许用保存下来的指针做任意内核 读写，但改动足够大，作者不再把它当作回移候选。

同一窗口里较小的事项

两个网络系列——一个重排设备设置顺序，让程序支持性检查发生在任何状态变更之前并在出错时回滚；一个 给虚拟接收队列加界——各自收到同一封自动请求，问缺陷是被触发的还是只从代码里读出来的；这封请求 明说判断由模型做出、可能出错。两件在技术实质而非流程上被回答的事，都取决于读"实际运行的代码"而不 是"写出来的代码"：一条已经自带边界检查的转换路径，和一个安放不到聚合类型上的 per-CPU 注解。
