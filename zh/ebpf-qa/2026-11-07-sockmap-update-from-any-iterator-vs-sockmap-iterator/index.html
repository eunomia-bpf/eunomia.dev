为什么校验器允许任何 BPF 迭代器程序更新 sockmap，而实际上只有 sockmap 迭代器是安全的？

因为校验器在加载时只回答一次这个问题，依据是程序类型和期望的挂载类型。对任何期望挂载类型是迭代器的 tracing 程序，may_update_sockmap() 都返回真，而函数上方的注释写明了让这种宽松成立的前提：这些上下文里的程序"拿不到一个已加锁的 struct sock"。这个前提说的是锁上下文，不是程序类型，而两者后来不再一致。迭代器交给程序的套接字，可能正被同一个任务持锁，也可能没上锁但正处于状态转换之中；而更新路径会拿一把不检查归属的自旋锁、分配一个套接字私有的状态对象、改写套接字的协议回调。上游正在评审的回应是：把校验器的门槛收窄到唯一同时保证这两件事的那种迭代器——套接字本身就是 sockmap 的成员，而且迭代器不持有它的锁。

机制

  1. 决定在哪里做出。 对 SOCKMAP 或 SOCKHASH 类型的 map，校验器只接受一张固定的辅助函数清单，其中 map_update_elem 与 map_delete_elem 必须经过 may_update_sockmap() 才被放行。这个函数检查两件事：解析后的程序类型是 BPF_PROG_TYPE_TRACING，且期望挂载类型是迭代器。它从不看程序挂到哪一个迭代器上，所以通过检查的集合是"全部"。注释记录了原因：作者认为没有哪个迭代器能够触到一个锁已被持有的套接字。

  2. 一次更新在运行期到底做了什么。 更新不是一次指针赋值。sock_map_update_elem() 先确认这是一个完整套接字、且其协议带 psock 更新钩子，然后关下半部并调用 bh_lock_sock()——那只是套接字锁字上的一次普通 spin_lock()，不检查归属——再检查套接字状态，然后进入公共路径。该路径用 GFP_ATOMIC 分配一个 link 对象，调用 sock_map_link()（在套接字的 callback 锁下可能分配并安装一个新的 psock），最后调用协议的 psock 更新钩子。对流式 Unix 套接字，这个钩子会读 peer 指针并给它加引用。于是一次辅助函数调用就改变了套接字的协议、回调和 peer 引用计数，而它的报文处理可能正在运行。

  3. "没有已加锁套接字"这个前提为什么失效。 Unix 迭代器原先在 lock_sock_fast() 之下运行程序。在快路径上，这个函数让套接字的自旋锁保持持有、下半部保持关闭，而归属标志仍是清零的。更新路径随后通过 bh_lock_sock() 去拿同一把自旋锁，而 spin_lock() 不可重入，任务于是在自己已经持有的锁上自旋。内核把它报告为可能的递归加锁，同一个套接字锁同时列在"已持有"和"正在申请"两处，任务永远读不完这个迭代器文件。修复把迭代器改成慢路径的 lock_sock()，它在置好归属标志后释放自旋锁；并在运行程序期间额外加上 Unix 状态锁，使更新路径的钩子读 peer 指针时它不会被并发释放。

  4. 为什么答案仍然是"只有 sockmap 迭代器"。 这两处修复让 Unix 迭代器能活下来，但并没有让每个迭代器都成为修改 sockmap 的正当位置。评审线程里给出了通用问题：来自不持套接字锁的上下文的更新，对套接字没有独占访问权，而 bh_lock_sock() 明确不管套接字是否已被某个任务持有。基于文件的迭代器可以把从文件描述符取出的套接字交给程序，既没锁，也不保证状态。sockmap 迭代器在两点上具体不同：它交出的套接字本来就是 map 成员，因此已有 psock、也已处于更新所接受的状态；它只在程序周围持 RCU 读锁，不持套接字锁，所以更新自己的自旋锁是第一次获取，而不是嵌套获取。

  5. 同一条边界也出现在 destroy 的 kfunc 上。 bpf_sock_destroy() 注册给 tracing 程序，并被过滤成只在期望挂载类型为迭代器时可调用。它的 TCP 实现用"当前是否有 BPF 程序在运行"来决定是否去拿套接字锁：在 BPF 上下文里它假定调用方已经持锁，注释里也这么写。这个假定对 TCP 和 UDP 迭代器成立——它们在运行程序前先锁套接字——对 sockmap 迭代器则不成立。因此同一系列用 BTF id 把这个 kfunc 限制到 TCP 与 UDP 迭代器，并且在完成这一限制之后的那一个补丁里，才把 sockmap 迭代器的套接字指针标记为 trusted。标记 trusted 正是让该上下文里的普通指针能被传给辅助函数的前提，所以先做这一步会重新打开限制刚关上的口子。

  6. 为什么门槛按名字而不是按标志判断。 该补丁把挂载函数名去掉迭代器前缀后与 sockmap 目标的字符串比较；作者注明先试过用 BTF id 集合，因为单元素列表需要写配置条件判断而放弃。名字正是迭代器机制本身用来把程序绑定到目标的键，所以这个检查与挂载的工作方式一致；代价是这个门槛继承了迭代器识别"以字符串为键"的性质。

验证与排障路径

  1. 看判定，不看意图。 把同一段程序体加载两次：一次放在 iter/sockmap 段，一次放在 iter/unix 段，都带一个 SOCKMAP map 和一次 bpf_map_update_elem() 调用。在没有这项限制的内核上两者都能加载；该领域的树内自测正是这样成对存在的，sockmap 那一例期望成功，打上补丁后 Unix 那一例期望以"不能在此上下文更新"的消息失败。

  2. 找出你所用迭代器的锁上下文。 读内核里该迭代器的 show 回调。如果它在运行程序前调用 lock_sock()，程序就是在套接字被当前任务持有的情况下运行；如果它只拿 RCU 读锁（sockmap 迭代器如此），就没有持有。这一处差别决定了在旧内核上更新的自旋锁是首次获取还是嵌套获取，也决定了你即将引用的 peer 指针是否受保护。

  3. 认出两种失败特征。 锁路径造成的死锁表现为可能的递归加锁报告，同一个套接字锁出现两次，栈里是迭代器的快锁函数，紧跟着就是更新路径。状态竞态则表现为 Unix psock 更新钩子里的 slab use-after-free，从 map 更新经 link 步骤到达，释放来自并发的 close。前者是锁嵌套缺陷，后者是生命周期缺陷，需要不同的修复。

  4. 确认你的程序对交出的套接字究竟能做什么。 导出该迭代器函数的 vmlinux BTF，看上下文参数的类型，再查其中哪些对你的程序类型标记为 trusted。未标记 trusted 的指针不能交给期望它的辅助函数，这正是"标记 trusted"与"限制辅助函数"必须以这个顺序落地。

  5. 不要从"加载成功"推断运行期契约。 能加载只证明校验器那层粗粒度检查通过了。把你这次更新可能来自的上下文全部列出来，凡是不给套接字加锁、或者交出的套接字本不在 map 中的上下文，都当作不受支持。

局限

  • 这项限制是评审中的补丁，不是已发布的行为。在当前发布内核上，更新仍然能从任何迭代器通过校验，所以今天能用的程序，可能在带这项收窄的内核上开始加载失败。固定你测试用的内核，并把校验器的消息当作与版本相关的信息。
  • 收窄到一种迭代器并不让 sockmap 更新变便宜或免锁。更新仍然要分配、要拿 map 的自旋锁和套接字的 callback 锁、仍运行在迭代器的 RCU 读区内无法睡眠，所以它是应当低频发生的控制路径操作。
  • 门槛以挂载函数名为键，也就继承了所有"以名字为键"的绑定方式的脆弱性：目标改名、或程序经另一条以别的名字绑定的路径挂载，判定依据都是那个字符串，而不是检查本来想表达的性质。
  • destroy 的 kfunc 保留着自己独立的限制，只到 TCP 与 UDP 迭代器，因为它需要调用方持锁。两项限制彼此独立，后续改动中可能各自漂移。
  • 这些都没有让来自迭代器的更新对套接字数据路径变成原子的；它只是让套接字的状态转换在被允许启动它的上下文里是安全的。

当日社区讨论

本次运行检查了六个白名单来源。其中两个是通过已批准的只读归档访问的 Slack 工作区，合计覆盖三个白名单频道；两者都可读，一个在 24 小时窗口内没有消息，另一个 24 小时内没有消息、七天内有一条。内核邮件列表与公开论坛通过其公开页面阅读，两者都可达；论坛最新帖是三天前的，所以它的 24 小时窗口是真的空，而不是不可访问。两个 Discord 工作区（合计十个白名单频道）未被覆盖：这个环境没有它们的登录会话，可见页面停在登录表单上。它们记为不可访问，而不是安静。合计四个来源已检查，两个未覆盖。

邮件列表窗口里有两个主题。第一个正是本页回答的：BPF 程序实际持有哪把锁，以及哪些代码对此作了假定。除 sockmap 系列外，同一窗口还有一个 virtio 传输修复：BPF 接收路径在等待数据时持有套接字锁，与需要同一把锁来排队数据的投递工作线程互相死锁；修复在等待期间释放锁，并采用原生路径的退出条件，另外把本不该进入 sockmap 等待的读操作单独处理。第二个实例是上文所述的 destroy kfunc 限制。第三个是评审回复，针对迭代器写入只读 map 的问题：提议的判定同时检查"程序只读"标志和 frozen 位，而更正意见是——冻结只阻止系统调用侧的写入，程序仍可写进冻结的 map，因此只用那个标志才是对的；进一步的要点是标志永不变更，所以不存在竞态。该线程还更正了 Fixes 标签、去掉了一个机器人提议的提交，并要求补一个自测：在创建为程序只读的 map 上，通过迭代器的 value 指针写入。

第二个主题是"合并状态的校验器"改变了程序里数值的范围，而这一改变的两个方向在同一天都出现了。一个包含九处修复的系列跟在一轮大的校验器重构之后：一个计数器在统计循环的跳转之前正好回绕，于是拿未回绕的值算出步长与余数，交给下一条指令的范围既排除了寄存器真正持有的数，又包含了它从未持有的数；修复在求和可能回绕时干脆不设范围。同一系列还修了两个只在特定编译器或特定架构下失败的自测——内层循环被展开后用一个指针遍历 map value，校验器找不到计数器——以及一种情形：程序抛出若干错误码之一却被拒绝，因为合并把标志与 throw 的 cookie 合到一起；修复让参数检查也读 throw 的参数，于是 cookie 不同的状态不再合并。另一个配套系列测试"携带所加载值"的短循环，其中包括一个先填栈槽、之后才被拷贝的循环，校验器只用了几条指令就走过它，而不是完整圈数。列表另一处，一个补丁拒绝挂载到在递归中被调用的子程序上，因为加载期的栈深检查看得到递归，却看不到之后挂上去的东西；还有一个会给所有不可睡眠程序关闭抢占的 trampoline 补丁，被指出的反对意见是：带上有界循环的程序可以跑四分之一秒，抢占应当按程序、通过显式辅助函数关闭，而不是全局关闭。

可通过归档访问的可观测性频道当天很安静；其七天窗口里唯一一条消息没有被引用在这里，因为它是一句状态说明，而不是技术问题。本页回答的问题来自公开邮件列表，页面里每一条机制性论断都对照了当前内核源码中的校验器、sockmap、Unix 套接字与 TCP abort 路径，而不只是采信补丁说明。
