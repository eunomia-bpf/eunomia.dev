因为 level 1 的校验器日志不再是一条路径，而是校验器访问过的每一个基本块的累积；而内核判断是否返回 -ENOSPC，依据是日志曾经达到过的最大长度，而不是结束时缓冲区里剩下什么。在校验器按控制流图顺序验证、并合并到达同一个块的状态的内核上，一个验证成功的程序仍然会在累积文本超过调用方缓冲区时加载失败，因为收尾步骤在结论之后才运行，它的 -ENOSPC 会覆盖掉验证结果。一个已经进入 bpf-next 的后续系列把 level 1 日志重新变回"一次一个基本块"，并在被拒绝的块前面打印通往它的路径。

机制

  1. 这条日志原本是什么。 在 level 1 下，校验器每验证一条指令就打印一条。在条件跳转处，push_stack() 把另一个分支放到一边，并把当时的日志末尾记在待处理项里；当它回头处理那个分支时，pop_stack() 调用 bpf_vlog_reset() 回到记录的位置。正是这一对操作让日志成为一条路径：长度不超过程序里最长的那条路径，而对于被拒绝的程序，它恰好是走到出错指令的那条路径。这两句话在当前主线源码里都成立。

  2. 合并状态的改动之后它变成了什么。 一旦校验器按控制流图的顺序验证基本块、并合并到达同一个块的状态，就不存在可以回退的路径了。pop_stack() 已从校验器中消失，没有任何地方按分支记录日志位置，也没有任何东西在一个函数验证期间把日志移回去。每个块每被验证一次就把自己的文本追加上去，于是日志里包含每一个块、每个分支的两边、按验证顺序排列。对大型真实程序来说，差别不是几个百分点：该系列给出的数字是，某个 Cilium 程序单条路径 51,434 字节，所有块 774,446 字节；某个 Katran 程序是 103,567 对 3,668,559。

  3. 于是合法程序为什么失败。 程序验证通过时文本会被丢弃——成功的一遍结束后日志被重置。但这没有帮助，因为收尾比较的是运行最大值，而不是当前长度：每次写入都把 len_max 更新为日志曾经达到过的最大总量，而收尾在缓冲区存在且该最大值超过缓冲区大小时返回 -ENOSPC。这个计数器的存在本就是为了让调用方知道被截断日志的真实大小，它同时也是回填给调用方的那个真实大小。

  4. 为什么这会变成加载失败而不是警告。 收尾调用位于加载路径上、在运行时选择之后，它的返回值会覆盖验证结果：只要收尾失败，这个错误就替换掉校验器得出的任何结论。于是校验器已经接受的程序被报告为加载失败，errno 是 ENOSPC。数量很大：在改动前有 2,841 个程序（自测、Cilium、调度器、少数 Rust crate）越过 64 KB 缓冲区，改动后是 5,503 个，加上后续系列后是 45 个。

  5. 为什么不能简单调大缓冲区。 bpf(2) 里展示的模式正好会踩中这一点：一个静态缓冲区、log_level 为 1、只调用一次、不重试。自己持有缓冲区的调用方从内核那里得不到第二次机会，而文档化的契约只说缓冲区太小时调用以 ENOSPC 失败——它并不区分"程序被拒绝"和"程序被接受但日志被截断"。对自有缓冲区，libbpf 确实会区分：遇到 ENOSPC 就翻倍自己的缓冲区并重试，上限是三十二位范围的一半。所以这个回归落在传自己固定缓冲区的调用方身上。

  6. 后续系列如何修日志。 两处改动。第一处增加一对辅助函数，把日志尾部取出到临时缓冲区、稍后再追加，并统计缓冲区装不下的字节数，使得上报的大小和是否截断的判断都描述一份按最终顺序写出的日志。该分配被设置为宁可失败也不触发 OOM killer；若分配失败，日志保持原样。第二处把日志在每个基本块前移回，使 level 1 日志重新一次只含一个块；当某个块被拒绝时，它以"先打印通往该块的路径、再打印该块与错误信息"的顺序输出：块先被暂存、路径打印出来、块再被追加回去。保留的状态带有它抵达时经过的那条边——合并之后是最后改动它的那条边——于是路径可以由状态重建，不需要重复验证任何东西。成功路径上的代价是每个状态两次 32 位存储，语料中最长的路径约耗时 0.4 毫秒。

  7. level 2 日志保留了什么。 level 2 不变，这也是为什么有六个读取路径上某条指令背后状态的自测被改成请求 level 2。level 1 不显示路径上各条指令背后的状态，也不显示独立验证的子程序体；level 2 两者都有。

验证与排障路径

  1. 用不带日志的重跑来区分两种失败。 把同一个程序的 log_level 设为 0 再加载一次，把日志从问题里摘出去。如果这样能加载，说明程序是被接受的，ENOSPC 来自日志而不是验证过程。这一步正是区分这个回归和真正过大的程序的办法。

  2. 读上报的真实大小。 程序加载属性里有一个输出字段给出日志的真实大小，文档说明它在日志被截断时可能大于缓冲区、未被填满时小于缓冲区。要看变化前后的这个数字，而不是从缓冲区长度猜：只有它能说明日志超出了多少。

  3. 确认你传的是哪个缓冲区。 libbpf 自己分配的缓冲区遇到 ENOSPC 会增长并重试；通过加载选项传入的缓冲区，或像 bpf(2) 示例那样的静态数组，则不会——libbpf 把它标记为非自有，在后处理文本后返回错误。如果你用的加载器传的是固定缓冲区，而某个以前能加载的程序现在报 ENOSPC，那就是出问题的面。

  4. 修复之后读日志尾部。 在带后续系列的内核上，被拒程序的日志以出错的块和它的信息结尾，而通往它的路径打印在前面，由保留的状态边重建。依赖行位置的工具必须预期这次重排；块本身的文本与之前相同。

  5. 测峰值，而不是末尾。 如果你在给校验器加测量，要盯的是收尾时拿来比较的那个运行最大值；成功加载后缓冲区里的字节数是另一个、且小得多的数字。

局限

  • 这个回归与其修复都在 bpf-next 树里，那棵树的验证过程已经按控制流图进行。当前主线仍然用 push/pop 的日志位置走路径，所以主线内核的行为与 bpf(2) 的描述一致。上面的数字描述的是合并状态树以及应用其上的系列。
  • 修复恢复了 level 1 日志的大小与形态，但没有恢复完全相同的旧文本。一个块在路径上只出现一次，所以路径绕循环一圈后从循环的支配者继续；在调用者栈帧里验证的函数只出现一次，且是它最后一次调用。期望逐字节复现合并前输出的日志消费者仍会看到差异。
  • 被丢弃的一轮验证完全不产生路径，未决信号会结束打印，所以路径可能比完整解释更短。
  • 暂存受缓冲区大小限制，缓冲区可能达到内核允许的上限，且分配可能失败；此时日志保持原样而不是让加载失败，也就是说在内存压力下重排是尽力而为的。
  • 语料数字来自作者，基于固定的程序集合和固定的缓冲区大小；把它们当作量级，而不是对某个具体二进制的保证。

当日社区讨论

本次运行检查了六个白名单社区。其中两个是 Slack 工作区，通过已批准的私有只读归档访问，覆盖三个白名单频道；三个频道在 24 小时窗口内都没有消息，七天窗口内同样没有，所以归档没有贡献任何主题。两个共含十个白名单频道的聊天工作区未被覆盖：本环境没有已认证会话，公开邀请页返回"邀请无效"页面，因此按不可访问记录，而不是按安静记录。从业者论坛在整个运行期间对可见浏览器返回网络安全拦截页，同样记为不可访问。内核邮件列表通过其公开归档页面阅读，上面的问题与下面的主题都来自它。

最主要的主题是：校验器的改动如何影响它周围的东西，而不是影响判定本身。level 1 日志是最清楚的例子——验证结论一直正确，而诊断通道悄悄变成了新的量级并丢掉了中心性质，失败最终以"校验器已接受的程序加载报错"的形式出现在调用方。它的修复必须在重排文本的同时，保持被截断的滚动缓冲区的逆序、真实大小报告与截断判断三者一致——这也是为什么该系列选择统计缓冲区装不下的字节，而不是重建日志。同一棵树上的两个同族报告呈现同样形状：一个在计数循环的那条跳转之前回绕的数值会得到用未回绕值算出的余数，于是校验器检查的是寄存器根本不会持有的数字，修复在可能回绕时干脆不设范围；另一个是抛出若干错误码之一的合法程序被拒，因为合并把抛出 cookie 与标志并到了一起，修复改的是参数检查而不是合并本身。

第二个主题是"只对作者心中那类输入成立"的检查。btf_struct_access() 拒绝直接访问程序分配对象上的特殊字段，但对可变偏移只检查最小偏移。编译器生成的 BTF 让这个推理成立：校验器把访问限制在一个数组内、步长是元素大小的整数倍，而特殊字段按元素重复，所以每个可达偏移都落在同一个成员上。手写 BTF 的重叠成员会击穿这个推理——当数组成员越过某个 kptr 指针的偏移时，一次完全合法的数组下标写入就会覆盖该指针，对象的释放路径随后释放被破坏的值。修复只检查可达偏移，即最小值加步长的整数倍；评审者给出的更短版本依赖"步长永不为零"这个不变量，而寄存器一致性检查已经保证了它，所以常量偏移只是同一个检查的第一种情形。补丁不许越过的那条边界由它自己的测试写明：始终落在每个元素非特殊成员上的写入必须继续能加载。

第三个主题是 map 与迭代器的权限，那里两种"只读"被混为一谈。迭代器的 value 指针对所有非 per-CPU map 类型都是可写的，于是程序可以向"对程序只读"创建的 map 写入，破坏内容被校验器当作常量的 map。提出的判断原本同时检查"对程序只读"标志和 frozen 位；更正的要点是冻结只阻止系统调用侧的写入，程序仍可写入已冻结的 map，所以只用该标志就够了——而且该标志永不改变，因此不需要考虑与冻结调用的竞态。同一次评审还修剪了 Fixes 标签、去掉了会让每个 map 都被拒绝的那个提交，并要求补一个在"对程序只读"的 map 上通过迭代器 value 指针写入的自测，因为早先的复现程序在修好的内核上也能通过。

第四个主题是 map 在遍历过程中变化时批量遍历该报告什么。哈希 map 的批量查找在一个键于遍历期间被删除时可能丢失游标，然后报告 map 结束，这会让调用方在仍有键时认为遍历完成。补丁把这种丢失报告为可重试的条件，让遍历器继续而不是下结论，并围绕遍历期间的删除加了回归测试。对用户态导出工具的实际含义是：一个短批次不是尾部为空的证据。

第五个主题是被 BPF 接管的接收路径里的锁归属。一个经 sockmap 重定向的传输层接收钩子先拿套接字锁，然后睡眠等待数据，而该传输层的投递工作线程需要同一把锁才能把数据排进队列——读方与它正在等待的生产者互相死锁。修复在等待前后释放锁，采用原生路径的退出条件，并单独处理本不该进入 sockmap 等待的读取：长度为零的读、错误队列和带外数据。当前树里的实现显示锁在等待循环之前获取、只在末尾释放，这正是该报告可信之处；作者同时列出了仍未修的部分，尤其是只存在于套接字 ingress 队列里的数据，以及缺少显式访问器的无锁读取。

两个较小的信号。一个 24 补丁的 arm64 JIT 系列用重建若干真实项目的 BPF 对象、并按微架构报告体积与建模周期的方式来度量自己，这是 JIT 改动需要却很少拿到的证据类型。另一个是挂载检查现在拒绝挂到一个被递归调用的子程序上，因为加载时的栈深检查能看到递归，却看不到之后挂载上去的东西——这是一个两端必须在同一时间点强制才成立的不变量示例。
