因为在 x86-64 上，使用私有栈的 JIT 程序没有帧指针寄存器，于是 JIT 把私有栈帧地址放在一个保留寄存器里，并在每次调用前后把它压栈、弹出。这样的程序抛出异常时，throw 辅助函数记录主程序帧的栈指针，异常回调从这个地址开始弹出自己保存的被调用者寄存器；而这个地址上放的是刚压入的帧地址，不是第一个保存寄存器。于是每个寄存器都拿到邻居的值，最靠内的那个拿到私有栈的地址。程序返回后内核使用这些寄存器时就崩了。修复的做法是把这个压入寄存器的八字节加到异常路径本来就携带的栈指针调整量上。JIT 发出的指令流完全不变。

机制

  1. 哪些程序会拿到私有栈。 校验器里的 bpf_enable_priv_stack() 只在 JIT 支持、且程序类型属于 kprobe、tracepoint、perf event 或 raw tracepoint 之一（经典 uprobe 用的就是 kprobe 类型）时才授予私有栈；tracing、LSM、struct ops 程序则是自己申请或者需要递归检查时才拿到。子程序还要满足更多条件：取整后的栈深度达到 64 字节下限、对象里没有任何程序使用尾调用、并且在 x86-64 上不在栈上传递参数。最后一条存在的原因，是同一个寄存器在原生调用约定里正是第六个参数。

  2. 私有栈对栈帧做了什么。 普通的 JIT 程序以 push rbp 和 mov rbp, rsp 开头，并把程序栈放在这个帧指针之下。使用私有栈的程序改为把每 CPU 栈区的帧地址放在保留寄存器里，原生帧指针和栈指针保持不动，并且在每次 helper、kfunc、直接调用和间接调用之前压入这个寄存器、之后弹出，因为调用可能覆盖它。序言还把程序自己的栈深度字段置零，因为程序栈已经不再位于内核帧里。

  3. 一次 throw 交给回调的是什么。 可能抛出异常的对象，其主程序在入口无条件保存被调用者寄存器：rbx、r13、r14、r15，再加一个没有映射到任何 BPF 寄存器的寄存器，因为 throw 可能发生在内核已经覆写它之后。bpf_throw() 沿栈走到「所属程序被标记为异常边界」的那一帧，记录该帧的栈指针，并把该指针加上一个保存的调整量交给异常回调。回调序言用这两个参数设置自己的栈指针和帧指针，弹出保存的寄存器，再复位帧。所以整个交接依赖一个整数：记录的栈指针到保存寄存器区之间的距离。

  4. 那八个字节的偏差。 没有私有栈时，记录的栈指针处的栈帧最内槽位正是最后一个保存寄存器，弹出是对齐的。有私有栈时，最内层的那次调用恰好把自己的帧地址留在这个槽位，比保存寄存器低一个条目。回调于是把帧地址弹进第一个寄存器，其余寄存器整体错一位，其中一个最终持有每 CPU 栈的地址。stack_arg_sp_adjust 本来就把指针从栈上出参移到保存寄存器区；修复在「主程序用私有栈 JIT」的情况下给它加八字节。一个常量就够：每一类调用都会发这条压栈，带尾调用的程序没有私有栈，回调自己不能再 throw，而且只有主帧会被恢复，因为子程序帧两种情况下都会被丢弃。

验证与排障路径

  1. 读崩溃位置。 故障不在 BPF 程序内部，而是出现在程序返回之后、进入它的那段代码里，因为被污染的保存寄存器正是在那里被使用。一个已报告的例子是程序测试运行路径中的空指针解引用。

  2. 确认私有栈真的在用。 用 bpftool prog dump jited 反汇编 JIT 镜像，找加载私有帧地址的序言，以及调用前后的压栈与弹出对。两个便宜的对照就能去掉它们：往空程序数组里放一次尾调用，或者让帧小到落在 64 字节取整下限之下。如果崩溃在这两种对照下都消失，变量就是私有栈。

  3. 对齐触发条件。 tracepoint、raw tracepoint、perf event、fentry 与 fexit、以及申请私有栈的 struct ops 程序，只要主程序的栈超过大约 48 字节原始深度（也就是取整后达到 64 字节阈值）就会受影响。throw 可以在主程序里，也可以在子程序里。迭代器被排除在私有栈选择之外。

  4. 理解这个组合为什么躲过了测试。 现有把私有栈与异常配在一起的 selftest 都是 fentry 程序。测试 loader 并不挂载它们，而通过测试运行系统调用去跑一个 tracing 程序会直接报不支持、根本不调用程序，于是这些对象只被加载、从未被执行。修复补上了 raw tracepoint 变体，测试运行路径会真正执行它们；没有修复时它们会让内核崩溃，而「只有子程序带私有栈」那个变体在修复前后都通过，这正是它成为回归护栏的原因。

局限

  • 这个缺陷和这个修复都只针对 x86-64 JIT。arm64 JIT 在同一交接处有另一个独立的缺陷：回调拿不到帧指针，只保留了 throw 留下的那个寄存器值；那个已经在上游修好并按安全修复跟踪，机制是缺少帧指针设置，而不是八字节偏移。
  • 本次运行时，x86-64 的改动只是针对当前开发树提交的补丁，尚未进入任何发行版本。带私有栈 JIT 支持的内核上，抛出异常的程序仍然会撞上它。
  • 这个调整量来自 JIT 实际发出的代码，而不是源码。将来若某次改动不再在调用前后压入帧寄存器，或者移动了保存寄存器，就必须回头重看这个常量。

当日社区讨论

本次运行的观察清单覆盖六个社区：两个聊天工作区共十个频道，两个由存档支撑的聊天工作区共三个频道，一个邮件列表，一个实践者论坛。那三个存档支撑的频道经已批准只读存档按 24 小时与 7 天窗口查询，均未返回任何消息，因此它们是安静而非跳过。两个聊天工作区的十个频道本次未覆盖，因为读取它们需要一次已登录的浏览器会话而本次没有；它们被记为未覆盖，而非安静。

邮件列表上有三个较大的线程。第一个就是上面回答的私有栈问题，而它只是一个更大未解问题的一角：一条为可睡眠程序关闭私有栈的系列仍在评审中，而本窗口内的一份生产报告在不可睡眠的探针上测到了同样的帧污染。它的数据才是重点。污染只出现在运行路径可能被抢占的地方：若干已发布内核与当前开发树在全抢占和惰性抢占下，大约每几百到每一千次被插桩调用出现一次损坏帧；而自愿抢占的构建、以及 JIT 不支持私有栈的内核则为零。两个对照——一次尾调用，或者一个很小的帧——在所有配置上都是零。报告还指出了探针为何暴露：uprobe 的运行路径关闭了迁移、拿了一把读侧锁，而在可抢占 RCU 的构建上这把锁并不阻止抢占；其中一条路径上方的注释一直声称它为程序关闭了抢占，可代码从来没有这么做。桌面上有三个修法，评审者指出了各自的代价：收窄授予条件，但加载时无法区分经典 uprobe 和 kprobe，除非新增一个标记；在挂载时拒绝未标记的程序，代价是给所有由旧 loader 或 libbpf 之外的 loader 构建的程序一个裸的 invalid argument 失败；以及在运行周围加一道抢占屏障。维护者直接否掉了最后一个，指出同样的做法在线程更早的地方已经被拒过一次。那次交锋——包括接受更正的回复——正是线程当前的末尾，所以边界仍然开着：每 CPU 栈加上可抢占的运行路径，要么需要一道屏障，要么就不要每 CPU 栈，问题在于这个修复被允许弄坏哪些用户。

第二个线程是一条重做的系列，改变有界循环指令执行 250 毫秒上限的方式。计数和截止时间放在包含该循环的函数的栈帧里，于是上限作用于子程序的一次调用，而不是程序的一次执行：跨调用嵌套的循环会叠加上限，帖子给出了九条指令就能占住一个 CPU 的例子。系列把两个值都搬到入口时设置一次的每 CPU 程序内存里，于是上限变成按次执行算，截止时间之后被调用的函数一次迭代都不做，bpf_loop() 与 map 元素迭代辅助函数也会在时间到时提前停止。测得的代价不大但明确——使用该指令的那一小部分调度扩展程序 JIT 代码略多、栈用量明显更少、调用略便宜、每次空迭代还便宜几分之一纳秒——而诚实的保留意见是：同一 CPU 上同一程序的第二次并发执行会共享这两个计数，这会把上限拉长而不是提前截断。任何依赖「每个帧各有一份配额」的推理都需要更新。

第三个是一条构建与内存系列，把内核自己的类型信息压缩保留到首次使用，而不是在启动时解析，在从不使用它的系统上省下大约六兆字节，代价是第一个用户一次性付出大约十五毫秒。它默认关闭，并且暂时只覆盖两种架构，因为在其他架构上启动镜像本来就带一份未压缩副本。它对这批读者的意义在于：从编译期字段重定位到 fentry、内核函数、struct ops、调度扩展和 LSM hook，全都依赖这份类型信息，所以这场讨论是一次发行版配置上的取舍，而不是程序行为的变化。同一窗口里的另一份报告——某个构建工具在相关的调试信息选项下崩溃——当天就得到了带具体机制的回复：在从一个基础 BTF 复制字符串时触发 use-after-free，因为复制的动作释放了该基础 BTF 的原始数据；回复附了一个单文件的提议修复，并以工具输出逐字节一致作为证据。

窗口内较小的条目，都还开着或处于早期评审：并发 sockmap 更新在改写 socket 协议与其挂载程序之间的数据竞争；一个校验器修复，处理栈上参数分析里「帧指针偏移为零」与「不是指向栈内」的值如何合并；一条网络系列，必须在 BPF 程序在段路由行为内部运行之后丢弃已校验的和校验；两个 XDP 驱动修复，一个在接口关闭时把帧当作 socket buffer 释放，另一个把错误的接收队列报给程序；面向零拷贝 packet socket 家族的多缓冲区发送校验和的第四版修订；以及对一条把逐记录重定位属性搬进生成的 C 输出的工具系列的持续评审。另有一场关于「新间接跳转特性中两个刚修好的缺陷是否应当得到与同一特性此前三个修复同等的安全与稳定回移待遇」的争论在窗口结束时仍未结束；维护者的反对点是「先查存档再提问」，所以「非特权威胁模型到底到哪里为止」这个问题本身仍然没有被写下来。

实践者论坛在窗口内没有新帖；最近的线程是几天前的，继续一篇关于大规模运行探针的运维记录，仍然挂着两个开放问题：在一个发送环上，内核唤醒标志到底值不值；以及在一台有负载的虚拟机上，为忙轮询循环独占一个核是否划算。

本次运行的存档来源在两个窗口都没有消息，所以上面的问题来自允许的公开 bpf 邮件列表，并对照已发布的内核源码做了核实；本节的全部主题也来自这个邮件列表。

为什么生成式 BPF loader 对象会在只有子程序或未加载程序把数量推过上限时被拒绝，而检查又如何移到真实的已加载程序数量上？

因为上限是针对对象的程序总数强制执行的，而这个总数把 loader 根本不会去加载的子程序与关闭了 autoload 的程序也算了进去，于是本该能加载的对象也被拒了。修法是把代码生成阶段的记账夹到上限之内，并把真正的拒绝推迟到「程序文件描述符真正写入 loader 栈」的那个时刻；只有那些真正通过了加载遍的程序才会走到那里。
