因为校验的代价不是程序里有多少条指令，而是程序里有多少条路径。今天的校验器逐路径走：每遇到一个分支就把抽象状态分叉，两边各自独立验证，只有当某条路径到达一条指令、而该指令上已保存的状态至少同样一般时，这条路径才被剪掉。于是，一个退出条件依赖计数器的循环，或者一个被多处调用的函数，都会按“到达同一指令的不同方式”成倍放大工作量。一个正在评审的系列把这条路径遍历整个去掉：两条路径相遇处合成一个覆盖两者的状态——r1=1 与 r1=5 变成 r1=[1,5]——反复迭代直到没有状态再变化。用户能看到的两个限制，100 万条已处理指令与 8192 条跳转序列，被替换成对状态数量的限制。真正难的并不是合并本身，而是哪些状态不能合并：一旦合并，后续检查就丢掉了它需要的信息。

机制

  1. 现在的限制到底在数什么。 BPF_COMPLEXITY_LIMIT_INSNS 是 1000000，比较的对象是 env->insn_processed，这个计数器每执行一条指令加一——是校验器走过的指令，不是程序里有几条指令。BPF_COMPLEXITY_LIMIT_JMP_SEQ 是 8192，比较的对象是 env->stack_size，即校验器已压栈、尚未恢复的分支状态个数。两者度量的都是探索量，与程序的静态规模无关。一个 3000 条指令的程序可能撞上其中任何一个；一个 50 万条指令的直线程序一个也撞不上。

  2. 为什么指令很少的程序会爆炸。 校验器为每个（指令，调用链）组合保存一个状态，分叉时把未走的那一边压栈。如果某个 helper 或静态子程序被多处调用，或者某个循环的边界只能表示为区间，同一条指令就会按到达它的路径数被反复验证。只有当该指令上已记录的状态相同或更一般时，路径才被剪掉；对循环而言，这要求状态收敛，而一个校验器只会对其做区间放宽、不会求解的循环，会不断产生新状态，直到某个迭代上限把它拒掉。上报的失败案例正是这个形状：某个调度器回调上 1000001 条已处理指令，以及一个向量 push/pop helper 上的 “sequence of 8193 jumps”。

  3. 什么是合并。 在汇合点不再保留两个状态，而保留一个：其中每个寄存器持有两者区间的并集，r1 成为 [1,5]。任何对并集成立的事实对两个输入都成立，所以验证并集对两者都是可靠的。但并集比任一输入都更弱，下游的某个检查可能在单条分支上通过却在并集上失败；对策是：当后续检查能够区分两者时，就不要合并。这是正确性要求，不是优化——合并得太急会把合法程序判掉。

  4. 哪些状态必须分开。 后续某条把寄存器与常量比较的条件跳转，或者在调用点、在退出处对其范围的检查，使该寄存器成为「被检查」的。若两个被检查的区间之间有空洞——-155 与 0，而不是 0 与 1——合并就会造出任何路径都不会产生的值。同理适用于两个无公共值的被检查寄存器、只有一侧初始化的寄存器（合并后会声称它在另一条路径上也可读），以及会变成栈偏移的常量。有些检查需要真正的常量而不是区间——bpf_ringbuf_reserve() 的大小参数是标准例子——于是那些喂给这类检查的寄存器和栈槽会在主流程之前一次性找出，在此处有差异的状态不合并。

  5. 循环怎么处理。 校验器能用标量演化计数的循环，用一个状态覆盖所有迭代；能走到头的循环，在常量决定出口期间每次迭代一个状态；其余所有循环在头部合并、放宽，并给一条 may_goto 边。may_goto 是校验器已经认识的指令：JIT 把它变成有预算的后向跳转，预算来自每次调用的时间片。当前树里这个运行时检查比较的是四分之一秒（NSEC_PER_SEC / 4），预算计数器是 BPF_MAX_TIMED_LOOPS，机制已经存在；该系列让校验器插入这些边，而不是要求作者自己写。

  6. 诊断输出被替换掉了什么。 去掉路径遍历，也就去掉了那些只为让遍历更便宜而存在的机制：精度跟踪、跳转历史、强连通分量的记账。mark_chain_precision()、日志里的 mark_precise:、N: safe 与 depth= 输出、SCC 列都会消失，这正是二级日志格式改变的原因——汇合处报告 joined、widened 或 within，而不再报告某条路径被剪掉。统计行保持原格式，所以解析 processed N insns (limit ...) 的工具不受影响；BPF_F_TEST_STATE_FREQ 仍然被接受，但不再有效果。

  7. 为什么静态子程序与递归是同一个变化的推论。 静态子程序目前在每个调用者的帧里被验证，两个调用者的帧不同就没有可合并之处，于是子程序按调用链被反复验证。改为按其首条指令处的状态集合验证一次，这个乘数就消失了；同一套机制允许递归：递归子程序按入口状态加放宽验证一次，深度由运行时对栈指针的检查限制，而不是由静态帧数限制。这正是该提案能在当前校验器拒绝递归的地方允许递归的原因。

验证与排障路径

  1. 看计数器，不要看指令数。 校验器的统计行会打印 processed %d insns (limit %d) max_states_per_insn %d total_states %d peak_states %d mark_read %d。在限制处被拒、同时 max_states_per_insn 只有几十、processed 到了百万，说明是探索量而非规模问题。要和程序头里的 insn_cnt 对比；如果它远低于 100 万，那就是路径爆炸，删指令是错的方向。

  2. 按报错信息区分三种限制。 “BPF program is too large. Processed N insn” 是指令预算；“The sequence of N jumps is too complex” 是待恢复分支栈；“infinite loop detected at insn N” 是循环状态不再变化但校验器证不出终止。三者成因不同，即使出现在同一个程序上；放宽一个会立刻暴露下一个。

  3. 找出代价集中的那条指令。 二级日志会显示被验证状态的流动；某条指令上的状态数特别大，它就是被按路径反复验证的汇合点，通向它的子程序或循环就是要重构的对象。由于 max_states_per_insn 是最大值而不是总和，它能定位位置但不能给出总代价；processed 才是总量。

  4. 先重构，再考虑删减。 把共享计算移出分支、把走 helper 的路径改成直线、把不可预测的循环边界换成可计数的，都能在不改变行为的前提下减少路径。把指令删到装得下会改变程序语义，这正是上报的案例来自一批无法简单裁剪的生成式 Rust 代码的原因。

  5. 用一个小程序测试合并语义。 检验该行为的关键实验，是一个两条分支给同一寄存器赋不同常量、且后续检查能区分的汇合点，以及它的反面：没有任何检查区分两者。前者必须不被合并且验证通过，后者合并后仍验证通过。一个把两者都合并的校验器在第二个例子上看起来正确，在第一个例子上是错的。

局限

  • 该系列是评审中的提案，不是已发布行为。在合入之前，程序撞到的是它所在内核 kernel/bpf/verifier.c 里的限制；上文数字来自当前树。
  • 合并是可靠的，但在作者关心的方向上并不完备：它可能拒掉逐路径验证本来会接受的程序，因为两状态的并集比任一状态都弱。文中列出的例子——区间丢掉两个标量之间的关系、r0 可能是 2 或 3 却塌缩成 [1,2] 从而被迫只能挂到 egress——都是真实的判定变化，不是以后靠放宽能补的 bug。
  • 对比数字来自作者的语料库与测试框架，有通常的注意事项：对不同程序集合求和、三次取最优的计时、以及“一个状态”按到达基本块的次数而不是按保存的状态计数。它们应当当作量级，而不是基准。
  • may_goto 的运行时侧仍受时间片限制，所以一个现在被接受的循环程序仍可能在运行时被截断；区别在于它会返回，而不是加载失败。依赖加载期拒绝非终止循环的程序会失去这项早期诊断。
  • 允许递归是 x86-64 与 arm64 的显式例外列表，因此一个递归程序可移植于这两者，但不一定超出它们。

当日社区讨论

本次运行审查了六个在允许清单内的社区。其中两个是通过获批的私有只读归档访问的 Slack 工作区，覆盖三个允许清单频道；在这个窗口里，一个 24 小时内没有任何消息，另一个 24 小时内没有、七天窗口内有三条。两个没有归档的聊天工作区没有被覆盖，因为这个环境没有它们的已登录会话，可见页面停在登录页；它们记为不可访问，而不是安静。内核邮件列表与实践者论坛通过其公开页面阅读。

邮件列表承载了上文的问题，另有四个主题，构成三类。第一类是用错误的谓词做边界检查。两个把 CPU id 作为不受约束 u32 接收的 helper，只拿它和 nr_cpu_ids 比较，而 per-CPU 内存只为possible CPU 分配；在一台 possible 掩码有空洞的机器上，落在空洞里的 id 通过了检查，per_cpu_ptr() 就用该 CPU 未初始化的偏移算出指针。上报的后果是把通过返回指针读到的 map value 交给更新时，在 memcpy 里发生错误；同一路径对 per-CPU 对象是可写。两个细节让它不只是一个缺失的检查：校验器会把已知 map 上的 lookup 重写成对 map 回调的直接调用，所以只在 helper 包装里检查覆盖不到 JIT 后的程序；校验器还会从 per-CPU 分配 helper 的返回值上去掉 PTR_MAYBE_NULL，于是跳过 NULL 判断的程序也能通过校验，然后在运行时出错。该线索上的评审意见是精简过长的提交信息，而不是质疑分析。

第二类是helper 静默丢信息而不是报错。有一个栈捕获 helper，有会缺页和不会缺页两套实现：不会缺页的那套无法把页面调入，于是当返回地址所在文件页不在内存中时，它退化成一个裸指令指针，而不是解析出 build id。今天只有探针类程序被路由到会缺页的变体，其他可以睡眠的程序类型对非常驻页持续丢失 build id，且没有任何错误提示。提出的修复把这些类型路由到可睡眠变体并给原型标上可能睡眠，这同时会让校验器拒绝在原子上下文中的调用——也就是说，今天能加载的程序可能开始失败，作者明确这是有意的一致性，而非附带损伤。

第三类是kfunc 里的生命周期假设。一个路径解析 kfunc 可以运行在为任务退出而释放的文件上，此时任务的文件系统上下文已被清理，底层解析器随即解引用空指针；修复是提前返回错误，并加一个不加修复就会崩溃的 selftest。第四条线索把同一类问题推到属主方向：BPF 程序原先在共享 workqueue 上释放，系列给它们专用 workqueue，使一次缓慢的释放不会拖住无关工作。

通过归档访问的可观测性频道在 24 小时窗口内安静；其七天内容是一条三条消息的线索，讨论该由谁拥有一个抑制厂商 SDK 自身 trace 导出、改走 instrumentation 路径的开关。技术内容是配置归属之争而非 eBPF 问题——反对意见是这个决定应属于 SDK，回应是 instrumentation 已经修好了手动路径，所以这个开关只是去掉一份重复——目前仍未关闭，PR 在等作者而不是在等维护者的反对。

本页问题的来源是公开邮件列表在当日窗口内的讨论；结论依据当前内核源码与补丁系列本身的文本核对，而不只是依据线索里的说法。
