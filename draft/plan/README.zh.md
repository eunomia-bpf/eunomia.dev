# 内容发布计划说明

> 状态：内部执行草案，不发布。更新时间：2026-08-05。

本目录只维护一个滚动发布队列：
`draft/plan/publishing-queue.zh.md`。发布顺序会变化，内容就绪、平台审核、
上一项反馈和用户确认都可能改变下一步，因此不再把候选内容提前塞进具体
日期，也不再维护月度日历式计划。

## 怎么写队列

- 从上到下按最早可执行顺序排列。
- 每个平台同步单列一个 checkbox；同一篇同步到两个平台算两个任务点。
- 每项写清状态、平台、源文件和必要检查，不创建“准备一天”“检查一天”
  之类空占位。
- 状态只使用 `排队`、`待确认`、`阻塞` 和 `跳过`。
- `排队` 是定时巡检的真实发布授权；`待确认` 与 `阻塞` 只能等待，
  `跳过` 必须附一句原因。
- 完成后改为 `[x]`，回填公开 URL、审核状态和 ledger 结果。

## 时间规则

- 正常节奏是每个自然日发布一篇。最近有可执行任务、却因登录、审核或
  编辑器等运行阻塞而没有任何公开发布时，每漏一天产生一个补发额度；
  后续巡检可以在正常任务之外继续处理下一条可执行任务，直到补齐。
- 同一平台在同一自然日最多发布一篇。主动暂停以及没有可执行任务的日期
  不产生补发额度，补发也不能绕过平台节奏或内容质量判断。
- 正常任务完成后，下一项在下一个自然日进入发布窗口；只有明确记录的
  补发额度可以在同日继续。平台需要更长间隔、前一项仍在审核或内容尚未
  就绪时，队列自然顺延。
- 暂停和阻塞写在队列顶部。已经发生的发布事实保存在 platform ledger
  和同日 `draft/media/YYYY-MM-DD/run-log.md`，不复制成日历流水账。
- Weekly Analysis 和研究报告由独立研究流程负责，不进入本发布队列。

## 排队前先做完

历史发布核对、重复检查、源文件质量修复和账号状态确认应尽可能立即完成，
不能伪装成未来任务。长文同步保持源标题和正文，只处理格式、图片和平台
元数据；源内容需要修正时先更新源文件，再进入队列。

当前同步原则：

- 知乎和掘金优先处理 ledger 确认缺失的中文长文和 tutorial。
- 历史回补默认只保留 tutorial；2026 年以前的非 tutorial Blog 不因平台
  ledger 缺失自动排队，只有新增证据、结论或明确发布需求时才重新评估。
- Medium 和 DEV 只处理 ledger 确认缺失的英文长文。
- X 和 LinkedIn 默认分享已发布长文链接，外加 1-2 句核心钩子；项目演示
  可以使用简短原生帖子和真实图片、GIF 或视频。
- Reddit 等社区平台只在内容与社区规则、当前讨论明确匹配时发布。

## 执行

1. 读取 `publishing-queue.zh.md` 顶部的暂停、阻塞和补发缺口。
2. 从上到下找到第一条可执行的 `排队` 任务，临时 `阻塞` 或 `待确认` 的
   项目不妨碍后续平台继续执行。发布前立即确认 ledger 仍缺失且源文是可
   独立阅读的完整文章；重复、过时或不适合平台的任务改为 `跳过`。
3. 完成当天正常任务后，每个待补日期允许继续完成一条后续任务；公开页
   QA 成功后才消耗一个补发额度，同一平台当天不重复发布。
4. 需要平台操作时，调用对应 publisher skill，并只使用普通可见浏览器 UI。
5. 发布前使用本地完成的 platform artifact；发布后检查公开页并更新 ledger。
6. 平台文案和上传 artifact 放在
   `draft/media/YYYY-MM-DD/<source-slug>/`。只有真实异常、反馈或待跟进
   事项才写同日 `run-log.md`。

不创建月度 daily log、figure inventory、platform hooks、单篇 publish QA
或其他仅用于证明流程执行过的一次性文件。
