Why does the verifier reject an array lookup whose key is a loop counter rather than a constant, and what does the proposed fix change the nullness check to?

  4. References

Because the verifier's permission to drop the NULL check on an array lookup has been keyed on the wrong property. A lookup in an array or a per-cpu array returns NULL for exactly one reason: the key is not below max_entries. The verifier has known that since the nullness-elision change, but it grants the elision only when the key is a compile-time constant. A masked key such as cpu & 3, and the counter of a bounded loop, are not constants; they carry a range. So the program pays for a NULL branch it cannot take, and if it omits the NULL check it is rejected with map_value_or_null. The fix posted for review keeps every other condition and replaces the constant test with a bound test: read the largest value the spilled key register can hold, and elide the nullness only when that maximum is below max_entries.

The mechanism

  1. Why a NULL check exists at all. The helper is declared to return a pointer-to-map-value-or-null, so the verifier gives register 0 that union type. Passing it through a non-null test splits the state: the true branch keeps a plain map-value pointer, the false branch gets a constant null and must not dereference. Without a test, any load through register 0 is rejected, because the verifier must assume the null branch is reachable. The array lookup itself has one failure path: the index compared against max_entries, returning NULL when it is not below.

  2. What the elided check requires today. For an array or per-cpu array, and only for bpf_map_lookup_elem(), the verifier tries to prove the key statically. Every condition in the current code must hold: the program has CAP_BPF; the key argument is a stack pointer at a constant offset; the covered stack bytes are either zero bytes, which means key zero, or one scalar spill exactly the four bytes of an array key; and the spilled register's value is a constant. When that succeeds the verifier clears the maybe-null flag on the return type, so the program can dereference directly. Because the verdict now depends on that value, the slot is marked precise, which stops the verifier from pruning a state on the assumption that the key is unknown. Any miss — a range instead of a constant, an unaligned or partly overwritten slot, an inner map — leaves the return nullable.

  3. Why a loop counter used to work. Bounded loops were verified by exploring the state of each iteration, so a counter incremented by a constant reached states where its value was known exactly, and the four-byte spill of such a state is a constant. A recent change to how the loop bound is computed and how registers are widened across iterations gives the counter one range that stands for every iteration instead. Now no state has a constant key, the static test fails, and a loop that previously loaded is rejected. The posted change carries that commit as the one it fixes. The masked-key case is older: a value like cpu & 3 has never been a constant, so a null-check-free lookup with a masked key has been rejected for as long as the elision has existed.

  4. What the fix actually changes. The helper that reads the key now compares the register's unsigned maximum against the map's max_entries instead of asking whether the value is constant, and the caller keeps the largest value rather than an exact one. Nothing else moves: the capability test, the constant-offset stack key, the four-byte spill or zero bytes, the inner-map exclusion, and the precise-marking all stay. The elision is still applied only to bpf_map_lookup_elem(), so the per-cpu lookup variant that takes a cpu argument does not get it. The generated code is untouched: the lookup still compares the key with max_entries at run time.

  5. Why the maximum is read as 64-bit. The stack slot inherits the range of the 64-bit register that was spilled into it, while the key is four bytes and max_entries is a 32-bit value. That is sound in the direction that matters: any value below max_entries fits in four bytes, so the helper reads the same value the verifier reasoned about. It also handles the signed-looking range correctly. A key whose range is minus one to zero can hold 0xffffffff, which is never below a sane max_entries, and the unsigned maximum is enormous, so the elision is refused and the null branch stays — which is the right answer, not a conservative accident.

  6. Why the verdict becomes range-sensitive. Once the elision depends on a range, two states whose key registers have different ranges are no longer equivalent, and the state that has been verified with an elided null check must not stand for one that has not. The posted tests pin this with a forced state-explosion flag: a path whose key range is in bounds on one branch and out of bounds on the other must be rejected, because the in-bounds path would otherwise cover the other. This is also why a small share of programs cost more instructions rather than fewer.

How to verify and debug

  1. Read the rejection. The message is a memory-access complaint about register 0 naming the map-value-or-null type, pointing at the load after the lookup, not at the lookup itself. That shape means the verifier kept a null branch and the program did not test it.

  2. Test the exact conditions, one at a time. Substitute a literal key: if the program then loads, the key was the problem. Then replace the literal with a masked value of the same width, and with the loop counter, to see which of the three cases you are in. Add a null test as a control: a program that tests is accepted regardless of the key shape, so a test-and-pass, no-test-fail pair isolates the elision rather than the map.

  3. Check the four silent disqualifiers. A program without CAP_BPF never gets the elision. A key whose stack slot is written in pieces, or at an offset that is not a constant, is not a single tracked spill. A map created with the inner-map attribute is excluded by design, because at run time the inner array can have fewer elements than the prototype the verifier sees. And the per-cpu lookup variant that also takes a cpu number is outside the elision even on an array map.

  4. Look for the range the verifier sees. Confirming that the key register has an unsigned maximum below max_entries is the whole check. A mask is the cheapest way to produce such a range; an unmasked counter that is only bounded by a comparison against a large value is not, because its maximum is that bound.

  5. Compare verification cost before and after. The posted measurements are the useful reference: on one scheduler workload roughly six percent of programs changed, with a several-percent instruction reduction in total and a handful needing more; on a large set of production networking builds nothing changed at all. Programs that grow are the ones where the key now has to be tracked as a range instead of being pruned as unknown.

The limitation

  • The fix is a posted change against the development tree, not a released kernel. Until it is merged, a ranged key needs either a constant key or a null test.
  • It only helps where the range is provably inside the map. A key that can exceed max_entries on some path still returns a nullable pointer on that path, and the program must handle it.
  • Eliding the null check does not change run-time behavior. An out-of-range key would still return NULL; the verifier has simply proven that this cannot happen for this program.
  • Two adjacent gaps were reported in the same window and are not closed by this change: a call to a static subprogram or callback can overwrite a pointer that the caller spilled in its own frame, which breaks the same kind of stack-argument analysis; and the analysis of an implicit argument of a kernel function marks a register live that the program cannot reach. Both are open review threads.

Community discussion today

This run reviewed six communities. Three channels in two archive-backed chat workspaces were read through the approved read-only archive for both the 24-hour and 7-day windows and returned no message, so they were quiet rather than skipped. The ten channels in the two other chat workspaces were not covered: reading them needs an authenticated browser session and this environment has none, so they are recorded as not covered, not quiet. One mailing list and one practitioner forum were read in full through their public pages. That makes two of the six allowlisted sources reviewed with content, two reviewed and empty, and two inaccessible.

The mailing list carried the question answered above as one patch inside a much larger repair effort, and the useful way to read this window is as a coordinated cleanup of state that BPF code mutates and then forgets to revalidate. A 27-patch fixes set for the current stable line splits into three families. The first clamps a length before it is used as an offset in the stack-trace helpers, in both the trace-length limit and the skip test, which is the same class of defect as an unchecked packet offset: a caller-supplied size is trusted after a truncation that the callee does not see. The second family is about memory regions: refusing to map an arena at address zero, refusing a mapping longer than the map's own page count, not letting the free routine observe a half-set range, and dropping a warning from the mapping hook. Those are the sharp edges a program hits once an arena is genuinely used for data rather than as an extra map, and the fixes are all "reject earlier" rather than "handle later". The third and largest family is the segment-routing and lightweight-tunneling helpers, where a BPF program rewrites packet headers: the network offset must stay signed, an encapsulation request must refuse a packet that is not the expected family, the header-adjustment helper must move the link-layer header along with the network header and must not leave a stale one behind, the socket-buffer control block must be reset after an encapsulation, a reroute flag must be required once the program changes the protocol, and the transport header must follow the headers that moved. Read together, these are one lesson for anyone writing header-rewriting programs: after a BPF program changes a packet, several derived pointers and cached values in the socket buffer are stale, and every helper that forgets one of them produces a wrong checksum, a wrong length, or a fault rather than a clean error. The most likely mechanism for the whole family is that the helpers were written as local edits on a single field, and the invariants they break live in a different structure. The practical diagnostic path is to run a header-rewriting program under both the transmit and the receive path and to test protocol changes separately from size changes; the unresolved part is that none of this is currently checked centrally, so a new helper can reintroduce it.

The second big set is fifteen fixes for socket-map and socket-message handling, and it is a distinct but related theme: verdict and redirect state that survives the operation that set it. The reports describe a drop verdict sticking into later traffic, a pass verdict covering the next message, a resume state left behind by a stopped socket, redirect targets not rechecked before each send, a copy position that is not reset when corking, a zero-length copy into a full cork, and a redirect that loses the rest of a corked buffer. For a practitioner the symptom is a service whose behavior after one unusual receive — a partial read, a fault while copying to user memory, a send that blocks — differs from the same service under clean traffic, which is exactly how these defects survive testing. The mechanism in every case is a per-socket field that is set on one path and cleared on a narrower one. The diagnostic path is to drive the failing operation with a program that returns each verdict in turn and to compare the next message's behavior, and to check the socket's state after a blocking send rather than only after a successful one. What remains uncertain is coverage: the fixes arrive as individual commits, and the window contains no test plan that exercises the verdict, cork, and redirect states as a matrix.

A third, longer-running thread is a fourteen-patch proposal to give programs a stack inside an arena. Its motivation is concrete and is the reason people keep asking about running code compiled by a general optimizing compiler as a BPF program: a data structure that holds a plain pointer to an object does not say which memory region that object lives in, so one load instruction has to work for heap memory, for read-only and global data, and for a local variable whose address was taken. That is only possible if all three live in one addressable region, because one instruction has one form once the code is compiled. The second motivation is size and reentry: programs of this kind routinely need tens of kilobytes of stack, and the existing private stack gives one frame per function per cpu, so it supports neither recursion nor a second run on the same cpu. The proposal adds a dedicated stack register, per-program stack areas in the arena, a way to keep pointers stored in an arena relocatable, and a local atomic operation, with support for the two main instruction sets. Review in the window is about the boundaries rather than the idea: how casts of pointers that are not in the arena should be treated, what the default size of an arena should be when the map does not state one, and where the new register may appear. For readers of this page the relevant consequence is that a program whose stack or pointer layout crosses the current model is not necessarily wrong; the region model is what is limiting it. The same window also carried a request to treat two earlier cross-subprogram jump fixes as security fixes and to add stable-tree tags, answered on process grounds — plain-text submission, and no need to involve the security list for something already resolved — which is the practical hurdle for anyone who needs a JIT fix backported.

Smaller items, all open or in early review: a zero-copy packet-socket fix that stops freeing a receive buffer when the receive ring is full, which is a leak precisely under ring pressure; a lightweight-tunneling fix that frees the socket buffer when the transmit path cannot expand the headroom, the same class of error handling; a transmit-queue fix that rejects a negative transport-header offset, again header-offset signedness reaching an arithmetic path; a tooling change that strips a build machine's compiler debug records before generating kernel type information; a third revision of a change that makes dumped enumeration values respect their signedness in two tools, with a matching fix for data dumps; and a report that a serialization cache can return pre-relocation bytes after a split-BTF object is re-parented onto a different base. On that last one the review turned into a real boundary question rather than a yes-or-no: for read-only objects parsed from a file, the in-memory type data points into the same buffer as the serialized form, so that buffer is not a cache and invalidating it would force a copy, turn name lookup linear, and make a newer object format fail outright, whereas only the byte-swapped copy is genuinely stale. The author of the report demonstrated the failure with a self-contained reproducer and a regression test, and the reviewer asked for a narrower invalidation and a different target branch, so it is an open review with the mechanism agreed and the fix shape not.

On the practitioner forum there was no new post inside the 24-hour window. The newest substantive discussion, a few days old, is a hands-on report about a packet-crafting scanner built on the zero-copy packet socket API, and both of its open questions are the kind an engineer meets in the same order. The author first reported a speedup that turned out to be wrong because a bug had measured a single target host and a time below the floor implied by the program's own rate limit; the rebuilt benchmark checks that each run finds every expected port and records cpu time and dropped frames. Two findings then followed. Busy-polling with a pinned core, harmless on an idle laptop, was actively harmful on a loaded virtual machine because the spinning receive thread competed for the one vcpu; it is now used only in zero-copy mode, and the copy-mode path blocks. The larger win came from batching: the API has a single transmit ring, and one submit call per packet made the system-call overhead the whole wall-clock time on a slow host, so up to sixty-four frames are now submitted per call, which brought the time level with a conventional scanner at roughly a third of the cpu cost of a raw scan. The honest open boundary is that the remaining speedup depends on zero-copy operation on a multi-queue device the author cannot test, and the two questions are whether the wakeup flag is worth anything for copy mode on a single transmit ring and whether the busy-poll loop ever repays the pinned core. The fill, completion, and wakeup semantics that decide both are documented in the kernel's packet-socket documentation, and the practical answer for now is that the batching change is portable while the busy-poll decision is a per-host measurement, not a default.

This run's archive-backed sources produced no messages in either window, so the question above was sourced from the permitted public mailing list and verified against its patch thread and the released kernel sources, and the mailing list supplied every theme in this section apart from the forum paragraph.
