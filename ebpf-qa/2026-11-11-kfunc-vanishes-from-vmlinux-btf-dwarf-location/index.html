Why can a kernel kfunc vanish from vmlinux BTF with no change to its C prototype, and why does that break the build?

Because the encoder that turns DWARF into BTF decides whether to emit a function from the parameter locations the compiler recorded, not from the C ABI. A kfunc parameter that the compiler describes in a callee-saved register for the range after a spill, or describes only after the function entry, reads to the encoder as "unexpected register usage". It then skips the whole function, so vmlinux BTF carries no FUNC entry for a kfunc whose prototype never changed. Two later steps depend on that entry: the tool that patches the kernel's kfunc ID sets, and the kernel's own kfunc registration. One turns the missing entry into a build failure under CONFIG_WERROR; the other turns it into an initcall that returns -EINVAL, leaving the kfunc unregistered on a kernel that built fine.

The mechanism

  1. What the kfunc macro guarantees. __bpf_kfunc expands to __used __retain __noclone noinline in the kernel's BTF header. The documented consequence is that a kfunc keeps the calling convention of its C prototype: it is never inlined, never cloned, and never eliminated as unused. The kfunc documentation adds that a kfunc must not be static, because its externally visible name is how BTF-based resolution finds it. So the prototype written in C is the ABI, and a BTF function prototype built from that source signature is correct by construction.

  2. Where BTF comes from. The compiler emits DWARF while building the kernel. scripts/gen-btf.sh runs the encoder over that DWARF to produce a detached BTF blob, then runs resolve_btfids over the blob and the ELF to apply kernel-specific transformations and to fill in the .BTF_ids entries that kfunc sets are built from. BTF is therefore a build artifact of a compiler plus an encoder, not a property of the source.

  3. The encoder's skip decision. The encoder saves a function state per definition and emits it later. Each parameter carries the location the DWARF described: a register, an entry-value expression, a stack slot, or a constant. For a clang producer whose signature did not change, the encoder matches each parameter against the ABI argument register expected at that position, and a parameter recorded in a different register is flagged as unexpected register usage. When the saved functions are emitted, that flag, an uncertain parameter location, reordered parameters, optimized-away parameters, an inconsistent prototype, or an ambiguous address each set a skip reason and the function is not added to BTF at all. In verbose mode the encoder prints the reason, for example a skip caused by unexpected register usage for a parameter.

  4. Why a kfunc is exposed to it. A kfunc is noinline, so clang spills and reloads its parameters around the calls it makes. The resulting location list describes the value correctly but not in the ABI register at that point: in the reported case the list for the second parameter begins after the function entry and names a callee-saved register, and another kfunc in the same week hit the same skip through a different DWARF pattern. That is a correct description of where the value lives, and an ABI-neutral one, because __bpf_kfunc already pinned the convention. The encoder's check, written to protect callers from genuinely changed signatures, cannot tell the two apart. The shape is reproducible: compiling a small noinline function that calls out before using its second argument produces a location list whose first range is the entry register and whose later ranges name a callee-saved register. On an arm64 KCSAN build the parameter was reassigned once before use, and bpf_tcp_ops_set_rcvlowat disappeared from vmlinux BTF.

  5. What the missing function breaks at build time. resolve_btfids walks the BTF set definitions that carry the kfunc flag, resolves each listed name to a BTF_KIND_FUNC entry, and warns when the lookup fails. The set entry then keeps its placeholder, so a second warning reports the symbol as unresolved. Both are warnings, but the kernel's BTF makefile appends the fatal-warnings flag to resolve_btfids whenever CONFIG_WERROR is on. Warnings then become a nonzero exit, gen-btf.sh fails, and the link step prints Failed to generate BTF for vmlinux with the advice to disable CONFIG_DEBUG_INFO_BTF.

  6. What it breaks without CONFIG_WERROR. The build succeeds and the entry is patched to zero. At late_initcall the subsystem registers its kfunc set, the kernel looks up the function ID and validates that it names a function, and ID zero is the void type, so validation returns -EINVAL. The initcall returns -22, the kfunc set and the struct_ops registration behind it never happen, and the only trace is the initcall line in the log. A BPF program then fails at load on a kernel whose source, configuration, and C prototypes are all unchanged.

  7. Workaround and real fix. The immediate workaround is source-level and compiler-shaped: keep the parameter in its entry register by not reassigning it, for example by folding the clamp into the call argument with a conditional expression. A prior report in the same shape used a compiler barrier on the parameter so that its location names memory rather than a register, chosen because the register-hiding macro that worked on one architecture broke another. The real fix belongs in the encoder: for a function already identified as a kfunc, clear the location-derived flags when the state is saved, skip the location-based checks when emitting saved functions, and collect kfuncs whenever BTF is encoded rather than only when the decl-tag feature is enabled. The inconsistent-prototype and ambiguous-address checks still apply, since those describe real ABI doubt. The decl-tag condition had to go because resolve_btfids now emits the kfunc decl tags itself, and the kernel stopped passing that encoder feature.

Verifying it

  1. Ask the running kernel what it has. A missing FUNC entry is the whole defect, so check the artifact rather than the source:

    The count is useful as a sanity check: with the current build chain the decl tags come from the ID sets, so a function that still has a set entry but no tag at all suggests a different failure than a dropped function.

  2. Read the encoder's own reason. Re-run the encoder verbosely over the object that failed and grep for the skip message. The skip reason names the parameter class, which is what distinguishes this from a genuinely inconsistent prototype.

  3. Look at the DWARF the encoder saw. Disassembling the debug location lists shows the shape directly: a range that starts after the function entry and names a callee-saved register, or an entry-value expression. Pair it with the disassembly to confirm the value really is in that register for that range; the location list is a description, not a bug in itself.

  4. Distinguish build failure from silent non-registration. If the build stopped, look for the missing-function warning before the fatal-warnings exit. If it did not, grep the boot log for the initcall line and its -22, then check whether the kfunc set is registered at all. The two outcomes have the same root cause and different evidence.

  5. Confirm the fix by diffing BTF, not by rebuilding twice. Rebuild with the fixed encoder, dump both BTF blobs, and compare function lists. The posted fix reports that only the two dropped kfuncs come back and nothing else in vmlinux BTF changes; a wider diff means the encoder changed more than the exemption.

Limits

  • The exemption is encoder-version bound. Released encoder versions still drop these functions, so a source workaround, an encoder pin, or a backport is needed until the fix ships. On a host whose encoder predates the clang location matching, the same object encodes cleanly, which makes "our build is fine" an unreliable conclusion without recording the encoder version.
  • This is not the only way a FUNC entry goes missing. Inlining, an inconsistent prototype, a signature change, or an ambiguous symbol address all drop a function too, and for those the drop is correct. The kfunc case is special only because the macro already fixed the convention.
  • The full check is a build-and-dump loop, so it belongs in kernel build validation, not in a BPF program's unit test. A program cannot detect at load time whether its kfunc is present; the failure it sees is an ordinary "unknown func" or a missing struct_ops member, which points at the wrong layer.
  • None of this makes a running kernel's BTF trustworthy across rebuilds. The same source built with a different compiler, encoder, or optimisation level can move a parameter into a different register and change which functions are emitted.

Community discussion today

This run reviewed two allowlisted communities through the approved private read-only archive, covering three allowlisted channels: one channel held no message in the 24-hour window and none in the seven-day window, and the other two held none in 24 hours and four in seven days, all four belonging to one thread about booking a conference table, with no technical content. Both Discord workspaces, ten allowlisted channels in total, were not covered: this environment has no authenticated session, and though the public invite page now loads, it only offers account creation. They are recorded as inaccessible rather than quiet. The practitioner forum was readable this run and had no post inside the window; its newest posts are four days old, and two of them are substantive. The kernel mailing list was read through its public archive, and both the question above and the themes below come from it.

BTF is emitted from debug information, so a metadata defect is a build defect

The answered case is the clearest one this window, and it has a second instance in the same week. A separate scheduler patch had already worked around the same encoder behaviour for a different kfunc, by forcing the argument into memory so its location names no register; that fix says explicitly that the register-hiding helper would have fixed one architecture and broken another. Read together, the two reports describe one boundary: whether a kfunc exists in BTF is decided by a DWARF heuristic, so the same C prototype can be present in one build and absent in the next. The practical diagnostic is to record the encoder version with the kernel build and to diff BTF dumps across builds, because the load-time error a BPF program sees names the kfunc, not the encoder. The unresolved part is deployment: until the encoder fix ships, distribution kernels built with an affected encoder plus CONFIG_WERROR will fail their build, and those without it will boot with unregistered kfunc sets.

Loop iteration counting changed shape, and it can change verdicts

An active six-patch series replaces the verifier's eight open-coded bounds in its scalar-evolution code with a single small scalar abstraction, and computes the loop backedge-taken count in one function instead of separate constant and range paths. Two consequences are stated rather than implied. More loops now get a count, including some that today fall back to the may_goto mechanism, and a count can cost instructions: the cover reports 90 to 247 instructions for a 32-iteration loop when a value in the body has no linear form. And a counted loop is summarised as initial plus step times count, so a count from one exit can invalidate an index bound that another exit does not constrain; the cover shows a loop that loads today becoming a rejected load after the counting patch and loading again after the latch patch. The reported validation is unusually complete: 1.1 million public programs with no verdict change, and the two Rust programs that grow in instruction count are named. For a practitioner the practical rule is to keep a failing program and its verifier log when upgrading a kernel, and to read an instruction-count change as a real change to what the verifier had to prove.

Networking metadata is being unified, and the hook decides the mechanism

Two related series ran in the window. One proposes a per-skb extension area so receive-side metadata survives XDP_PASS and redirects, on the argument that hash, VLAN tag, and checksum handling are being fixed piecemeal in separate attempts; a reviewer's concern is that XDP is growing a second metadata area and slowly becoming an skb. The other adds a per-device transmit headroom reservation so an egress program that pushes headers stops reallocating the packet head, and it distinguishes the new value from the driver's existing needed headroom precisely because the latter is fixed at device creation and expanding it regresses current paths. Two details in the exchange are worth carrying: the headroom can be declared by a BTF declaration tag on a tc program, the attached programs' tags sum, and the total is clamped, so a tag is a request rather than a guarantee; and the reservation is applied only where packets are allocated, which is why TCP is explicitly out of scope. A remaining boundary is that native XDP on a veth peer still copies, because the head must also be a page fragment, not only large enough.

AF_XDP zero copy is being re-expressed as a page-pool provider

A larger series makes UMEM a page-pool memory provider, so a driver that already owns a page pool no longer needs a second receive allocator for zero copy. The structural changes are a refill contract replacing NAPI kicks, an explicit capability saying whether the stack may keep provider buffers, and an unchanged xdp_buff whose head pointer lives in driver memory. The cover states its own costs: multi-buffer frames redirected to a device map or a cpumap are dropped after being linearised, generic XDP and cpumap cannot feed a provider socket, and only aligned chunks are supported. It also leaves one question open for userspace, which is how a socket learns the chunk constraints before bind. For anyone operating AF_XDP today, the useful reading is that the zero-copy fast path is being kept and the copy-mode plumbing is what changes, so throughput claims should be re-measured per driver once the series lands.

Smaller signals, each a boundary between what a subsystem promises and what a tool derives. A symbol-search optimisation series for kallsyms was on its third revision, a reminder that large generated symbol tables have their own build-time cost curve. And a tc-only attachment design in the headroom discussion shows the recurring trade: a per-device hook lets the kernel know which device to update, while a filter shared by several devices does not.
